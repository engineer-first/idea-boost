# PBIを一緒に考える

IdeaBoostのPBIを、目的・背景・期待する振る舞いから一緒に考えます。
実績の整理、新しい希望、相談Issueの具体化、複数Taskの束ね直しを自然な言葉で頼めます。
以下は依頼例です。例の文言やモード番号を使う必要はなく、どの入口でもまず草案だけを頼めます。

AIは依頼と資料から入口を判断し、最初に「今回は実績から整理します」など短く示します。
実績と未完Taskが混ざっていれば部分ごとに扱い、不明な点だけ確認します。

## 実績から整理したい

> この期間に終えたIssueと実装PRから、まだPBIに紐付いていない実績を整理したい。まず全体の草案だけ見せて。

渡すとよい資料：対象期間・締切時点、リポジトリ、完了Issue・対応PRのURL、既存のPBIや対応表。
Issueの当初予定とPRの実際の変更を照合し、実現した成果と未確認の効果を分けます。

## やりたいことと背景から考えたい

> 付箋を続けて書くときに考える流れが途切れる。何ができると嬉しいか一緒に考えて、まずPBIの草案だけ作って。

渡すとよい資料：誰が・どんな場面で困るか、望む結果、本人の発言や利用観察、関連する要求。
実装PRは不要です。足りない背景は仮案として確認し、AIが事実として補いません。

## 上位の相談Issueを具体化したい

> この相談Issueにはいくつか目的が混ざっている。背景を一緒に詰めて、目的ごとのPBI案に分けたい。まず草案だけお願い。

渡すとよい資料：相談IssueのURL・本文・回答、関連資料、すでに決めたことと保留中のこと。
元の要望と各案の対応を示し、目的が不明な要望を黙って落としたり、採用済みPBIとして登録したりしません。

## 複数のTaskから目的を整理したい

> このTask群は未完のものもある。何のための作業か整理して、同じ目的のものをPBIにまとめたい。まず草案だけ見せて。

渡すとよい資料：各TaskのURL・要求・背景・現在の状態、親PBIの有無、分かる範囲の関連資料。
未完Taskも扱えます。実装済みやPRの存在を前提にせず、これから必要な成果と残る作業を明らかにします。

## 草案から反映まで

草案 → あなたのレビュー → 修正 → 依頼された範囲をGitHubへ反映、の順で進めます。
最初に全体数・残る判断・今回の終点を示し、4件程度または全案をまとめて見せます。
タイトル・背景・期待する振る舞いと判断材料を見て、目的の違い、背景の訂正、統合・分割、保留を伝えてください。
「まず草案だけ」の段階ではGitHubを変更しません。内容に合意しても、それだけで登録済み・受け入れ済み・完了とは扱いません。
反映を頼む場合は「この案をIssueに反映して」のように対象を伝えれば、その依頼範囲で更新し、結果と残件を確認します。

## チームで使う

このリポジトリをチェックアウトし、対象ツールから開いて使います。
共通のスキル実体はこのディレクトリの[SKILL.md](SKILL.md)。CodexとOpenCodeは `.agents/skills/pbi`、Claude Codeは既存の `.claude/skills/pbi` symlinkから読みます。
読込経路の保守は[共有スキルの正本](../../../docs/development/agent-maintenance.md#共有スキルの正本)、
書き残す型・採番・GitHub状態は[Issue運用](../../../docs/team/issues.md)と[PBIフォーム](../../../.github/ISSUE_TEMPLATE/01-pbi.yml)を参照してください。

## 短い入力で始める

「付箋を追加するたび入力先を探して考えが途切れる。続けて案を書ける体験にしたい。Why中心の短いPBIを一緒に考えて」だけでも始められます。
解決方法・具体仕様は担当者とAIで詰めます。実績IssueとPR、壁打ち、相談・要望、既存Taskのどの入口にも固定の大きな入力フォームは求めません。
