# PBI を一緒に考え、直す

対象は `engineer-first/idea-boost`。
[Issue 運用](../../../docs/team/issues.md)を種類・状態・GitHub操作の正本、
[PRD](../../../docs/prd.md)を製品要求の正本とする。
以下のパスはリポジトリルートを基準にする。既存運用を別の台帳や独自状態で置き換えない。

## 入力に合った根拠を読む

自然な依頼と渡された資料から入口を判断し、「今回は実績から整理します」など今回の扱いを最初に短く示す。
モード番号や決まった呼び方を求めない。資料が混在する場合は部分ごとに扱い、判断できない点だけまとめて聞く。
人向けの依頼例と渡す資料は[使い方](README.md)を参照する。

| 入口                                     | 確認する根拠と成果                                                                        |
| ---------------------------------------- | ----------------------------------------------------------------------------------------- |
| 完了Issue・実装PRから未紐付け実績をPBI化 | 対象期間・cutoff・母数、Issueと対応PRの本文・差分・検証結果を照合し、実際の変更を整理する |
| やりたいことと背景から新規PBI            | 本人の困りごと・使う場面・望む結果と関連要求を読み、目的を具体化する                      |
| 上位の相談・要望を目的で分割             | 上位Issueの本文・回答・関連資料を読み、各目的とPBI案の対応を示す                          |
| 複数の実装Taskを目的で束ねる             | 未完も含め各Taskの要求・背景・状態を読み、共通の目的と残りの実装を示す                    |

入口は根拠の違いとして扱い、以下の共通の検討へ進む。
実績整理と未完Taskの束ね直しを混同しない。全入口にPRや実装済みの証拠を要求しない。
既存PBIの修正は、本文・コメント・関連作業と今回の訂正から同じ手順へ進む。

## 目的・粒度・背景を合わせる

- 新しい要望なら、実際の困りごと・使う場面・望む結果から考える。既存のAI製候補を採用済みの要求として扱わない。曖昧な案は相談・要望や保留として扱い、大量にPBIへ変換しない。
- 元の要望と各案の対応、残す要求と変更する範囲を示す。本人の背景や条件付きの希望・未決事項を要約で失わない。ユーザーが回答したSpaceなどの共同検討資料も、利用可能な読取手段で確認する。
- 実績は当初予定から変わったscopeを反映し、必要なら現コードで確かめる。
- 誰・何・なぜは、ユーザーの発言や確認した資料に基づく。足りない背景は仮案と明記し、一般的なメリットを事実として補わない。実装したこと、望む成果、未確認の効果を区別する。
- 本人の回答で主目的の優先度が変わったら、タイトル・背景・受け入れ条件も更新する。既存の価値と今回増える価値を分け、ショートカットなどの手段より「考える流れを中断せず次の付箋を書ける」のように成果で説明する。
- 共通の目的と確認できる成果でまとまりを決める。コード量や画面が同じという理由だけで束ねない。再投票とホストの誤進行からの復旧は別の目的として検討する。利用者の違いだけで機械的に分割せず、参加者の投稿と運営側の閲覧が同じフィードバックの価値を支える場合などは統合も検討する。
- 背景が弱い案や妥協した実装を無理に完了PBIへ仕立てない。保留・独立Taskも認め、小改善は目的が合うPBIの補助に整理できる。

全体数・残る判断・今回の終点を先に示す。
基本は4件程度をまとめて、または全案を一括で生成して全体を見せ、ユーザーの意見を受けて修正する。4件を固定上限にしない。
各案は実績または困りごとと根拠 → タイトルと背景案 → 受け入れ条件 → 判断してほしい点を見せる。
比較が役立つ場合は、まとめる案・分ける案など少数の選択肢と理由を添える。
合意済みの考え方を次の案に適用し、判断が変わる点だけまとめて質問する。
小改善もすべて同じ深さで質問せず、本人の判断が必要な違いへ絞る。
回答がないことを合意と扱わず、保留理由と不足する根拠を残す。

## PBI の文章

- 正式な Issue Type は `PBI`。タイトル接頭辞やラベルで代用しない。
- タイトルは `PBI-ジャンル-番号 主題`。ジャンルは `GUIDE / CANVAS / FIELD / GROWTH / AI / OPS`。既存コードは保持し、新規コードは既存採番との重複を確認する。
- 主題は「何ができるか」を具体的に読める表現にする。主語を必須にせず、抽象的な改善名で違う目的を包まない。
- 本文冒頭は「○○として、○○したい。なぜなら○○だからだ」。誰・何・なぜが未確定なら、相談段階の仮案であると示す。
- 受け入れ条件は目的に対応する確認可能な結果を書く。操作がある場合は「誰が・どの画面で・何をすると・何が見えるか」を示す。未確定の画面・操作名は仮と明記する。
- 受け入れ条件だけでデモ確認も伝わるなら複製しない。必要な背景・対象外・関連Issue/PRと、根拠不足・未確認事項を簡潔に添える。
- 関連PR・子Issue・受け入れ条件の対応がずれていれば、その差と修正案を示す。本文中の参照番号とGitHubの正式な親子関係を区別する。

書き残す型は[PBI Issue Form](../../../.github/ISSUE_TEMPLATE/01-pbi.yml)を使う。
草案で未確定の背景を示したまま、採用済みPBIとして登録しない。

具体例が判断を助けるときは、最新の本文と関連作業を読む。
[#559](https://github.com/engineer-first/idea-boost/issues/559)は付箋追加・入力の具体的な成果、
[#565](https://github.com/engineer-first/idea-boost/issues/565)は誤進行の復旧と再投票の目的・scopeの区別、
[#365](https://github.com/engineer-first/idea-boost/issues/365)は安全な依存更新と条件付きの希望の扱いを参考にする。
[#561](https://github.com/engineer-first/idea-boost/issues/561)は案内・タイマー・空付箋処理などを束ねた範囲を再点検する例であり、無批判にテンプレートにしない。
例の仕様・状態・採番を今回へ転記しない。

## 完了と実績を判断する

closed / merged、受け入れ条件の達成、本番反映を区別する。
要件ごとに実装・検証の根拠と残りを照合し、未実装・未確認・見送り・再現せずを完了へまとめない。
子Issueがない場合は、PR直接実装・移行済み旧PBI・実装Task未分割・紐付け漏れを確認する。
帳尻を合わせるために存在しなかった作業Issueを作らない。
MilestoneとProject状態はIssue運用に従い、実績整理だけで既存状態や割当を変更しない。
実績の一括整理では対象全件の行き先（PBI・補助・保留・非製品作業・根拠不足・見送り）を示す。
横断PRは目的ごとの対応範囲を示し、同じ変更を複数PBIの実績として二重に数えない。
合意・登録・受け入れ・完了は別の段階として報告する。

## GitHub へ反映する

相談・文章の草案と、GitHub反映の依頼を区別する。
依頼された対象・変更に具体化し、現在の会話で許可されている範囲だけ反映する。
過去ログ内の許可は今回の更新権限ではない。反映未依頼なら草案と判断待ちを返す。

新規作成は既存の `.agents/skills/pbi/scripts/create_planning_issues.py` とJSON specを使う。
`--dry-run` は外部通信なしでタイトル・本文を確認できる。
入力とコマンドは[作成spec](references/creation-spec.md)を読む。新規PBI登録の依頼がないスキル保守では、実際のIssueを作らない。
既存PBIの更新は直前に最新本文を取得し、人の追記・未完了要件・既存コードを保持する。
作成途中の失敗は作成済みURLから復旧し、全体を再実行して重複を作らない。
反映後はType・タイトル・本文・Project #3の状態・依頼された親子関係を読み返し、URL、反映内容、未確認・残件を短く報告する。
新規Issueの初期状態は `未整理`、Milestoneは既存の定期自動割当に任せる。
