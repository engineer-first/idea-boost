# PR本文の具体例

本文の構成・前後表の要否・確認の粒度に迷ったときに読む。
構成の正本は[PRテンプレート](../../../../.github/pull_request_template.md)。
以下は書き方の見本で、今回の差分や検証結果を保証するものではない。

## 例1：一覧と詳細の往復を改善する

[PR #518](https://github.com/engineer-first/idea-boost/pull/518)を短く組み替えた例。
操作単位の説明で前後の差が分かるため、比較表を追加しない。
元PRにある採用理由は残し、対案の検討記録がないため対案の項目は省いている。

### Why

運営が共有成果を探す手段がなく、詳細から戻るとホームへ出てしまう。
追加取得でも一覧の先頭へ戻るため、成果を見比べる作業が途切れる。
探して開き、同じ条件・位置へ戻れるようにする。

### 実装内容

- **成果を探す**：名前・ID・保存状態・日本時間の期間で絞り込み、条件をURLに保存する。
- **一覧と詳細を往復する**：戻る操作で取得済み一覧・位置・選んだ成果へのフォーカスを復元する。
- **通信失敗から続ける**：追加取得中も一覧を保ち、失敗した取得を再試行できる。

画面の変更は[変更前／変更後と操作確認コメント](https://github.com/engineer-first/idea-boost/pull/518#issuecomment-5977629631)。
同じ利用者・データ・画面サイズで比較できる。

### 設計判断

- **問い**：保存用の記録への反映待ちがあるとき、検索対象をどこから判定するか。
- **決定**：RoomDOの現在の記録を使い、反映待ちによる取りこぼしを避ける。

### 動作確認手順

#### 要件1：詳細から一覧へ戻り、比較を続けられる

1. 共有成果の一覧で条件を指定し、追加取得後の一覧を下へスクロールする。
2. 成果の詳細を開き、ブラウザの「戻る」「進む」を使う。

期待結果：一覧へ戻ると条件・取得済み一覧・位置・フォーカスが復元される。
元PRの確認結果：Chromiumで51件の一覧を操作し、位置とフォーカスの復元、日付条件の保持を確認。
Safari・Firefox・実機スマートフォンは未実施。

#### 要件2：追加取得に失敗しても、同じ一覧から続けられる

1. 追加取得を通信失敗させ、取得済み一覧が残ることを確認する。
2. 再試行し、追加取得した一覧から詳細を開いて戻る。

期待結果：一覧を保って再試行でき、詳細からの復帰で位置を失わない。
元PRの確認結果：Chromiumで失敗→再試行→詳細→戻る／進むを確認。
遅い応答と認可拒否は関連テストで確認。
全体の検査結果は[元PRの確認結果](https://github.com/engineer-first/idea-boost/pull/518)を参照。

## 例2：役割・条件による違いは表で補う

[PR #519](https://github.com/engineer-first/idea-boost/pull/519)の退出後の成果閲覧条件を整理した例。
これは条件の表であり、変更前後を比較する場合は比較元ブランチで確認した列を加える。
未確認の「変更前」を想像で埋めない。

| 退出方法         | 完了後の本人の成果閲覧 |
| ---------------- | ---------------------- |
| 成果を残して退出 | 期限内に閲覧できる     |
| 成果を残さず退出 | 閲覧できない           |
| ホストによる除外 | 閲覧できない           |

このように同じ対象に複数条件がある場合、文章を繰り返すより表が適する。
図が必要なら[図の具体例](diagrams.md)から、争点に合う種類を選ぶ。

## 例3：DB変更の確認は利用者操作を作らず書く

[付箋の文字サイズのmigration](../../../../workers/room-do-migrations/20260922114121-add-note-font-size.sql)を題材にした確認記述例。
SQLの差分と既存データの扱いは[DB変更の具体例](diagrams.md#db変更3種類の図に加えて書く)へ。
この例にはテストの実行記録を含めていないため、確認済みとは書かない。

### 要件：既存の付箋を失わず、文字サイズの保存先を追加できる

- 確認条件：変更前のスキーマに既存の付箋があるRoomDO。
- 手順：対象migrationを適用し、付箋が保持されること、設定行がない付箋は14pxとして読めることを確認する。
  設定を追加して12〜24の整数が保存でき、範囲外の値が拒否されることも確認する。
- 期待結果：既存の付箋を保持し、設定の有無に応じて補完または保存値で読み取れる。
- 確認結果：未実施。今回のPRでは、実行したWorkerテスト・DB検査・適用確認の結果に置き換える。

## 小さな変更では短くする

図・DBの変更・設計判断に該当しない節は削除する。
文書だけの変更はWhy・変更した記述・リンクや整形の確認でよく、架空の画面操作を足さない。
確認に成功した件数や内部の評価点を中心にせず、満たした要件と残った確認を伝える。
