# PR を書く

レビューする人が「何がどう変わるか」「何を確認できたか」を少ない読み直しで理解できる PR にする。

本文の構成と各欄の目的は、リポジトリルートの
[PR テンプレート](../../../.github/pull_request_template.md) を正本とする。
以下のパスとコマンドは、特記がなければリポジトリルートを基準にする。

## 変更を把握する

- 作成時は remote、ベースブランチ、現在のブランチを確認する。更新時は対象 PR の現在のタイトル・本文・ベースブランチを取得する。
- ベースブランチとの全差分を読み、関連する仕様や既存テストで意図を確認する。最新コミットだけを見て PR 全体を説明しない。
- テスト・操作確認の実行結果を集める。会話中に記録された結果や対象コミットの CI 結果も使えるが、確認後の変更で古くなっていないか確かめる。

## 人が読む本文を作る

- タイトルと冒頭で、具体的な問題と変更後の結果を伝える。バグ修正なら「どの操作で何が起きていたか → どう直るか」を短く書く。
- 変更内容はレビューに必要なまとまりに絞り、理由を添える。ファイル一覧、試行錯誤、会話の経緯は省く。スコープが変わったらタイトルと本文を最終差分に合わせて書き直す。
- 確認結果には、実行したコマンドや操作と結果を書く。手動確認は条件・手順・結果が再現できる粒度にする。未実施・失敗・環境による制約を成功扱いしない。
- 長いログはリンクにし、追加の比較画像や詳細は必要に応じて `<details>` にまとめる。主要な結果や未確認事項は折り畳みの外に残す。
- テンプレートの案内コメントと空の箇条書きを除き、該当しない任意の節は削除する。変更を理解するために必要な情報を優先し、同じ説明を複数の節で繰り返さない。

## 画面や操作の変更を見せる

- UI の変更には、実際に描画・操作した画面のスクリーンショットや短い動画を用意する。見た目の変更は変更前／変更後を並べ、ドラッグなど動きが重要な変更は動画を優先する。
- 変更前後は画面サイズ、データ、ステップ、ユーザーの役割などを揃える。ベースブランチ側を撮る必要があれば一時 worktree などで分離し、作業中の変更を壊さない。新規画面など変更前が存在しない場合は、変更後とその旨を示す。
- 各画像・動画に、どこを見ると何が変わったか分かる短い説明を添える。主な変更を理解できる少数の場面を本文に載せ、網羅的な画面一覧は折り畳みや Storybook へのリンクにまとめる。
- その環境で利用可能なブラウザ・撮影・添付手段を使い、レビュアーがアクセスできる URL で載せる。ローカルパスを GitHub の画像 URL として貼らない。添付後は PR 上で表示・再生できるか確認する。
- 撮影や添付ができない場合は、欠けている資料と理由、代わりの確認手順を書く。添付したことにしたり、「後で追加」の空欄で済ませたりしない。

## PR に反映する

- 下書きの依頼なら本文を提示する。PR の作成・更新を依頼されている場合は、その範囲で反映する。Issue の新規作成はこのスキルに含めない。
- `Closes #番号` は手書きしない。既存の `.github/workflows/pr-issue-link.yml` が PR 作成時にブランチ名の最初の数字から自動追記する。Issue と紐付けない PR では、ブランチ名に数字を含めない。
- 既存本文を更新する直前に最新の本文を取得し、人が追記した内容、`<!-- issue-ref:... -->` と対応するリンク、Bot が管理する節を保持して編集する。作成時に保存した本文で全体を上書きしない。
- CLI を使う場合、複数行の本文は一時 Markdown ファイルに書き、`gh pr create` / `gh pr edit` の `--body-file` で渡す。
- 反映後にタイトル・本文・差分を読み直し、対象ブランチ、画像・動画、確認結果、追記情報が意図どおりか確認する。ユーザーには PR の URL と要点を返す。
