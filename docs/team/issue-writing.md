# Issue記述ルール

読者: IdeaBoostのIssueを作成・レビューするチーム全員とAIエージェント。
Issue Type・採番・親子関係・状態・スプリントは[Issue運用](issues.md)に従います。この文書が人・AI・外部ツール共通の正本です。フォームは入力支援、AGENTS・Skillsはここへの案内です。

## 起票時はWhyを中心に短く書く

Issueは担当者がAIと解決方法を考え、PRへ進むための入口です。起票時には現状の問題、利用者への影響、改善が必要になった背景を事実に基づいて書きます。「誰が・どんな場面で・何に困り・どう変わるとよいか」をWhyの中で具体化します。新しい必須欄にはしません。

解決方法・具体仕様・詳細テストが未定でも起票し、調査や壁打ちを始められます。空欄を埋めるために事実や合意を作らず、重要な未確認だけ短く添えます。タイトルはGitHubのタイトル欄だけに書きます。

| 種類       | 起票時に伝えたいこと                   | 担当者とAIが必要に応じて詰めること                                  |
| ---------- | -------------------------------------- | ------------------------------------------------------------------- |
| PBI        | Whyと、ユーザーに提供する体験          | 主要なユーザーに提供する体験、体験を確認する少数の観点              |
| Task       | 作業が必要な理由と現在の障害           | How・具体仕様・必要なら制約という小さな設計メモ、少数の作業完了条件 |
| Bug        | 起きていることと影響                   | 分かる範囲の再現条件、原因、修正方法                                |
| Spike      | 判断できず困っていることと調べたい問い | 調査方法と、次の判断に必要な成果                                    |
| 相談・要望 | 困りごと、望む変化、相談したいこと     | 目的の整理、必要ならPBIやTaskへの分割                               |

PBIは一つの目的と利用者・運営者が観察できる体験でまとめます。Taskの作業一覧やマージ件数をPBIの成果にしません。Taskは独立して進められる範囲にし、無関係な変更を束ねたり関数ごとに機械的に分割したりしません。

## 書き残す型

短いPBIの例（架空の仕様。今回のIssueへそのまま転記しません）:

```markdown
## Why

参加者は付箋を追加するたびに入力先を探しており、案を書く流れが止まる。思いついた内容を忘れる前に、次の付箋へ続けて案を書けるようにしたい。
```

短いTaskの例。タイトルは「個人作業中の付箋追加で入力の流れを保つ」:

```markdown
## Why

付箋を続けて書く際、毎回追加ボタンへ移動する必要があり、入力の流れが止まる。キーボードで案を書き続けられるようにしたい。
```

これだけで起票できます。PBIの体験を別に示すと読みやすい場合は `## ユーザーに提供する体験` に少数の結果を添えます。デモゴールは「ユーザーに提供する体験」であり、詳細なテスト手順ではありません。体験で伝わるなら別欄へ複製せず、デモの代表確認も必要な場合だけ同じ欄へ短く添えます。

冒頭の「参加者として、入力を中断せず案を書き続けたい。なぜなら、思いついた内容を忘れる前に残したいからだ。」というユーザーストーリーも任意で使えます。Whyは現状の事実と影響を補い、同じ文を繰り返しません。定型文やフォーム由来の見出しの削除は必須ではありません。

## 実装中の追記と人・AIの役割

担当者はWhyを起点にAIと壁打ちし、解き方を選びます。Taskには必要な範囲だけ `## How`、`## 具体仕様`、`## 制約`、`## 作業完了条件` を追記できます。起票時や着手前にすべてを埋める必要はありません。既知の仮説は仮と明記し、調査後に変わった重要な判断だけ更新します。

- Howは対象や方針に絞ります。技術選定・保存先・データ構造・代替案の比較は担当者とAIが必要に応じて考えます。根拠のないライブラリ名や内部の関数名を先に固定しません。
- 守る権限境界・互換性など、既知の重要な制約は理由とともに残します。対象外・画面イメージ・未確定事項も、判断を助ける場合だけ補います。
- 人は体験、設計判断、確認すべきリスクとテストの粒度を判断します。細かなテストケースの生成・反復検証はAIに任せ、全ケースの人間レビューを必須にしません。
- 完成を判断する観点は少数に絞り、詳細なケースはテストコードや必要な検証資料へ置きます。Issueを長い仕様書やテストケース集にしません。

上のTaskなら、壁打ち後に「How: 既存の追加処理を利用し、新規付箋へフォーカスを移す」「作業完了条件: 合意した操作で付箋を追加し、そのまま本文を書ける」と追記できます。日本語変換中・長押しなどの確認は、必要性と粒度を判断してAIにテストを作らせます。

## チーム全員が使う入口と保証範囲

GitHubの[Issue Forms](../../.github/ISSUE_TEMPLATE/01-pbi.yml)、空Issue、CLI / API、ローカルAI、外部ツールのどこからでも起票できます。固定の大きなフォームを要求しません。[pbi Skill](../../.agents/skills/pbi/README.md)では、実績IssueとPR、やりたいことの壁打ち、相談・要望の分割、既存Taskの束ね直しのどの入口も使えます。

外部ツールへの短い依頼例:

> engineer-first/idea-boost の docs/team/issue-writing.md を読み、この困りごとからWhy中心の短いIssueを作ってください。解決方法や未確認の背景は作らず、担当者とAIで詰められる形にしてください。取得できなければルール本文を依頼者に求めてください。

GUIはIssue Typeと必須入力を支援します。CLI / APIや外部AIがテンプレートやAGENTSを自動で読む保証はないため、ガイドのURLか本文を渡し、作成後にType・タイトル・本文を確認します。

### 入口を問わない作成後検査

[Issue Writing](../../.github/workflows/issue-writing.yml)はdefault branchへのマージ後、Issueの作成・編集・再オープン・Type変更で最新本文を検査します。PBI・Taskはタイトルと `Why` 見出しの有無・重複・空欄だけを確認します。How・具体仕様・作業完了条件・ユーザーに提供する体験・ユーザーストーリー・箇条書きは要求しません。フォームの `###` と通常の `##` は同等です。コード例やコメントだけではWhyの記入になりません。Bug・Spike・相談はこの構造検査の対象外で、Type未設定には分類だけを案内します。

不足はBot自身のコメント1件で案内し、再検査では同じコメントを更新、同じ結果は再投稿せず、解消後は解消済みにします。本文・タイトル・Type・親子関係・Project状態・Milestoneを変更せず、起票・着手をブロックしません。検査中の本文変更では古い結果の投稿を保留し、APIエラーはActions失敗として記録します。

GitHub Actionsが無効、イベント未着、`GITHUB_TOKEN`による作成・編集などで動かない場合は、Actions → Issue Writing → Run workflowから番号を指定できます。新しい認証設定は不要です。過去Issueの一括検査・書換えは行いません。

形式合格はWhyの真偽や十分さ、着手・完了を保証しません。チームは問題と体験が短く伝わるかを判断し、必要な確認を担当者と進めます。

### 機械検査の契約

責務と粒度は本文、必須見出しは以下を正本とし、フォーム・スクリプトとの整合をテストします。

## 分野ごとの良い例・悪い例

以下は必要に応じて実装中に具体化した場合の比較例です。起票時に全欄を埋める例ではありません。不具合の報告はBug、不確実性を減らす調査はSpikeも使えます。Bug・SpikeをTaskへ一律に変更せず、報告や問いから具体的な作業を切り出した場合にTaskの型を使います。

### UI: 付箋を続けて書く

- 良いPBIタイトル: 「付箋を追加し、続けて案を書ける」
- 良いPBIのWhy: 「追加後の入力先が分かりにくく、操作を探す間に案を書く流れが止まる。」
- 良いユーザーに提供する体験: 「参加者が個人作業画面で付箋を追加すると、本文へ直ちに入力できる。」
- 良いTask: Whyは「新規付箋に入力先が移らない」、Howは「作成後に本文へフォーカスを移す」、作業完了条件は「追加直後の文字が新規付箋に入り、既存付箋を変更しない」。
- 悪いPBI: 「UI改善」。ユーザーに提供する体験が「関数を追加する・イベントを登録する」では、利用者の成果が分かりません。
- 悪いTask: 「いい感じにする・見た目を確認したら完了」。対象と確認できる結果がありません。

### 機能追加: 結果を保存する

- 良いPBIタイトル: 「チームの検討結果を持ち帰って共有できる」
- 良いユーザーストーリー: 「参加者として、検討結果を保存したい。なぜなら、参加していない人にも結論を伝えたいからだ。」
- 良いWhy: PBIでは「参加していない人は検討に使った画面を閲覧できないため、参加者が結論を手作業で転記している」、Taskでは「保存に必要な結果の取得手段がない」と書き分けます。
- 良いユーザーに提供する体験: 「参加者が結果画面から保存した結果を渡すと、参加していない人も選んだ案と結論を確認できる。」
- 良いTask: Howは「既存の閲覧権限に従って保存用の結果を取得する」、作業完了条件は「閲覧権限のある利用者は対象結果を取得でき、権限のない利用者へ内容を返さない」。
- 悪いPBI: 「APIを作る」。手段だけで持ち帰れる価値が示されていません。
- 悪いTask: 「保存できること」だけでは、取得・画面・ファイル生成のどこを担当するか判断できません。

### 不具合: 再接続後も投票を保つ

- 良いPBIタイトル: 「接続が切れても投票をやり直さず参加を続けられる」
- 良いWhy: PBIでは「再接続後に投票が消えて見え、利用者が投票済みか判断できない」、修正Taskでは「再接続時に保存済みの投票を画面へ反映していない」と書きます。原因未確認なら後者を断定しません。
- 良いユーザーに提供する体験: 「投票後に接続が切れても、再接続すると自分の投票済み状態を確認できる。」
- 良いTask: Howは「Bugに記録した再現条件から、復元されない箇所を調べて修正する」、作業完了条件は「同じ条件で投票状態が復元され、重複投票が増えない」。
- 悪いPBI: 「Bugを3件閉じる」。件数では体験を判断できません。
- 悪いTask: 「原因は通信なので待ち時間を増やす」。根拠のない原因と手段を先に固定しています。

### 調査: 同時編集の遅延を調べる

- 良いPBIタイトル: 「複数人で編集しても変更を確認しながら議論できる」
- 良いWhy: PBIでは「他の参加者の変更が遅れて見え、同じ案を扱っているか確認しづらい」、調査Taskでは「遅延がどこで発生するか不明で、対策を選べない」と書きます。
- 良いユーザーに提供する体験: 「参加者が付箋を更新すると、合意した参加人数と待ち時間の範囲で他の参加者にも反映される。」人数と待ち時間が未定なら未確認と明記します。
- 良いTask: Howは「同じ操作・参加人数で送信から表示までを比較する」、作業完了条件は「測定条件・結果・制約・対策候補と推奨理由を記録し、次の対応を選べる」。
- 悪いPBI: 「計測ツールを導入する」。計測の実施と利用者の成果が混ざっています。
- 悪いTask: 「2時間調べる・問題を完全解決する」。調査時間だけでは成果を判断できず、解決まで必須にすると調査範囲を超えます。

### OPS: 障害から復旧する

- 良いPBIタイトル: 「運営者が更新の失敗から直前の利用可能な状態へ戻せる」
- 良いユーザーストーリー: 「運営者として、更新に失敗したら復旧したい。なぜなら、利用できない時間を短くしたいからだ。」
- 良いWhy: PBIでは「復旧方法が個人の記憶に依存し、担当者不在時に対応が止まる」、Taskでは「手順に復旧対象の選び方と結果確認がない」と書きます。
- 良いユーザーに提供する体験: 「権限を持つ運営者が手順に従うと、対象の版へ戻し、利用可能な状態か判断できる。」
- 良いTask: Howは「既存の復旧手段を使い、対象の選択・実行・確認を手順化する」、作業完了条件は「検証環境で手順を実行でき、成功・失敗の見分け方と戻せない範囲が文書にある」。
- 悪いPBI: 「手順書を書く」。文書を作る作業だけで運営者の成果がありません。
- 悪いTask: 「本番で一度戻せたら完了」。必要のない本番操作を要求し、再現可能な手順や制約が残りません。

## 検証結果はPRで扱う

Issueには期待する結果を残し、「テスト成功済み」「実機確認済み」で置き換えません。[PRテンプレート](../../.github/pull_request_template.md)と[write-pr](../../.agents/skills/write-pr/SKILL.md)に従い、主要な要件とリスクについて検証方法・実際の結果・未確認を短く示します。詳細なテストケースや全ログを本文へ転記しません。

## 作成・レビュー時の確認

- 既存要求と根拠を読み、Whyの事実・仮説・未確認を分ける。
- 問題と提供したい体験が短く伝わるかを見る。未定のHowを起票・着手の条件にしない。
- 設計とテストの粒度を判断し、詳細は担当者とAIに委ねる。人の補足を形式整備で消さない。

参考: [AIコーディングに関する登壇資料](https://www.docswell.com/s/PassionateHachi/KN73NR-2026-10-18-161120/1)の対象者・場面・困りごとの具体化、体験と実装手段の分離、完成判断と詳細検証の分離を採用しています。資料の項目全体を必須フォームへ移植するものではありません。
