# Issue記述ルール

読者: IdeaBoostのIssueを書く開発者とAIエージェント。説明なしで使ってよい語: Issue、PBI、Task、Bug、Spike、OPS、UI、PR、API、GitHub、テスト、デモ、実装、フォーカス、ショートカット。

この文書は、過去の会話や特定の開発プロセスを知らなくても、同じ責務と粒度でIssueを書くための正本です。Issue Type、採番、親子関係、状態、スプリントの扱いは[Issue運用](issues.md)に従います。例は架空の仕様です。対象のIssueにそのまま転記しません。

## PBIは価値、Taskはその実現に必要な作業を書く

| 観点               | PBI                                                    | Task                                                               |
| ------------------ | ------------------------------------------------------ | ------------------------------------------------------------------ |
| 主な問い           | 誰が何をできるようになるか                             | そのために何を変えるか                                             |
| ひとまとまりの基準 | 一つの目的と、利用者・運営者が観察できる成果           | 一つの作業方針で進め、完了を判断できる範囲                         |
| Why                | 現状の問題、利用者への影響、改善が必要になった背景     | この作業が必要な理由、成果を妨げる現状の障害                       |
| 条件               | 主要な操作と結果。体験を左右する失敗時の振る舞いも含む | 作業範囲の動作、重要な異常系・境界条件、調査なら判断に必要な成果物 |
| 実装手段           | 原則として固定しない                                   | Howに方針と守る制約を書く                                          |
| 完了判断           | 期待する振る舞いが実現したか                           | 作業完了条件を満たしたか                                           |

PBIはコード量や画面単位ではなく目的でまとめます。Taskの条件を単純に集約しません。「イベントを受け取る・作成処理を呼ぶ・フォーカスを移す」はTaskの範囲です。PBIでは「次の付箋を追加し、入力を中断せず案を書き続けられる」と書きます。

Taskは独立して作業と確認ができる範囲にします。無関係な変更を束ねず、関数ごとに機械的に分割もしません。複数Taskの完了やPRのマージだけでPBI全体の達成を判断しません。

## 書き残す型

タイトルはGitHubのタイトル欄に書き、本文へ重複させません。既存のPBI識別子と採番ルールは維持します。

PBIの本文:

```markdown
参加者として、入力を中断せず案を書き続けたい。なぜなら、思いついた内容を忘れる前に残したいからだ。

## Why

現状は付箋を追加するたびに入力先を探す必要があり、案を書く流れが止まる。

## 期待する振る舞い

- 参加者が個人作業画面で付箋を追加すると、そのまま本文を書き始められる。
- 次の付箋を追加して、続けて案を書ける。
```

Taskのタイトル例は「個人作業中にショートカットで付箋を追加する」。本文:

```markdown
## Why

付箋を続けて書く際、毎回追加ボタンへ移動する必要がある。入力の流れを保つため、キーボードから追加できるようにする。

## How

- 個人作業画面にショートカットを追加し、既存の付箋追加処理を利用する。
- 追加後は新しい付箋の本文へフォーカスを移す。
- キーの組み合わせは既存操作との競合を確認して決める。

## 作業完了条件

- 決定したショートカットを操作すると、付箋が1枚追加され、直ちに本文を入力できる。
- 日本語変換中は付箋を追加しない。
- キーを押し続けても付箋を二重作成しない。
```

PBI冒頭のユーザーストーリーは見出しを付けず、「○○として、○○したい。なぜなら、○○だからだ。」の形で書きます。理由はその人が求める価値です。Whyは現状の事実と影響を補い、同じ文を繰り返しません。

関連Issue、対象外、利用の流れ、画面イメージ、未確認事項は必要な場合だけ補足します。期待する振る舞いを読めばデモで確認する内容が分かるなら、別欄へ複製しません。

### フォームとAIから同じ型で作る

[フォーム](../../.github/ISSUE_TEMPLATE/01-pbi.yml)は入力欄名を本文の見出しとして挿入します。PBI作成後は冒頭の「ユーザーストーリー」見出しを削除し、段落から始めます。空欄から生成された不要な見出しも除きます。AIは最初から上記の本文を生成し、[PBI作成スクリプト](../../.agents/skills/pbi/references/creation-spec.md)または本文ファイルを使います。フォーム経由・AI経由とも、反映後に本文とIssue Typeを読み返します。

フォームの必須欄は起票時の最小限を維持します。未整理の段階では不足を未確認と明記して起票でき、作業開始までに必要な背景・方針・条件を補います。AIが空欄を埋めるために事実や合意を作ってはいけません。

## Howは必要な方針と制約に絞る

既存処理の再利用、対象画面、互換性、権限境界など、作業に必要な判断を書きます。根拠のある必須の手段は理由とともに指定できます。

- 良い例: 「既存の追加処理を再利用する。利用できるか確認し、合わなければ理由と変更範囲を示す。」
- 悪い例: 「未調査だが、新しいライブラリを導入し、関数名・引数・内部変数をこの通りにする。」
- 良い例: 「候補を同じ条件で比較し、採用案と制約を記録する。」
- 悪い例: 「調査する前に方式Aを採用すると決め、調査結果も方式Aの優位性に合わせる。」

調査で変更方針が変わったらWhy・How・作業完了条件の整合を直します。実装の詳細な手順や差分の説明はPRへ残します。

## 分野ごとの良い例・悪い例

以下は各欄の比較例です。実際の本文では上記の型にそろえます。不具合の報告はBug、不確実性を減らす調査はSpikeも使えます。Bug・SpikeをTaskへ一律に変更せず、報告や問いから具体的な作業を切り出した場合にTaskの型を使います。

### UI: 付箋を続けて書く

- 良いPBIタイトル: 「付箋を追加し、続けて案を書ける」
- 良いPBIのWhy: 「追加後の入力先が分かりにくく、操作を探す間に案を書く流れが止まる。」
- 良い期待する振る舞い: 「参加者が個人作業画面で付箋を追加すると、本文へ直ちに入力できる。」
- 良いTask: Whyは「新規付箋に入力先が移らない」、Howは「作成後に本文へフォーカスを移す」、作業完了条件は「追加直後の文字が新規付箋に入り、既存付箋を変更しない」。
- 悪いPBI: 「UI改善」。期待する振る舞いが「関数を追加する・イベントを登録する」では、利用者の成果が分かりません。
- 悪いTask: 「いい感じにする・見た目を確認したら完了」。対象と確認できる結果がありません。

### 機能追加: 結果を保存する

- 良いPBIタイトル: 「チームの検討結果を持ち帰って共有できる」
- 良いユーザーストーリー: 「参加者として、検討結果を保存したい。なぜなら、参加していない人にも結論を伝えたいからだ。」
- 良いWhy: PBIでは「参加していない人は検討に使った画面を閲覧できないため、参加者が結論を手作業で転記している」、Taskでは「保存に必要な結果の取得手段がない」と書き分けます。
- 良い期待する振る舞い: 「参加者が結果画面から保存した結果を渡すと、参加していない人も選んだ案と結論を確認できる。」
- 良いTask: Howは「既存の閲覧権限に従って保存用の結果を取得する」、作業完了条件は「閲覧権限のある利用者は対象結果を取得でき、権限のない利用者へ内容を返さない」。
- 悪いPBI: 「APIを作る」。手段だけで持ち帰れる価値が示されていません。
- 悪いTask: 「保存できること」だけでは、取得・画面・ファイル生成のどこを担当するか判断できません。

### 不具合: 再接続後も投票を保つ

- 良いPBIタイトル: 「接続が切れても投票をやり直さず参加を続けられる」
- 良いWhy: PBIでは「再接続後に投票が消えて見え、利用者が投票済みか判断できない」、修正Taskでは「再接続時に保存済みの投票を画面へ反映していない」と書きます。原因未確認なら後者を断定しません。
- 良い期待する振る舞い: 「投票後に接続が切れても、再接続すると自分の投票済み状態を確認できる。」
- 良いTask: Howは「Bugに記録した再現条件から、復元されない箇所を調べて修正する」、作業完了条件は「同じ条件で投票状態が復元され、重複投票が増えない」。
- 悪いPBI: 「Bugを3件閉じる」。件数では体験を判断できません。
- 悪いTask: 「原因は通信なので待ち時間を増やす」。根拠のない原因と手段を先に固定しています。

### 調査: 同時編集の遅延を調べる

- 良いPBIタイトル: 「複数人で編集しても変更を確認しながら議論できる」
- 良いWhy: PBIでは「他の参加者の変更が遅れて見え、同じ案を扱っているか確認しづらい」、調査Taskでは「遅延がどこで発生するか不明で、対策を選べない」と書きます。
- 良い期待する振る舞い: 「参加者が付箋を更新すると、合意した参加人数と待ち時間の範囲で他の参加者にも反映される。」人数と待ち時間が未定なら未確認と明記します。
- 良いTask: Howは「同じ操作・参加人数で送信から表示までを比較する」、作業完了条件は「測定条件・結果・制約・対策候補と推奨理由を記録し、次の対応を選べる」。
- 悪いPBI: 「計測ツールを導入する」。計測の実施と利用者の成果が混ざっています。
- 悪いTask: 「2時間調べる・問題を完全解決する」。調査時間だけでは成果を判断できず、解決まで必須にすると調査範囲を超えます。

### OPS: 障害から復旧する

- 良いPBIタイトル: 「運営者が更新の失敗から直前の利用可能な状態へ戻せる」
- 良いユーザーストーリー: 「運営者として、更新に失敗したら復旧したい。なぜなら、利用できない時間を短くしたいからだ。」
- 良いWhy: PBIでは「復旧方法が個人の記憶に依存し、担当者不在時に対応が止まる」、Taskでは「手順に復旧対象の選び方と結果確認がない」と書きます。
- 良い期待する振る舞い: 「権限を持つ運営者が手順に従うと、対象の版へ戻し、利用可能な状態か判断できる。」
- 良いTask: Howは「既存の復旧手段を使い、対象の選択・実行・確認を手順化する」、作業完了条件は「検証環境で手順を実行でき、成功・失敗の見分け方と戻せない範囲が文書にある」。
- 悪いPBI: 「手順書を書く」。文書を作る作業だけで運営者の成果がありません。
- 悪いTask: 「本番で一度戻せたら完了」。必要のない本番操作を要求し、再現可能な手順や制約が残りません。

## 検証結果はPRで扱う

Issueの条件は期待する結果です。「テスト成功済み」「実機確認済み」のような実績へ置き換えません。[PRテンプレート](../../.github/pull_request_template.md)と[write-pr](../../.agents/skills/write-pr/SKILL.md)に従い、要件ごとに確認条件・手順・期待結果・実際の結果を記載します。未実施や失敗は理由も残します。

例: Taskには「日本語変換中は追加しない」と書き、PRには「変換中の操作で追加されないことをテストで確認。実機での確認は未実施」と書きます。テスト成功が保証する範囲と、未確認の利用体験を分けます。画面や操作の変更はPRからGitHub上の画面資料へ案内します。

## AIが出力前に確認すること

- Issue Typeと目的を確認し、既存の要求・本文・コメントを読む。学校や組織固有の事情、過去の会話、未定義の工程番号を前提にしない。
- 事実・仮案・未確認を分ける。ユーザーストーリーとWhy、PBIの成果とTaskの作業を区別する。
- 主要な操作と結果が具体的か確認する。操作のない調査・運用作業に架空の画面操作を追加しない。
- Howで根拠のない手段を固定せず、条件は第三者が確認できる表現にする。
- タイトル・冒頭段落・見出しをそろえる。既存の補足や人の追記を消さず、採番・Type・親子関係・自動化はIssue運用に従う。
