# AIが作る記録Issueの例

読者: Idea Boost の記録運用をレビューするチーム。Issue、Type、Project、本文、コメント、フィードバック、成果データを使う人向けの例です。

以下の3件は構成を確認するための架空データです。実際の利用結果・調査結果ではなく、この例をGitHubへ起票しません。フィードバックは1日分を1 Issueにまとめ、追加取得も同じIssueのコメントへ追記します。

## 例1: その日のフィードバックをまとめる

Type: フィードバック\
タイトル: `2026-10-20のフィードバック`

### 本文

```markdown
## 対象日・収集範囲

- 対象日: 2026-10-20（日本時間）
- 出典: アプリ内フィードバック2件、同日実施のフォーム回答1件
- 取得日時: 2026-10-20 18:00（日本時間）
- 18:00以降の追加分は未取得。3件は投稿・回答の数で、人数ではない。

## 要約

付箋をまとめて動かしたいという要望と、次に何をするか迷ったという報告があった。他の人の票が見えない点には好意的な声があった。採否・再現確認は未判断。

## 原文・コメントの索引

- コメント1: 原文3件。媒体と元の受付ID・回答位置を併記。
- 追加取得分・分析・対応方針: まだなし。得られた時点で別コメントに記録し、この索引を更新する。

## 確認事項・未確認

報告された内容の再現確認はしていない。好評だった理由を原文以上に補完しない。

## 関連Issue・現在の判断

既存の改善Issueとの対応は未整理。原文1件ごとに作業Issueを作らない。
```

### コメント1: 原文をまとめて残す

```markdown
## 2026-10-20の原文（初回取得3件）

### F01｜アプリ｜ほしい｜1-3 グループ化
- 元の受付ID: sample-feedback-01
> グループ化した付箋をまとめて動かしたいです。

### F02｜アプリ｜よかった｜1-4 投票
- 元の受付ID: sample-feedback-02
> 他の人の投票が見えないので、自分の考えで選べました。

### F03｜フォーム｜使い方について
- 元の回答位置: サンプル回答シート・タブ1・行5・問7（M5）
- 元セルのURL: https://example.com/sample-sheet?tab=1&cell=M5 （架空URL）
> 問いを考える場面で、何を書けばよいか迷いました。
```

同じ日に2件追加で取得した場合は、同じIssueへ「追加取得2件」のコメントを残します。既存の受付ID・回答位置と照合し、本文を計5件へ更新します。同じ日の別Issueを作りません。

## 例2: 競合の1テーマを調べる

Type: 競合調査\
タイトル: `競合Aのアイデア入力中に出るヒントを調べる（2026-10-20）`

### 本文

```markdown
## 要約

競合Aのアイデア入力中に出るヒントを調べ、案内の文言と表示場面を記録する。

## 出典・識別情報

- 対象: 競合Aのアイデア入力画面
- 製品URL: https://example.com/competitor-a （架空URL）
- 調査テーマ: ヒントの文言と表示場面
- 観察日時: 2026-10-20 10:00（日本時間）
- 調査環境: 検証用アカウントとダミーのルーム

## 観察記録

コメントに文言・操作・画像を追記する。本文には確認できた種類と未確認の範囲を要約する。

## 確認事項・未確認

直前の操作と表示原因は分けて記録する。すべての文言を収集できたとは扱わない。

## 関連Issue・現在の判断

自分たちの製品へ採用するかは未判断。
```

### コメント1: 1回の観察を残す

```markdown
## 観察1: 入力欄を開いた場面のヒント

- 操作: 新しい入力欄を開き、文字を入力せず画面を確認した。
- 表示文言: 「まずは思いついたことを1つ書いてみましょう」
- 証拠: この場面の画像を添付する。
- 未確認: 入力欄を開いたことが表示原因なのか、一定時間で出るのかは未確認。
```

文言を1つ見つけるたびに新しいIssueを作らず、この調査のコメントへ追加します。作業中の既存Issueがある場合は、それを維持します。

## 例3: 1ルームの活動で得た成果を残す

Type: 成果データ\
タイトル: `2026-10-20の成果データ：サンプルルームA`

### 本文

```markdown
## 要約

サンプルルームAで、授業中の質問のしづらさを課題にし、質問を匿名で集める案を決定した。

## 出典・識別情報

- 対象: サンプルルームAの1回の活動
- ルームID: sample-room-a
- 活動ID: sample-session-2026-10-20-a
- 活動日: 2026-10-20
- 保存日時: 2026-10-20 15:00（日本時間）
- 取得日時: 2026-10-20 18:00（日本時間）
- 元データ: https://example.com/outcomes/sample-session-2026-10-20-a （架空URL。この活動の成果詳細と進行記録）

## 成果・進行の記録

- 参加人数: 4人（保存された人数）
- 到達工程: アイデア決定
- 記録: 確定
- 保存状態: 保存済み
- 課題: 授業中に質問しづらい
- 問い: どうすれば、ためらわず質問できるだろう？
- 決定したアイデア: 匿名で質問を送り、共通する質問をまとめて取り上げる

## 確認事項・未確認

この案を実行した結果や効果は未確認。

## 関連Issue・現在の判断

同じ活動のフィードバックがあれば日別まとめへ関連付ける。成果を保存しただけで改善作業のPBIを作らない。
```

### コメント1: 進行の記録を補足する

```markdown
## この活動の進行記録

課題・問い・アイデアの各工程で保存された記録をまとめる。記録がない工程は未記録とし、経過時間が長いという理由だけで「迷った」と判断しない。
```

この例は現在の成果データの単位である「1ルームの1回の活動」を示します。付箋ごと・工程ごとにIssueは分けません。

## フォームとAI向けルールの役割

フォームは人がGitHub画面から起票するときの入力支援です。AIがCLI・APIを使う場合にフォームが自動適用されるわけではありません。そのため、[AGENTS.md](../../AGENTS.md)から[記録の運用](evidence-issues.md)へ案内し、AIにも先に日付・既存Issue・粒度を確認させます。Projectの自動化はTypeに基づく振り分けを担当し、原文の分割や新規Issueの大量作成は行いません。
