1データの流れ — 経路は2本ある

この実装のいちばん大事な設計判断です。ドラッグ中の座標はDBを通さず Realtime broadcast だけで流し、指を離した確定値だけをDBに書きます。 高頻度の書き込みでDBとRealtimeのレート制限を圧迫しないためです。

経路① ドラッグ中（一時データ）

約80msごと・DBには何も書かない

ブラウザA 付箋をドラッグ。note-card.tsx がポインタ操作を拾い、room-board.tsx の handleNoteDragMove へ
▼
スロットル throttle.ts の createThrottled が送信を約80ms間隔に間引く（間隔は board-constants.ts）
▼
Realtime channel.send で note-drag イベントをプライベートチャンネル room:<ルームID> へ。メンバー以外は realtime.messages のRLSで送受信できない（migration）
▼
ブラウザB room-board.tsx が受信し、notes-reducer.ts の applyNoteEvent（DRAG）で画面の付箋が動く

経路② 確定操作（正データ）

ドロップ・作成・編集・削除 → DBが真実

ブラウザA 指を離す（または追加・編集・削除）→ Server Action を呼ぶ（例: updateNotePosition）
▼
サーバー actions.ts が zod で入力だけ検証。「やっていいか」の判断はしない（DBに任せる）
▼
Postgres notes を更新。RLSと列限定GRANT（content, x, y のみ更新可）が権限を強制。他人の付箋の窃取はここで 42501 拒否（migration）
▼
トリガー notes_broadcast_changes トリガーが変更を同じチャンネルへ INSERT/UPDATE/DELETE イベントとして配信（migration）
▼
両ブラウザ applyNoteEvent で反映。自分がドラッグ中の付箋は巻き戻らないようローカル座標を優先（notes-reducer.ts）

2ファイル別の役割 — 4つの層

25ファイルは4層に分かれます。層ごとに「なぜ分けたか」があり、 それぞれテスト方法が違います（DB=pgTAP、ロジック=Vitest、表示=Storybook）。

データベース層 — 認可の本体

なぜ: 「誰が見られる・書けるか」を全部DB側で強制する。アプリのコードにバグがあっても突破できない。

supabase/migrations/20260703131517_realtime_note_sync.sql rooms / room_members / notes の3テーブル、RLSポリシー、create_room・join_room RPC、broadcast トリガー、Realtime のチャンネル認可、UPDATE の列限定GRANT。全部この1本
supabase/tests/realtime_note_sync_test.sql pgTAP 28件。「他人の付箋の author_id を書き換えて削除権限を迂回する」等の実攻撃SQLが失敗することの固定化を含む

サーバー境界 — 入口の検証だけ

なぜ: 検証（形式が正しいか）はここ、認可（やっていいか）はDB。同じチェックを2箇所に書かない。

app/rooms/actions.ts Server Actions 6本: createRoom / joinRoom（RPC呼び出し）と付箋のCRUD 4本（zod検証のみ）。RLSで0行更新になったら「権限がありません」を返す

クライアント配線 — Supabase依存をここに閉じ込める

なぜ: Realtime購読やServer Action呼び出しという「テストしにくい部分」を2ファイルに隔離し、残りを純粋に保つ。

app/rooms/[id]/page.tsx Server Component。初期表示の rooms / notes を取得。非メンバーはRLSで0件になり404へ
app/rooms/[id]/room-board.tsx このPoCの心臓部。setAuth() → プライベートチャンネル購読、4イベント（INSERT / UPDATE / DELETE / note-drag）のハンドリング、ドラッグのスロットル送信、Server Actions呼び出し

純粋ロジック — Vitestの主戦場

なぜ: 状態とロジックの分離。ブラウザもSupabaseも無しで、同期の核心ロジックを高速にテストできる。

app/rooms/notes-reducer.ts 受信イベントを付箋配列に適用する純粋関数。「自分がドラッグ中の付箋はエコーで巻き戻さない」ルールもここ
app/rooms/throttle.ts 汎用スロットル。動き始めは即送信＋止まった位置も必ず送る（leading + trailing）
app/rooms/invite-code.ts 招待コード（英数字6桁）の正規化と検証
app/rooms/board-constants.ts ボードサイズと80msスロットル間隔の定数

表示コンポーネント — Storybookで見る側

なぜ: propsを受けて描くだけにして、Supabase無しでStorybook・テストを回せるようにする。

app/rooms/[id]/board-view.tsx ボードの見た目。招待コード表示・付箋追加ボタン・付箋の配置
app/rooms/[id]/note-card.tsx 付箋1枚。ドラッグ操作・本文編集・削除ボタンをコールバックで親に伝える
app/page.tsx トップページに「ルームを作成」「招待コードで参加」フォームを追加（既存ファイルへの変更はこれだけ）
*.spec / *.stories / *.fixture 各コンポーネントに併設。テストデータはfixtureに分離（ハードコード禁止の規約どおり）
