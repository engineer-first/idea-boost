§概要

ハッカソン・ビジコン初期の「何を作ればいいか分からない」を支援するフレームワーク型ブレストアプリ。 技術的な核は「ルームの中身の真実は誰が持つか」という設計判断で、その答えが Durable Object（RoomDO）である。

D1 はユーザーと招待コードのディレクトリ（検索台帳）に徹し、ルームに入ってからの状態 （メンバー・付箋）は 1 ルーム = 1 Durable Object インスタンスだけが権威として保持する。 これにより同時編集やフェーズ遷移のレースは単一スレッド直列化によって構造的に起きない。

§アーキテクチャ

本番は 2 つの Cloudflare Worker で構成される。idea-flow-app が配信を、 idea-flow-api がデータへの唯一の入口を担う。箱の入れ子は「誰が何を内包し、唯一の到達経路になっているか」を表す。

§境界と責務

認可チェックの分散を防ぐため、各層が「やってよいこと」と「やらないこと」を固定する。

層責務守ること
UI（app/） 画面表示・フォーム操作 D1 / RoomDO に直接到達しない。データは必ず api-worker 経由
Server Actions UI 近傍に置けるサーバー処理の起点 毎回 getCurrentUser() で認可を検証（Proxy には頼らない）
api-worker D1・RoomDO への唯一の入口 全エンドポイントでセッション検証、入力は zod で検証
RoomDO ルーム内の真実（members / notes）を保持 配信は visibility.ts の visibleTo() を必ず経由
contracts/ 境界を流れる型とバリデーションの単一の真実 実装より先にここを変更する

§リアルタイム設計

RoomDO への HTTP/WebSocket 経路と、contracts/room-protocol.ts が定めるメッセージ形。

メソッドパス用途
POST/api/auth/syncログイン確定時のユーザー upsert（署名済みログイン主張で認証）
POST/api/roomsルーム作成
POST/api/rooms/join招待コードでルーム参加
GET/api/rooms/:idルーム情報取得
GET/api/rooms/:id/wsWebSocket アップグレード（RoomDO へ接続）
  • authorId を書き換えるメッセージは存在しない
    なぜ: サーバーが接続時ヘッダー（検証済みユーザーID）から authorId を決める。Supabase 時代に列レベル GRANT で塞いでいた権限昇格を、プロトコルの形で構造的に塞ぐ。フィールドごと無くせば、チェック漏れという実装ミスの余地自体が消える。
  • roomId はそもそもプロトコルに現れない
    なぜ: 1 RoomDO = 1 ルームなので、接続先（どの DO に繋いでいるか）自体が roomId を意味する。メッセージ内の値を信頼する必要がそもそも無い。
  • note:drag は永続化されない一時データ
    なぜ: ドラッグ中の逐次送信を毎回ストレージに書くと無駄が大きい。確定（永続化）は note:move（ドロップ時）だけが行う。

§デプロイ構成

2 つの wrangler 設定が別々の Worker としてデプロイされ、サービスバインディングで結合される。 図・秘密一覧・デプロイ順の詳細は デプロイ構成図を参照。

idea-flow-appidea-flow-api
設定ファイルwrangler.jsoncworkers/wrangler.jsonc
エントリworkers/app-worker.tsworkers/api-worker.ts
役割Next.js（OpenNext）配信 + 静的アセット + /api/* 転送D1 + Durable Object（RoomDO）への唯一の入口
バインディングASSETS, API_WORKERDB (D1), ROOM_DO (DO)
ビルドnpm run build:cf（opennextjs-cloudflare）ビルド不要（TS のまま wrangler が bundle）
デプロイnpm run deploy:appnpm run deploy:api
  1. wrangler d1 create idea-flow-lobby で D1 を作成し、workers/wrangler.jsonc の database_id を置き換える
  2. wrangler d1 migrations apply DB --remote --config workers/wrangler.jsonc
  3. 両 Worker に同一の SESSION_SECRET（app 側は root の wrangler、api 側は --config workers/wrangler.jsonc）
  4. npm run deploy:api → NEXT_PUBLIC_SITE_URL=… npm run deploy:app（順は api → app）
SESSION_SECRET は vars に置かない。 vars は secret put で上書きしない限り平文が本番に残るため。 ローカルは workers/.dev.vars（gitignore 済み）、テストは miniflare bindings、本番は wrangler secret put の3経路で注入を分けている。

§CI/CD

PR 検証と本番デプロイ、ドキュメント公開は別ワークフロー。

ワークフロートリガー内容
ci.yml pull_request lint / test（unit + workers）/ build:cf / smoke。デプロイはしない
deploy.yml push to release 品質ゲート → D1 remote migrate → deploy:api → deploy:app → health チェック
deploy-pages.yml develop への push（docs/site/** 変更時） ドキュメントサイト（静的 HTML）を GitHub Pages に公開。アプリ本体とは無関係
