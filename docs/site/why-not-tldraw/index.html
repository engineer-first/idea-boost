設計判断の記録 — PR #76

付箋ボードを tldraw ではなく自前実装にした理由

一言でいえば、付箋を「絵」ではなく「データベースの行」として扱いたかったから。ホワイトボード SDK を捨てて Pointer Events 約 40 行のボードを選んだ判断の、経緯と理由を記録する。

  • 2026-07-04
  • branch: poc-realtime-note-sync
  • 関連: docs/tech-stack-research.md
  • 関連: docs/tldraw-supabase-poc.md

要は

  1. 可視性制御がこのアプリの核だから。「個人ワーク中は自分の付箋だけ」「ステルス投票は自分の票だけ」を DevTools でも破れない形で守るには、付箋が Postgres の行で、RLS が行単位に効く必要がある。tldraw のドキュメントモデルとは噛み合わない。
  2. 必要な操作は 4 つだけ（付箋の作成・編集・ドラッグ・投票ドット）だから。無限キャンバスも自由描画も要らず、フル描画 SDK は PRD の「あえて自由度を絞る」という思想に反するノイズになる。
  3. tldraw の同期の公式ルートは Cloudflare 前提だから。まともに採用すると、検証済みの Supabase Auth・RLS・pgTAP というテスト資産ごと作り直しになる。DIY 同期の限界は先行 PoC で実証済み。
まず前提のただし書き

「dnd-kit を使った自前実装」と紹介されることがあるが、実装は dnd-kit も使っていない。package.json に @dnd-kit/* は存在しない。

技術調査（docs/tech-stack-research.md §6）の時点では「React + dnd-kit（または Pointer Events）」と両案併記だったが、実装で選ばれたのは素の Pointer Events だった。理由は後述。

経緯 — 3 つのステップ

  1. STEP 1 — tldraw × Supabase 同期 PoC（feature/22_update） tldraw の store 差分を Supabase Realtime Broadcast に流す DIY 同期を検証

    配線自体は成立した。ただし初期スナップショットなし・永続化なし・競合解決なし・認可なしという構成で、これらを埋めるコストは tldraw sync 公式（Cloudflare 前提）を採用するのと大差ない、という知見が残った。

  2. STEP 2 — 技術スタック調査（2026-07-03） 「Supabase 継続 + ボードは tldraw を使わず構造化ボードとして自作」を結論として明文化

    Cloudflare 移行案（Durable Objects）と比較した上で、付箋・投票を Postgres の行として持ち、RLS で可視性を強制する構成 A を推奨。ボード UI は「React + dnd-kit（または Pointer Events）+ CSS transform の固定サイズ 2D ボード」とした。

  3. STEP 3 — 縦切り PoC（PR #76、2026-07-04） 自前ボードを実装し、tldraw の UX の良い部分だけを移植

    認証・RLS・Realtime を実配線して「2 ブラウザで付箋ドラッグが滑らかに同期するか」を検証。ドラッグは Pointer Events、同期は約 80ms スロットルの Broadcast + DB トリガー配信で成立した。

理由 1 — 付箋は「絵」ではなく「行」である必要があった

このアプリの核となる要件は、リアルタイム同期そのものではなく可視性制御にある。個人ワーク中は自分の付箋しか見えず、ステルス投票中は自分の票しか見えず、開票で一斉に公開される。しかもこれは「クライアントで出し分ければよい」ものではない。DevTools を開いた参加者に他人の票が見えてはならないので、サーバー側で強制しなければならない。

tldraw — ドキュメントモデル

shape:note-a1shape:note-b2shape:arrow-c3shape:draw-d4camerapage:1

クライアントの store が全レコードを保持し、同期はドキュメントぐるみ。「この付箋だけ見せない」はアプリコードのフィルタの責任になり、漏れ = 即事故。

自前ボード — 行モデル

RLS ✓ notes: 自分の行 (x, y, content)
RLS ✓ notes: 公開済みの行
RLS ✗ notes: 他人の private 行

付箋 1 枚 = notes テーブルの 1 行。RLS が行単位で SELECT/UPDATE を強制し、pgTAP で回帰テストできる。

Postgres の行にしておくと、宣言的な守りが可能になる。実際に PR #76 では、notes の UPDATE を 列限定 GRANT（content, x, y のみ）にすることで「付箋は動かせるが author_id や room_id の書き換えによる窃取は DB が拒否する」を権限レベルで実現し、否定系を含む pgTAP 28 件でテストしている。tldraw のドキュメントモデルの上でこれをやろうとすると、同期レイヤーとは別に行相当の概念を自分で発明して二重管理することになる。

理由 2 — 必要な操作は 4 つだけ。フル SDK はノイズ

tldraw は「無限キャンバスの描画アプリを作る」問題を解く SDK であり、その問題設定に対しては素晴らしい道具だ。しかしこのプロダクトの PRD はあえて自由度を絞ることを思想として掲げている。参加者を迷わせないために、できることを絞った構造化ボードであることに価値がある。

tldraw が解いている問題

  • 無限キャンバスとズーム・パン
  • 自由描画・図形・矢印・回転
  • 汎用シェイプシステムと undo/redo
  • 描画アプリとしての拡張性

MVP に必要な操作

  • 付箋の作成
  • 付箋の編集
  • 付箋のドラッグ
  • 投票ドット

解いていない問題のためにフル SDK を背負うと、依存の重さだけでなく「ユーザーができてしまうこと」も一緒に付いてくる。使わない自由度は、このプロダクトでは機能ではなくノイズになる。

そして必要な 4 操作のうちドラッグは、固定サイズボード上の絶対座標配置なら pointerdown / pointermove / pointerup の 3 ハンドラと setPointerCapture、座標の clamp だけで書ける（note-card.tsx で約 40 行）。dnd-kit すら使わなかったのはこのためだ。dnd-kit の主戦場はリストの並べ替えやドロップゾーンといった「要素の受け渡し」の抽象化であり、今回の「自由座標へのドラッグ + 4px 閾値でクリックと区別 + ドラッグ中 80ms スロットルで座標を broadcast」という制御は、抽象を挟まずポインターイベントの生の流れの中に書いた方が素直で短い。ライブラリを挟んでいたら、そのイベントモデルに合わせるためのアダプタコードの方が本体より厚くなっていた。

理由 3 — tldraw の同期の公式ルートは、スタックごと引っ越しを要求する

「tldraw を使いつつ同期を自前で」は STEP 1 の PoC で実際に試している。store.listen() の差分を Supabase Realtime Broadcast に流す DIY 同期で、配線は動いた。しかし本番に必要な残りが全部欠けていた:

  • 初期スナップショットなし — 後から入室した人に既存の付箋が見えない
  • 永続化なし — 全員がタブを閉じたらボードが消える
  • 競合解決なし — 同時編集は「最後に届いた Broadcast 勝ち」の偶然任せ
  • 認可なし — 誰でもチャンネルに参加・送信できる

これらを DIY で埋めるコストは、tldraw sync 公式プロトコルを採用するのと大差ない — というのが PoC の結論だった。では公式を採用すればよいかというと、tldraw sync の公式テンプレートは Cloudflare Workers + Durable Objects 前提で、乗るならホスティングごと引っ越しになる。動作確認済みの Supabase Auth（Google ログイン）を捨てて認証を自作し、pgTAP / supabase test db のテスト戦略も作り直すことになる。MVP の同期要件は「行単位の付箋 + 最後勝ち」で、Supabase Realtime の守備範囲に収まっているのに、だ。

自前ボードにすれば、同期は「正データは DB トリガー（broadcast_changes）で配信、ドラッグ中の座標だけ約 80ms スロットルの Broadcast」という 2 経路で済む。付箋が行だから、この構成が素直に書ける。

捨てたのはライブラリで、UX は捨てていない

tldraw を依存から外す判断と同時に、tldraw の付箋 UX の良い部分は仕様として移植した。感触を決めていたのはライブラリ本体ではなく、この 3 つの設計だった:

  • 1 クリックに 3 つの意味 — 1 回目のクリック = 選択（青枠）、選択済みへのもう 1 回 = 編集開始、4px を超えて動かしたら = ドラッグ。tldraw の SelectTool/PointingShape の方式（DRAG_THRESHOLD_PX = 4 も tldraw の判定距離に合わせた値）
  • 下方向にしか落ちない影 — box-shadow の spread に blur 以上の負値 + 正の Y オフセットで「机に貼られた紙」の見た目を作る。浮き量は付箋 id から決定的に導出して 1 枚ごとに揺らす（NoteShapeUtil.getNoteShadow の移植、note-shadow.ts）
  • モードで意味が変わるキーボード操作 — 選択中（青枠）の Backspace は削除、編集中（カーソル）の Backspace は文字消し。Enter で編集開始、Esc で編集終了

下のボードは、この解説ページ自身に埋め込んだ実物のデモ。動かしているのは note-card.tsx と同じ構造の Pointer Events 3 ハンドラ + note-shadow.ts と同じ式で、ライブラリは 1 つも使っていない。

このデモの全実装が pointerdown / pointermove / pointerup の 3 ハンドラ。これが「dnd-kit すら要らない」の意味。

将来この判断を見直すトリガー

この判断は「tldraw が悪い」ではなく「今の要件に対して過剰」という判断なので、要件が変われば戻ってくる。技術調査に再評価トリガーとして明文化されているのは:

  • カーソル共有・自由描画など、サーバー権威の高頻度同期（実質的な Miro 化）が要件になったとき
  • tldraw sync の公式採用を決めたとき（Cloudflare Workers + Durable Objects テンプレートが公式ルート）
  • Supabase Realtime のレート制限・同時接続数が実利用で頭打ちになったとき

なお、旧 PoC の名残（package.json の tldraw 依存と /whiteboard ルート）は、技術調査の「MVP ではノイズになるため削除を推奨」に従い、Cloudflare 移行の PR で削除済み。
