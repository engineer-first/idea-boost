1 — What is VRT

VRT とは：「前回の見た目」を正解にするテスト

ロジックのテストは「入力 X なら出力 Y」と正解を assert で書きます。しかし UI の見た目（角丸・余白・色・折返し）を assert で書き尽くすことはできません。VRT は発想を変えて、前回のスクリーンショットそのものを正解とし、ピクセル単位の比較で「意図しない見た目の変化」を検出します。

2 — How Chromatic behaves here

Chromatic はこのリポジトリでこう動く

push のたびに、変更内容に関係なく全 story を撮影します。撮影は Chromatic のクラウド（常に同一の Linux + Chrome 環境）で行われるため、「ローカル macOS と CI で画像が一致しない」という VRT 最大の落とし穴を構造的に回避しています。story は .storybook/main.ts の glob（app/** と components/** の *.stories.tsx）が対象です。

スクリーンショットはどこに保存されるか

すべて Chromatic のクラウド上です。リポジトリには画像が 1 枚も入らず、git は軽いままです（ベースライン画像をリポジトリにコミットする Lost Pixel 方式との大きな違い）。保存されるのは 2 種類：

  • スナップショット — story ごとの撮影画像と履歴。ダッシュボードのビルド一覧から過去分も遡れる
  • ビルドされた Storybook 一式 — 「Storybook Publish」リンクの先（*.chromatic.com）で、その PR 時点の Storybook をブラウザでそのまま操作できる。レビュアーがローカルで動かさずに UI を確認する手段としても使える

なにが比較されるか：単位は story、比較先は git 履歴から決まる

比較の単位は story 1 つです。push すると全 story がクラウドで撮影され、各 story のスナップショットが「その story のベースライン」と 1 対 1 でピクセル比較されます（アンチエイリアス等の微差は許容する閾値つき）。ベースラインはブランチごとに独立していて、ブランチを切った時点のコミットのビルドから継承されます。fetch-depth: 0 が必要なのは、この git 履歴の追跡のためです。

develop     A───B─────────────────M   M（マージ）で autoAcceptChanges が働き、
                 \                     ベースラインは常に最新に保たれる
feature/89        C───D               C・D は「B 時点のベースライン」と比較される

撮影のタイミングにも作り込みがあります。ネットワークが静かになるまで待つ（network quiescence）、CSS アニメーション・動画・GIF は自動で一時停止、フォントの読み込みを待つ——「フレーキーさとの戦い」の大部分はツール側に内蔵されています。

なぜ実際の画面ではなく Storybook を撮るのか

一言でいうと決定性（毎回同じ画像になること）のためです。VRT は「前回と違う = 異常」という仕組みなので、コードを変えていないのに画像が変わる要素はすべてノイズになります。

  • 実画面は非決定的 — DB のデータ・ログイン状態・現在時刻に依存し、同じコードでも毎回違う画像になって偽差分だらけになる。story は固定の props / fixture で描画するので毎回同一
  • 状態を網羅できる — 実画面で loading や error を狙って再現するのは大変。story なら列挙でき、「loading / empty / success / error の story を作る」ルールがそのまま VRT の状態網羅になる
  • 原因の特定が速い — 差分が「どのコンポーネントのどの状態か」に story 名で直結する。ページ全体の diff だと切り分けが別途必要
  • インフラ不要 — 静的ビルドを上げるだけ。CI に DB・サーバー・シードデータを用意しなくてよい

実画面の VRT が必要になったら、Chromatic には Playwright / Cypress 統合もあります。決済や招待のような重要フローだけ E2E スクリーンショットを足す、という将来の拡張は可能です。

workflow の設定と、その理由

設定何のためか（そうしないとどうなるか）
on: push pull_request イベントでは GitHub が一時的なマージコミットを作り、比較先のベースラインがずれることがある。push なら実ブランチのコミットがそのまま比較される（公式推奨）。
fetch-depth: 0 Chromatic は git 履歴を辿って「分岐元のビルド」をベースラインに選ぶ。shallow clone だと履歴が辿れず、正しい比較ができない。
exitZeroOnChanges: true 差分の合否は Chromatic 側のステータスチェックで管理する。これがないと差分検出だけで workflow が赤になり、「承認待ち」と「壊れている」の区別がつかない。
autoAcceptChanges: develop develop へのマージ後は差分を自動承認して新ベースライン化する。これがないと PR で承認済みの変更が develop 上で再び「未承認」となり、以降の PR が古いベースラインと比較される。

コスト削減オプション（TurboSnap・skip・exitOnceUploaded など）は .github/workflows/chromatic.yml に無効状態のコメントとして記録済み。月間スナップショットが無料枠の半分（約 2,500）を超えたら有効化を検討する。

PR のチェック欄に出る 2 つのステータス

Storybook Publish

ビルドした Storybook が Chromatic 上に公開されたことを示す。リンクを開くとこの PR 時点の Storybook をブラウザでそのまま操作できる。レビュアーがローカルで動かさずに UI を確認する手段としても使える。

UI Tests — unchanged

全 story がベースラインとピクセル一致。→ 作業なし。自動で green になる。見た目を触らない PR は常にこれ。

UI Tests — N changes must be accepted

N 個の story で差分が検出され、人間の判断待ち。→ Details から差分を確認し、意図どおりなら Accept、意図しない壊れなら Deny して修正 push。

課金の仕組み（story の書き方に効く）

課金単位はスナップショットで、スナップショット数 = story 数 × viewport 数 × ブラウザ数。story 1 つにつき毎 push 1 枚撮影される。だから Button の story は variant × size を個別 story（50 枚超/push）にせず、全組み合わせを 1 枚のグリッドに敷き詰めて 1 スナップショットにしている。グリッド内のどのセルが 1px 変わっても画像全体の差分として検出されるので、検出力は落ちない。viewport やブラウザを追加すると乗算で増えるため、増やす前に月間消費を再試算すること。

現在の対象は 5 ファイル・16 story（= 16 枚/push）。Cloudflare 移行時のリファクタリングで login-card・note-card・board-view などの story が増えた。story が増えたときにコストと開発体験をどう両立するかは、次のセクションの「story の増やし方」を参照。

3 — Daily operations

これからの運用：変わるのは「Accept 1 クリック」だけ

日常の開発フローはほぼ変わりません。唯一増えるのは、見た目を変えた PR でマージ前に差分を Accept する操作です。

いつも通りPR を作って push する
→
自動Chromatic が全 story を撮影・比較
差分なしUI Tests が自動で green。何もしなくてよい。
差分あり（意図した変更）Details から差分画像を確認して Accept → green になり、新ベースラインに。
差分あり（意図しない壊れ）Deny してコードを修正、再 push。VRT がマージ前にデグレを止めた成功例。

誰が Accept するか：推奨は「PR 作者が Accept し、レビュアーは承認済みの差分画像を見て確認する」。意図した変更かどうかを一番知っているのは作者だからです。どちらの運用でも構いませんが、決めておかないと pending のまま放置されて形骸化します。

Accept しないとどうなるか（マージとの関係）

Accept はマージの前提条件ではありません（UI Tests は required check ではない）。マージ待ちがスタックすることも、誰かの未承認があなたの PR を妨げることもありません。正確な挙動は次の 4 つです。

マージ可否

UI Tests が pending のままでもマージはできる。承認待ちがマージを機械的にブロックすることはない。

持ち越し

同一ブランチでは、未 Accept の差分は次の push でも「未承認」として出続ける。比較先が「最後に承認されたベースライン」のままだから。 作業が増えるわけではなく同じレビューが 1 件残り続けるだけ。Accept を 1 回押せば全部消える。

独立性

ベースラインはブランチごとに独立。あなたが Accept しなくても、他のブランチは自分の分岐点から比較されるため影響ゼロ。「誰かが前のを承認しないと新鮮な VRT にならない」状況は構造的に起きない。

落とし穴

未レビューのままマージすると、autoAcceptChanges: develop が壊れた見た目も「正解」として自動承認してしまう。以降の PR はその壊れた状態と比較されるので、デグレ検出器として無力化する。 だから「マージ前に差分を見て Accept」は仕組みではなく規律として守る。徹底したくなったら required check 化で仕組みにできる。

知っておくと良い挙動

撮影範囲

現在撮っているのは light テーマ × 1 viewport × Chrome のみ。addon-themes で切り替える dark テーマは撮影されていない。 Chromatic の modes 機能で dark も撮れるが消費が 2 倍になる。dark 対応を本格化するタイミングで判断する。

偽差分

develop で承認された変更は他ブランチへ自動反映されない。長生きしているブランチで身に覚えのない差分が出たら、ベースラインが古いサイン。 develop を merge（または rebase）してから差分を見直す。

誤 Accept

間違って Accept しても、直近のビルドならダッシュボード上で取り消せる。ビルド自体の削除はできない。 古い承認まで遡って戻したい場合は、git で該当変更を revert するのが確実。

MSW 依存

Storybook の MSW 起動は NEXT_PUBLIC_USE_MSW=true のときだけ有効（.storybook/preview.tsx）。現在の story はすべて props 注入なので無関係だが、api-worker への fetch に依存する story を作る場合、Chromatic のビルドにこの環境変数を渡さないとクラウド撮影時だけ error 状態で撮られる。 そうなる前に、そもそも fetch を story に持ち込まず fixture を props で渡せないかを先に検討する（通信状態を props に落とすパターンと同方向）。

story の増やし方：開発用 story は自由に、VRT 観測点は絞る

課金対象は story の数なので、状態ごとに個別 story を増やすほど消費が線形に増えます。かといって story を減らすと、component-driven 開発・状態網羅・公開 Storybook でのレビューという開発体験が犠牲になる。そこでこのリポジトリでは「開発用 story」と「VRT の観測点」を分離する方針を取ります。

  • 個別 story はこれまで通り自由に書く — loading / empty / success / error の網羅（CLAUDE.md 規約）、Storybook 上での隔離開発、レビュアーが操作できる公開 Storybook。開発体験の核なので削らない
  • 表示コンポーネントは「カタログ story」1 枚で撮る — 全状態をグリッドに敷き詰めた story（Button の AllVariants が実例）だけを撮影対象にし、個別 story は chromatic: { disableSnapshot: true } で撮影から外す
  • fullscreen・レイアウト系は個別 story のまま撮る — BoardView のような画面全体のコンポーネントをグリッドのセルに縮めると、幅・折返し・スクロールの描画条件が本番と変わり「本番と違うもの」を守ることになる。ここは 1 状態 = 1 枚が正しい

disableSnapshot を付けた story も公開 Storybook には残ります（Chromatic の Library に表示され、Snapshot タブが消えるだけ）。失うのは「その story 単体のピクセル比較」だけで、開発・レビューの導線は無傷。カタログが同じ状態を敷き詰めていれば検出力も落ちません。書き方は「meta で一括 disable + カタログだけ有効に戻す」が推奨——個別 story を後から足しても撮影対象が勝手に増えないためです。

// note-card.stories.tsx — 個別 story は開発用、撮影はカタログ 1 枚だけ
const meta = {
  component: NoteCard,
  parameters: { chromatic: { disableSnapshot: true } }, // 一括で撮影対象外に
} satisfies Meta<typeof NoteCard>;

// 開発用: Storybook には残る。撮影だけスキップされる
export const Default: Story = {};
export const Selected: Story = { args: { selected: true } };

// VRT 用: 全状態を 1 グリッドに敷き詰め、ここだけ撮影を有効に戻す
export const Catalog: Story = {
  parameters: { chromatic: { disableSnapshot: false } },
  render: () => (
    /* Default / Empty / LongContent / Selected / Dragging を並べる */
  ),
};
コンポーネントの性質撮り方
幅が固有で、状態が props だけで決まる表示系
Button・NoteCard・LoginCard など		 カタログ 1 枚に集約 + 個別 story は disableSnapshot。グリッドでも描画条件が変わらないので、1 枚で全状態を検出できる。
fullscreen・ビューポート幅に応答するレイアウト系
BoardView など		 個別 story をそのまま撮影。縮めると描画条件が本番と乖離するため集約しない。
play function やインタラクション後の見た目を持つ story 個別撮影のまま。操作後の状態はグリッドに敷き詰められない（静的に再現できる場合はカタログへ寄せてよい）。

通信状態も props に落とせば観測点にできます。board-view は WebSocket を持つフック層と表示層が分離され、connectionStatus を props で受けるため、「接続中」「再接続待ち」という一見動的な状態も固定画像として監視できています（Connecting / Reconnecting story）。Cloudflare（Durable Objects）移行後に通信がらみの story を書くときは、このパターン——WebSocket は story に持ち込まず、接続状態を props に落としてから撮る——に従ってください。

適用タイミング：新しいコンポーネントは最初からこの形で書く。既存 story（note-card・login-card）の改修は急がなくてよい——集約するとベースラインの張り替えが発生するので、月間消費が無料枠の半分（2,500）に近づいたタイミングでまとめて移行する。全適用すると現在の 16 枚/push は約 10 枚/push になり、以降はコンポーネントが増えても消費は「1 コンポーネント ≒ +1 枚」に漸近します。

意識すること（作業ではなく心構え）

カバレッジ

VRT が守るのは story がある UI だけ。story のない画面は「テストのないコード」と同じ。 CLAUDE.md の「全 UI コンポーネントに story を作る」を守っていれば自然に満たされる。

フレーキー

現在日時・乱数・自動再生アニメーションを story に入れると、変更がなくても毎回差分が出て「オオカミ少年」化する。 日付や ID は固定値の fixture を使う（「fixture はコンポーネント外に置く」ルールと同方向）。

コスト

push のたびにスナップショットを消費する（現在 16 枚/push）。story が増えたら Chromatic のダッシュボードで月間消費を時々確認する。 目安式: story 数 × 月の push 回数。無料枠 5,000 の半分を超えたら、まず上記の方針で表示系 story をカタログに集約し、それでも超えるなら workflow コメントの TurboSnap を有効化。

任意で決めておく選択肢

UI Tests の required check 化 — 現状は pending でもマージ自体は可能。承認漏れマージを機械的に防ぎたくなったら、ブランチ保護ルールの required status checks に UI Tests を追加する。チームが小さいうちは任意運用で十分。
