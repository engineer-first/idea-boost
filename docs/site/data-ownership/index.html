Idea Boost / Architecture Note

データはどこに住むのか — D1・RoomDO・contracts の責務マップ

「なぜストレージが2つあるのか」「contracts/ はどこまで面倒を見るのか」「PRD の残り機能でデータはどう増えるのか」。現行コードの実装コメントと PRD を根拠に、3つの問いに答える。

D1 — ロビー（ルーム横断） RoomDO — ルームの中の真実 contracts/ — 境界の形

Q1

なぜ DB を D1 と RoomDO の2つに分けているのか

まず前提として、これは「同じデータを2箇所に置く冗長化」ではありません。答える質問の種類がまったく違う2つのストレージで、同じ事実の真実は必ずどちらか一方だけが持ちます。

分ける理由 1 — 答える質問のスコープが違う

D1 は「全ルームを横断して探す」ための場所です。招待コード ABC123 がどのルームを指すかは、全ルームの中で一意であって初めて成立します（rooms.invite_code に UNIQUE 制約）。この一意性は、ルームごとに分断されたストレージでは原理的に保証できません。各 RoomDO は自分のルームのことしか知らないからです。

逆に RoomDO は「このルームの中」だけに答えます。workers/migrations/0001_lobby.sql の冒頭コメントがこの分担をそのまま宣言しています:

-- ロビー層のスキーマ。ルームの「中身」（メンバー・付箋）の真実は RoomDO が持ち、
-- D1 はルーム横断のディレクトリ（ユーザー・招待コード → ルーム解決）だけを持つ。

workers/migrations/0001_lobby.sql:1-2

分ける理由 2 — 同時編集のレースを「構造」で消す

Durable Object は 1 インスタンスが単一スレッドで動くため、そのルームへの操作はすべて自動的に直列化されます。2人が同時に同じ付箋を動かしても、フェーズ遷移と投票が同時に走っても、DO の中では必ず一列に並びます。ロックやトランザクション分離レベルの設計をアプリ側で考える必要がなくなる、というのが本質的な利点です。

もし付箋を D1 に置くと、複数の Worker インスタンスから同じ行への書き込みが並行して飛び、「最後に書いた方が勝つ」型の競合をアプリケーションコードで捌くことになります。ルームという自然な直列化単位があるのに、それを使わない手はありません。

分ける理由 3 — リアルタイム配信とデータの同居

RoomDO には WebSocket 接続そのものがぶら下がっています（Hibernation API）。付箋の状態と接続一覧が同じオブジェクトの中にあるので、note:move を受けたら「同期的に SQLite を更新 → その場で全接続へ配信」が 1 箇所で完結します。this.ctx.storage.sql.exec() は同期 API なので、メッセージ処理中にネットワーク往復すら発生しません。

D1 にはプッシュ通知の仕組みがないため、付箋を D1 に置いた場合「誰がどうやって変更を全員に配るのか」という別のインフラ（ポーリングや Pub/Sub）が必要になります。

分ける理由 4 — セキュリティ境界としても機能する

DO は外部から直接到達できず、必ず api-worker を経由します。api-worker がセッションを検証し、検証済みユーザー ID をヘッダー（X-Idea-Flow-User-Id）で DO に引き継ぐ設計なので、「D1 の rooms 行を知っていること」と「ルームの中身に触れること」が分離されています。実際、DO 側に残っていた招待コードの複製（旧 meta テーブル）は、ベアラートークン相当の秘密を二重に持たないよう v1 マイグレーションで意図的に掃除されています。

もし全部 D1 に寄せたら
  • 付箋の移動・編集のたびに共有 DB への書き込みが競合し、レース対策（楽観ロック等）を自前で書くことになる
  • 変更をリアルタイム配信する経路がなく、ポーリングか別インフラが必要になる
  • ルーム数が増えるほど、無関係なルーム同士が同じ DB の書き込み帯域を奪い合う
もし全部 RoomDO に寄せたら
  • 招待コードのグローバル一意性を保証できない（各 DO は自分しか知らない）
  • 「コード ABC123 はどのルーム？」に答えるには全 DO への問い合わせが必要になり、ディレクトリなしでは解決できない
  • 「自分がホストのルーム一覧」のような横断クエリが書けない
運用ルール（CLAUDE.md より）

D1 の rooms 行は「招待コード → ルーム解決」のディレクトリにすぎない。ルームの中の真実（メンバー・付箋）は RoomDO だけが持つ。同じ事実を両方に持たせないことで、二重管理の同期バグをそもそも起こせなくしている。

補足 — マイグレーションの流儀も2つある

ストレージが2種類あるので、スキーマ進化の仕組みも2系統あります。これは分離のコストではなく、それぞれのライフサイクルの違いの反映です。

D1RoomDO
置き場所 workers/migrations/*.sql（連番ファイル、wrangler d1 migrations がディレクトリを直接読む） workers/room-do-migrations/*.sql（タイムスタンプ名ファイル）。適用順序を決める集約 index.ts は gitignore 済みの生成物で、npm ci・テスト・起動時に自動再生成される（コミットするのは .sql だけ）
適用タイミング デプロイ時に npm run db:migrate で一括適用 各 DO の起動時。schema_migrations テーブル（適用済みIDの記録）と突き合わせ、不足分だけを transactionSync で原子的に適用
なぜそうなるか DB は1つしかないので、1回適用すれば終わり DO はルームごとに独立ストレージを持ち、起床タイミングもバラバラ。「どのマイグレーションを適用済みか」を各自が記録して収束させるしかない

Q2

contracts/ はどこまでの責任を負うのか

contracts/ の責任は一言でいうと「境界を流れる値の形」です。判断基準は明快で、その値だけを見て判定できるか。ストレージや状態を見ないと判定できないことは、すべて実装層（api-worker / RoomDO）の仕事です。

contracts/ が負う（値だけで判定できる）
  • 構造の検証 — メッセージ型の discriminated union、UUID 形式、必須フィールド
  • 値域の検証 — 本文 2000 文字以内、座標が CANVAS_COORDINATE_LIMIT 内の有限数
  • 正規化 — 招待コードの大文字化・空白除去（normalizeInviteCode）と形式チェック
  • 共有定数 — キャンバス座標の安全上限、付箋の初期配置範囲、Cookie 名、トークン audience
  • 形による封じ込め — 危険なフィールドをそもそもプロトコルに存在させない（後述）
contracts/ が負わない（状態が必要）
  • 認可 — 「メンバーか」「author 本人か」→ RoomDO の isMember / author_id 照合
  • 存在確認 — 「その付箋はあるか」→ RoomDO のストレージ照会
  • 可視性 — 「誰に配信してよいか」→ workers/visibility.ts の visibleTo() に一点集約
  • 永続化と配信 — SQL 実行、broadcast
  • 秘密の取り扱い — JWT の署名・検証は lib/session/（contracts は形だけ定義）
認可を contracts に混ぜない理由: zod スキーマは純粋関数として両側で再利用される。DB を触る検証を混ぜた瞬間、クライアントから import できなくなる。

なぜ「両方が import する」ことに意味があるのか

クライアント（lib/room-client）とサーバー（RoomDO）が同一のスキーマオブジェクトを import しているため、「クライアントは送れると思っているがサーバーは受け取れない」というズレが構造的に起きません。contracts/board.ts の座標安全上限もこの共有境界の一例です。

CLAUDE.md の「コントラクト層を厳密に定義し、実装層は再生成可能に保つ」はこのことで、形さえ合意されていれば、実装はどちら側も安全に書き直せるという設計です。

バリデーションを超えた責任 — 「形で塞ぐ」セキュリティ

contracts/ の最も重要な仕事は、実は検証ではなく「何をプロトコルに存在させないか」の決定です。contracts/room-protocol.ts の設計上の不変条件:

// - authorId を書き換えるメッセージは存在しない（構造的に不可能にする）。
//   authorId はサーバーが接続時のヘッダー（検証済みユーザーID）から決める。
// - roomId はそもそもプロトコルに現れない。1 RoomDO = 1 ルームなので、
//   接続先自体が roomId を意味しており、メッセージに含めて信頼する必要がない。

contracts/room-protocol.ts:6-11

「authorId の書き換えを認可チェックで拒否する」のではなく、書き換えを主張するフィールド自体が存在しないので、チェックの書き忘れという事故クラスが丸ごと消えます。認可チェック（実装層）は人間が書き忘れうるコードですが、スキーマに無いフィールドは忘れようがありません。これが「認可チェックではなく形で塞ぐ」（CLAUDE.md）の意味です。

検証の実行場所と責任の分担

contracts/ は「この値は正しい形か」まで。「このユーザーはそれをしてよいか」「その対象は実在するか」からは実装層。前者は純粋関数で両側から使え、後者は状態（ストレージ・セッション）が要るのでサーバー側にしか置けない — この物理的制約が、そのまま責任の境界線になっています。

Q3

PRD のこれからの機能で、データはどう増えるのか

PRD（デザインスプリント MVP）の残り機能を分解すると、増えるデータのほぼすべてが「ルームの中の真実」です。つまり Q1 の分担ルールに従えば、置き場所は考えるまでもなく RoomDO に決まります。D1 はほとんど太りません。

RoomDO 側 — 将来のマイグレーションのイメージ

Q1 で見た版管理の仕組みに乗せると、増分は workers/room-do-migrations/ 配下に YYYYMMDDHHmmss-短い説明.sql を1つ追加するだけです（npm run new:room-do-migration -- 短い説明 が UTC で発番してスタブを作ります）。適用順序を決める集約ファイル index.ts は gitignore 済みの生成物で、npm ci・テスト・起動時に全 *.sql をタイムスタンプ順に読んで自動再生成されるため、コミットもレビューも .sql だけで完結します。ファイル名のタイムスタンプが衝突することはまずなく、万一 #79 と #80 が同じ秒に別々のファイルを追加しても、生成スクリプトが重複として検出してエラーにします。各 DO は次に起きたときに不足分だけを原子的に適用します。

-- workers/room-do-migrations/20260810103000-phase-and-note-kind.sql（イメージ）
CREATE TABLE room_state (
  phase TEXT NOT NULL DEFAULT 'lobby',   -- lobby/map/hmw/sketch/decide
  step  INTEGER NOT NULL DEFAULT 1,
  timer_ends_at TEXT                     -- 個人ワークのタイマー締切
);
ALTER TABLE notes ADD COLUMN kind TEXT NOT NULL DEFAULT 'problem';
ALTER TABLE notes ADD COLUMN group_id TEXT;

-- workers/room-do-migrations/20260812141500-votes-and-decisions.sql（イメージ）
CREATE TABLE votes (
  voter_id TEXT NOT NULL,                -- サーバーが接続から決める
  note_id  TEXT NOT NULL,
  dot      TEXT NOT NULL,                -- 'subjective' | 'objective'
  phase    TEXT NOT NULL,
  PRIMARY KEY (voter_id, note_id, dot, phase)
);
CREATE TABLE decisions (
  phase   TEXT PRIMARY KEY,
  note_id TEXT NOT NULL
);

イメージ（実際のスキーマは実装時に contracts と同時に設計する）。それぞれ別ファイル・別タイムスタンプなので、#79 と #80 が同時期に着手しても編集箇所もタイムスタンプも衝突しません。

データと同時に増えるもの — 契約と可視性

Q2・Q1 の構造から、テーブルを足すときは必ず3点セットで増えることになります。ここが今のアーキテクチャの効き所です。

  • contracts room-protocol.ts に vote:cast や phase:advance などのメッセージが増える。このとき既存の不変条件を踏襲し、voterId をメッセージに含めない（authorId と同じく、投票者はサーバーが接続から決める。なりすまし投票を形で塞ぐ）。
  • visibility visibleTo() にフェーズ・ロールに応じた分岐が増える。「個人ワーク中は自分の付箋のみ」「ステルス投票中は自分の投票のみ」。配信経路がこの関数に一点集約されているため、見せない制御の実装箇所は増えない。
  • 否定系テスト CLAUDE.md のルール通り、「非メンバー・非 author・未認証ができないこと」を先に書く。可視性ルールを変えたら visibility.spec.ts のテーブルを必ず更新する。
判断基準のまとめ

新しいデータの置き場所に迷ったら、「入室する前に必要か？」と問う。前に必要（ルーム解決・一覧・ユーザー同定）なら D1、入室後にしか意味を持たないなら RoomDO。PRD の残り機能はステルス投票もタイマーもグルーピングも、すべて「入室後」の世界の話 — だから D1 はディレクトリのまま薄く保たれる。
