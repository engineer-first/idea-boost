RELEASE GUIDE

公開する。その入口は
$release だけ。

今回の変更を見て、必要なら説明を直す。
公開の意思を伝えたら、いつもの品質検査から履歴の記録まで進みます。

このページは手順書です。実際の操作はリポジトリを開いたCodexのCLIで行います。

普段はこれだけ

起動だけでは、本番は変わりません
あなたがすること
Skill / scripts / Actions がすること
01 · START$release

リリース作業を明示的に始める。

READ ONLY今回の変更を集める

前回の本番とdevelopを比較。関連PR、説明、タグ候補、現在の状態を提示。

02 · REVIEW見る。必要なら edit

利用者に伝わる内容か確認。自然言語でタイトルや説明を直せます。

DRAFT説明を整え、再提示

変更点 → 利用上の注意 → 必要な内部変更。PRやcommitは詳細として添えます。

03 · PUBLISHrelease

「これで公開して」でも同じ。cancel なら書き込まず終了。

PRODUCTION本番公開 → GitHub Release

候補を再確認 → 品質ゲート → D1 → API → App → health。成功してから履歴を記録。

branch・SHA・PR番号・run ID・attempt・タグの転記は不要。公開完了までSkillが状態を確認します。

見るのは、利用者に伝える意味

SkillがPR本文・commit・差分をもとに下書きします。タイトルの一覧ではなく、何ができるようになるかを確認してください。

機能そのものを今回から外したい場合は公開を止め、開発側で対象を整えます。edit はコードの公開範囲を変えません。

CLI の対話例

edit

「テキスト保存」ではなく
「結果をテキストで保存」にして

→ 説明だけを直して、もう一度確認。

目的に合う入口へ

OPERATE

今、公開する

$release が対話を担当。scriptsが対象・差分・採番を決め、Actionsが既存の公開処理を実行します。

UNDERSTAND

やり方を理解する

この恒久ページで流れと判断を確認。細かなコマンドや緊急操作は詳細運用へ。

LOOK BACK

以前の公開を見る

GitHub Releases が公開履歴の正本。版・日時・変更・commit・成功証跡を一緒に残します。

READABLE VERSIONS

日付と、今日の何回目か。

prod-2026.09.27.1

公開成功日時の日本時間（JST）で採番。同日2回目は末尾が .2。公開が日をまたぐと、提示した候補から日付が変わります。

タイトルは、主要な変更

例：「付箋の自動保存と結果の保存」

記録だけの再試行は同じタグ。過去のタグは改名しません。run ID / attemptやmanual receiptは重複を防ぐ内部証跡として保持します。

WHEN SOMETHING STOPS

止まったら、状態から次を決める

新しいチャットでも $release で状態を再取得できます。番号を探して転記する必要はありません。

本番変更前の検査で失敗した

読み取り・説明・品質ゲートの失敗

原因を直し、現在の候補を確認し直します。通常の公開では既存のDeploy品質ゲートを必ず通ります。失敗した処理を成功履歴にしません。

migration / API / App / health の途中で失敗した

一部が本番へ反映されている可能性

Skillは停止して該当runを示します。失敗した段階と実際の構成を確認し、担当者が部分再試行や復旧の方針を決めます。全再実行や自動ロールバックは行いません。全体の成功が確認できるまで正常Releaseは作りません。

本番とhealthは成功、Releaseの記録だけ失敗した

$release → retry-record

本番の再デプロイは不要。Skillが対象を自動取得し、既存のRecord Releaseで記録だけを回復します。同じ公開を二重登録せず、未記録のまま次の公開へ進みません。

実行中、または応答が返らなかった

statusを再取得し、待機・実行中のrunを監視します。dispatch受付だけを成功とせず、GitHub Releaseまで確認します。通信断の直後に同じ公開を繰り返し起動しません。

緊急の手動操作や、古い公開の記録が必要

詳細運用の互換・緊急入口へ。従来のPromote Release、Deploy、npm run deploy、manual/actions receiptは維持しています。個別Cloudflare操作はGitHubから自動観測できないため、確認証跡を残します。

この分担にした理由

相談と公開を分ける

「次のリリースに入れたい」では起動しません。明示的な $release と、内容確認後の公開指示を分け、普段の相談から本番が変わらない入口にします。

判断だけを人に残す

文章を整えるのはAI、差分取得・採番・状態判定はscripts。PR承認や追加の環境承認を増やさず、既存の品質ゲートとhealthを使います。

会話が途切れても戻れる

承認した説明は不変のGit参照へ保存。公開状態はActionsとReleasesから再取得します。説明保存後に公開開始が失敗しても、同じ候補なら保存した説明を再提示。developが進んだ場合は今回の差分を確認し直します。会話履歴だけに成功や再試行の根拠を置きません。

本番を変えずに試す

Codexで $release 今回の変更を確認したい。内容を見て、edit を試し、cancel で終了します。GitHub CLIの認証があれば、読み取りだけで進められます。

開発者向けの非本番検証は 副作用を差し替えたVitest手順へ。公開・回復・競合をテストし、実際の本番や架空のReleaseは作りません。
