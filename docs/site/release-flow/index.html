本番リリース手順書

開発した変更を ideaboost.dev に公開し、GitHub Releases に記録するまでの操作です。Codex Skill、GitHub Actions、ローカル手動操作の入口を記載しています。

通常の公開対象は GitHub 上の最新の develop 全体です。開発PRを develop にマージしてから公開します。ローカルで開いている feature ブランチや未コミットの変更は公開対象になりません。

1. どのブランチで、何をするか

ブランチ役割と操作本番への影響
feature/* 等実装・テスト・レビュー。PR のマージ先は develop。PR作成やpushだけでは本番は更新しない。
develop開発の統合先、通常公開の候補。最新を取得して $release を実行。Promote Release / Record Release の実行ブランチもここ。マージだけでは本番アプリを更新しない。docs/site/ の変更は Pages を更新する。
release本番デプロイ用。Promote Release が develop の確認済みcommitまで fast-forward。Deploy の手動実行ではこのブランチを選択。pushまたはDeploy起動で、品質ゲートの後に本番を更新する。

順序：作業ブランチ → 開発PR → develop にマージ → 公開内容を確認 → Promote Release → release 更新 → Deploy → health → GitHub Release。

Promote は履歴を揃えるために fast-forward します。develop → release のPRをGitHubの Merge ボタンでマージしないでください。通常公開では release を直接更新する必要はありません。

2. 公開前の準備

  1. 今回含める開発PRを develop にマージし、そのcommitの CI を確認します。develop に入っている他の変更も今回の対象です。除外する変更があれば、公開前に開発側で対象を整えます。
  2. ローカル操作をする場合、作業ツリーに未保存の変更がないことを確認して、リポジトリのルートで以下を実行します。develop が別worktreeで使用中ならそのworktreeで作業してください。
git status --short
git fetch origin
git switch develop
git pull --ff-only origin develop
mise install
npm ci
gh auth status

git status --short に変更が出たら、作業を保存してから切り替えます。git pull --ff-only が失敗したらローカル履歴を確認し、強制リセットで進めないでください。GitHub未認証の場合は gh auth login で認証します。Node等の開発ツールは mise.toml に従います。

  1. 初回は、Skillとworkflowが develop に導入済みであること、Actionsで公開・記録できる権限があることを確認します。Actionsには CLOUDFLARE_API_TOKEN、CLOUDFLARE_ACCOUNT_ID、vars.NEXT_PUBLIC_SITE_URL（本番は https://ideaboost.dev）が必要です。設定場所とWorker構成は構成・初期設定を参照してください。
  2. Actions で Promote Release / Deploy / Record Release の進行中・待機中の処理を確認します。進行中なら完了を待ちます。前回の本番公開が未記録なら、先に記録を回復します。

ここまでの準備・読み取りでは本番は変わりません。以下の3か4のどちらかで公開します。

3. Codex Skill で公開する

実行場所：最新の develop を取得したリポジトリをCodexで開きます。$release はシェルのコマンドではなく、Codexのチャットへの入力です。SkillはローカルのHEADに関係なくGitHubの develop を候補として取得します。

  1. $release と入力します。前回の本番、今回の差分・関連PR、説明、タグ候補、状態が表示されます。
  2. 公開する機能、利用上の注意、タイトルを確認します。直す場合は edit と自然言語の指示を入力します。例：edit タイトルを「結果をテキストで保存」にして。説明の編集は公開するコードの範囲を変えません。
  3. 表示内容で公開するなら release または「これで公開して」と入力します。ここからGitHubへ書き込み、Promote Releaseを起動します。公開しない場合は cancel で終了します。
  4. Skillが示すActionsのrunを確認し、公開完了の確認まで進みます。受付メッセージだけで完了にしないでください。

SHA・PR番号・タグの転記は不要です。新しい会話でも $release で状態を再取得できます。説明を保存した後に中断した場合は同じ候補の保存内容を再提示します。保存済み説明は上書きできないため、内容を変える必要があれば中止して新しい候補を用意します。

公開せず試す場合：$release 今回の変更を確認したい → 説明を確認 → edit → cancel。一般のリリース相談だけではSkillは起動しません。

4. Skill を使わず GitHub Actions で公開する

Codexを使わない場合は、説明JSONをコードと一緒にレビューしてから Promote Release を実行できます。この経路も既存のDeploy品質ゲートとhealthを通ります。

4-1. リリース説明を develop に用意する

  1. 直前の本番Release の本文から「公開commit」の40桁SHAを取得し、今回の差分と関連PRを確認します。ローカルで読み取りを補助する場合は以下を使えます。
npm run release:operator -- status .release-history/snapshot.json

previousCommit が直前の本番、candidate がGitHubのdevelopです。ready なら続行、current なら公開差分なし、その他は復旧表へ進みます。APIエラーを差分なしとして扱わないでください。

  1. developから説明更新用の作業ブランチを作り、.github/release-note.json を更新します。下の例の比較元・説明・PR番号を実際の内容へ置き換え、開発PRでレビューして develop にマージします。JSONだけを未コミットのまま置いてもActionsは読みません。
{
  "title": "今回の主要な変更",
  "previousCommit": "直前の本番Releaseの40桁commit SHAに置き換える",
  "mode": "release",
  "changes": [
    { "kind": "修正", "text": "利用者に見える変更を書く", "prs": [123] }
  ],
  "notices": []
}

これは書式例です。kind は「追加・変更・修正・内部変更」、関連PRがなければ prs: []。自分自身のcommitや公開日時は書きません。説明準備後にdevelopへ別の変更が入ったら、説明と公開範囲も再確認します。初回の比較元や保存済み説明との互換は詳細運用を参照してください。

4-2. develop → release のPRを確認して起動する

  1. GitHubの Pull requests → New pull request で base: release / compare: develop を選び、PRを作ります。方向を逆にしないでください。
  2. 差分、説明JSON、CIと Release Note Check のSummaryを確認します。PRのheadが最新developと一致している必要があります。
  3. Actions → Promote Release → Run workflow を開き、以下を入力します。
欄値
Use workflow from / Branchdevelop
pr_number今作った develop → release PRの番号
expected_sha / note_jsonこのPR経路では両方空欄
  1. 公開内容を確認して Run workflow を押します。Promote がreleaseを進め、Deployを起動します。PRの Merge ボタンは押しません。
  2. 公開完了を確認します。

CLIで同じ起動をする場合（123 は実際のPR番号に置き換える）：

gh workflow run promote-release.yml \
  --repo engineer-first/idea-boost --ref develop -f pr_number=123

releaseがdevelopの祖先でなければPromoteは停止します。強制pushで回避せず、hotfix等の履歴を開発側へ取り込んでからやり直します。

5. 公開完了を確認する

  1. Actions → Deploy で今回の release のrunと対象commitを開きます。gate → deploy-api → deploy-app → health-check → record-release が成功していることを確認します。D1 migrationは deploy-api 内で行います。
  2. GitHub Releases に今回の版があり、本文の公開commit・変更内容・本番Deployのリンクが対象と一致することを確認します。
  3. 本番アプリ で今回変更した主要操作を確認します。health成功は全機能の動作保証ではありません。

完了条件：対象commitのデプロイとhealth成功、対応するGitHub Releaseの記録、今回の主要操作の確認。

版は prod-YYYY.MM.DD.N（例：prod-2026.09.27.1）。公開成功日時のJST日付と同日の連番で確定します。候補提示から日をまたぐと日付が変わります。記録だけの再試行は同じ版を使い、実際に同じcommitを再デプロイした場合は別の版になります。過去のタグは改名しません。

6. 失敗・中断から復旧する

まずActionsのrunを開き、どのジョブまで成功したか確認します。Skillを使う場合は $release、CLIなら npm run release:operator -- status で状態を取り直せます。

状態・失敗箇所次の操作
currentdevelopと記録済み本番は同じcommit。通常の新規公開は不要です。
running / Actions待機中該当runを待つ。通信断でも先にActionsを確認し、二重起動しない。
Promoteの検査失敗ログから説明・ブランチ・比較元を修正し、候補を再確認。release更新前なら本番変更なし。
説明保存後／release更新後、Deployの起動失敗まずDeployが起動済みでないか確認。同じ候補ならSkillで保存済み説明から再開。releaseが対象commitまで更新済みなら下記「Deployを手動起動」も利用可能。
deployment-failedDeployの失敗ジョブを確認。gateだけの失敗なら原因を修正して再検査。migration / API / App / healthで失敗した場合は部分反映の可能性があるため、実際の構成とログを確認して担当者が復旧を判断。
retry-record / record-releaseのみ失敗本番とhealthは成功済み。下記「記録だけ回復」へ。再デプロイは不要。

6-1. 記録だけ回復する

Skillなら $release → retry-record。Skillを使わず対象を自動取得する場合：

npm run release:operator -- status
npm run release:operator -- retry-record --confirm

2行目は retry-record 状態を確認して実行します。GitHub画面だけで行う場合は：

  1. 対象DeployのURL /actions/runs/実行番号 からrun IDを確認し、再実行履歴のattemptを確認します。
  2. Actions → Record Release → Run workflow で branch: develop、run_id と attempt にそのDeployの値を入力。note_json は空欄で実行します。
  3. Record Releaseの成功とGitHub ReleaseのURLを確認します。元のDeployの record-release ジョブだけを再実行する方法も使えます。

記録の回復に Re-run all jobs や npm run deploy を使わないでください。未記録の本番があるまま次の公開へ進むと事前検査で停止します。

6-2. Deploy を手動起動する

Promoteによって release が確認済み対象まで更新され、Deployだけが起動されなかった場合、または同じcommitを意図して再公開する場合に使います。developの新しい変更を取り込む操作ではありません。

  1. releaseの先端commitと説明を確認し、同じDeployが実行・待機中でないことを確認します。
  2. Actions → Deploy → Run workflow で branch: release を選び、実行します。
  3. 品質ゲートから記録までを確認します。releaseを選ばないとDeployのgateは実行されません。
gh workflow run deploy.yml \
  --repo engineer-first/idea-boost --ref release

6-3. 本番が部分的に更新された場合

失敗した段階、D1 migrationの適用状況、API/AppのWorker versionとcommit、healthの結果を確認し、関連PR/Issueに実状態を残します。自動ロールバックはありません。Re-run failed jobsは以前の成功段階を引き継ぎますが、後続の公開が既にある場合は古いrunを再実行せず、現在の本番を基準に復旧を判断してください。全体の成功が確認できるまで正常なReleaseを作りません。

7. ローカルから手動で公開する

Actionsが利用できない等の理由でローカル公開を選ぶ場合の入口です。このコマンドはローカルHEADを公開します。Skillの公開対象（リモートdevelop）との違いに注意してください。

  1. リリース担当者間で手動公開を共有し、ActionsのPromote / Deploy / Record Releaseが実行・待機中でないことを確認します。手動操作は共通Actionsキューのロック外です。作業中に別の公開を開始しないでください。
  2. 通常は確認済みの origin/develop を取得します。例外的な復旧commitは担当者が対象を指定します。git status --short が空、git rev-parse HEAD が公開予定commitで、同じcommitがGitHub上にあることを確認します。
  3. 対象の .github/release-note.json（または保存済み計画）、差分とCIを確認します。gh auth status とCloudflare認証、wrangler.jsonc / workers/wrangler.jsonc の本番アカウント・Worker・D1を確認します。設定は構成・初期設定を参照します。
  4. 本番公開を実行します。
npm run deploy

説明・未記録版・作業ツリー等の事前検査後、D1 → API → App → https://ideaboost.dev/api/health の順で処理します。ローカル入口はActionsの全品質ゲートを再実行しません。公開するcommitの必要な検証を先に完了させてください。

  1. 成功receiptが .release-history/ に保存され、Record Releaseが起動されます。コマンドの終了は記録依頼の受付までです。ActionsのRecord Release成功とGitHub Releaseまで確認します。

記録の送信だけ失敗したら、出力された同じreceiptファイルを再送します（下のファイル名は実際の出力に置き換えます）。

npm run release:submit -- .release-history/出力されたファイル.json

receiptを作り直したり再デプロイしたりせず、元の成功証跡を使います。receipt保存自体が失敗した場合はエラーに出力された成功情報を保存します。個別の deploy:api / deploy:app / deploy:migrate は全体の成功を自動記録しません。

8. hotfix・ロールバック・外部操作

  • hotfix：可能なら修正をdevelopへ取り込み通常の公開経路を使います。releaseへの直接pushはDeployを起動します。例外的に直接更新する場合も対象commitに説明を用意し、公開後は修正をdevelopへ取り込み、次回のfast-forwardを妨げないよう履歴を確認します。
  • ロールバック：$release は巻き戻しを実行しません。担当者が復旧commit、DBとの互換性、利用者への影響を判断して復旧します。過去のコードへ戻すだけではD1やRoomDOのデータは戻りません。
  • Cloudflare画面・個別コマンドからの更新：GitHubは全体成功を自動観測できません。migration/API/App/health、共通commit、UTC完了時刻、Worker version、確認者をPR/Issueに残します。異なるcommitのAPI/App混在を1版として記録しません。

外部操作や復旧の記録は、説明JSONに commit と成功証跡 deployment を追加したreceiptを作り、npm run release:submit -- receipt.json で送ります。巻き戻しは mode: "rollback" と notices が必須です。Record Release画面ならbranchは develop、note_json にreceipt全文、run_id / attempt は空欄です。receiptの形式と確認項目を参照してください。

9. この手順書を GitHub Pages へ公開する

手順書の公開先は GitHub Pages、本番アプリの公開先はCloudflareです。手順書の更新に本番アプリのリリースやprodタグ作成は必要ありません。

  1. docs/site/release-flow/index.html を作業ブランチで編集し、develop 向けPRを作ります。
  2. PRの Docs サイトプレビュー コメントで表示を確認します。リンクはcommit SHA固定のgithackプレビューです。これは本番Pagesへの公開ではありません。
  3. PRを develop にマージします。docs/site/** の変更を検出すると Deploy docs site to GitHub Pages が自動実行されます。
  4. workflowが成功したら 公開された手順書 を開いて更新内容を確認します。PRのままではこの恒久URLは更新されません。

再公開が必要な場合は同workflowの Run workflow → branch: develop を選びます。docs/site/ 全体がPagesへ公開されます。初期設定はRepositoryの Settings → Pages → Source: GitHub Actions。Pagesの環境設定・権限で停止していないかActionsのログで確認します。

10. 仕様・検証・参照先

実行するworkflow選ぶブランチ役割
Promote Releasedevelop候補の検査、release更新、Deploy起動
Deployrelease品質ゲート、本番更新、health、履歴記録
Record Releasedevelop成功済み公開の記録のみ。再デプロイしない
Deploy docs site to GitHub Pagesdevelop手順書など静的HTMLの公開

Promote / Deploy / Record Releaseは共通キューで直列に処理します。タグやGitHub Releaseを手動作成するだけでは本番を公開したことにはなりません。記録の正本はGitHub Releases、手順・失敗判断はこのページ、スキーマや証跡の詳細はリリース履歴の運用仕様にあります。

開発者が本番へ書き込まず公開・回復・競合の振る舞いを検証するには：

npm run test -- scripts/release-operator.spec.ts scripts/release-history.spec.ts scripts/promote-release.spec.ts scripts/release-automation.spec.ts scripts/deploy-production.spec.ts

テストはGitHub API等を差し替えます。実際のCloudflare更新や本番のRelease作成を行うものではありません。履歴の文面訂正は同じReleaseを編集し、訂正日時と理由を追記します。タグ・公開commit・元の成功証跡は書き換えません。
