IDEA-FLOW-APP 技術解説 / CLOUDFLARE 編

「サーバーが1台いる」をやめた世界の地図
— Workers・Durable Objects・D1

Vue + Go の掲示板では、1つの常駐プロセスがリクエスト処理・状態保持・DB接続のすべてを担っていました。 Cloudflare はこの1人3役を 実行（Workers）・状態（Durable Objects）・台帳（D1） の3部品に分解します。 この分解を頭に入れると、このリポジトリの構成がそのまま読めるようになります。

00 — まず対応表から

あなたの知っている部品は、全部ある

新しい概念に見えますが、実際は「Go サーバーの中に同居していたもの」が独立した部品になっただけです。 先に対応表を頭に入れてから、各章で「なぜ分けたのか」を見ていきます。

GO + VUE の世界CLOUDFLARE の世界役割

01 — WORKERS

Workers：常駐しない、状態を持てない Go ハンドラ

Worker は一言でいうと 「fetch ハンドラだけを世界中に配ったもの」 です。 Go で書いていた http.HandleFunc の中身に相当するコードを書いてデプロイすると、 Cloudflare が世界300以上の拠点すべてにそのコードを配置します。 リクエストは利用者にいちばん近い拠点で処理されます。

Go との最大の違いは プロセスが常駐しない ことです。 Worker はリクエストが来た瞬間に V8 の isolate（Chrome のタブ1枚に近い超軽量な実行環境。コンテナより2〜3桁軽い） の中で起動し、応答を返すと基本的に破棄されます。だから Go では当たり前だったこれが動きません： 

// Go ではプロセスが1つだから、これで「全リクエスト共有のカウンタ」になった
var count int
func handler(w http.ResponseWriter, r *http.Request) {
    count++  // Workers で同じことをすると…
}

Workers でグローバル変数に書いても、次のリクエストは別の拠点の別の isolate に届くかもしれず、 同じ拠点でも isolate はいつ破棄されるか分かりません。カウンタは「増えたり戻ったり」して見えます。 つまり 状態は必ず外部に置く しかない。その置き場が次の2章です。

なぜそうするのか / そうしないとどうなる？

常駐プロセスを捨てた見返りが「コールドスタートほぼゼロで、無限にスケールし、利用者の近くで動く」こと。 逆に Go の1台構成のままだと、ブラジルの利用者は毎回東京まで往復し（RTT 250ms超）、 アクセス急増時はそのプロセス1つが上限になります。Workers は「状態を持てない」制約を受け入れる代わりに、この2つの問題を構造的に消しています。

02 — DURABLE OBJECTS

Durable Objects：名前で呼べる「世界に1つだけ」のミニサーバー

Durable Object（DO）は Workers が捨てた「状態」を取り戻すための部品で、 名前を指定すると、世界でただ1つのインスタンスに必ずつながるオブジェクト です。 このリポジトリでは 1ルーム = 1つの RoomDO。実際のコードはこの1行です：

workers/api-worker.ts:44

// roomId という「名前」から、世界で一意な RoomDO インスタンスを取得する。
// どの拠点の Worker から呼んでも、必ず同じインスタンスに着く。
return env.ROOM_DO.get(env.ROOM_DO.idFromName(roomId));

DO には Go 経験者にこそ刺さる性質が3つあります。

1. シングルスレッドで直列化される — Mutex が要らない

1つの DO へのリクエストは1つずつ順番に処理されます。 Go の掲示板で sync.Mutex や channel で守っていた「同時書き込みのレース」が、構造的に発生しません。 このアプリで「2人が同時に付箋を動かしても壊れない」のは、RoomDO がすべての変更を一列に並べるからです。

2. 自分専用のストレージ（SQLite）を持つ

各 DO はインスタンス専用の SQLite を内蔵しています。RoomDO はコンストラクタで自分のテーブルを作ります：

workers/room-do.ts（抜粋）

export class RoomDO extends DurableObject {
  constructor(ctx: DurableObjectState, env: Env) {
    super(ctx, env);
    this.ctx.blockConcurrencyWhile(async () => {
      this.ctx.storage.sql.exec(
        `CREATE TABLE IF NOT EXISTS members (...);
         CREATE TABLE IF NOT EXISTS notes (...);`,  // ← この DO 専用の SQLite
      );
    });
  }

「room-abc の付箋」は room-abc の DO の中にだけ存在します。 Go でいえば map[roomID]*Room の各エントリが、永続化とロックつきで独立プロセス化されたイメージです。

3. WebSocket を握り続けられる

Worker は応答したら消えますが、DO は接続を保持できます。RoomDO は各クライアントの WebSocket を受け付け、 付箋の変更を visibleTo()（可視性ルール）を通して全員に配信します。 Go で goroutine ごとに接続を持ってブロードキャストしていた部分の置き換えです。 しかも Hibernation API により、接続を維持したまま DO 本体をメモリから追い出せる（= 待機中は課金されない）ようになっています。

なぜそうするのか / そうしないとどうなる？

仮に付箋の状態を Worker のメモリに置くと、01章の通り「どのコピーに当たるか分からない」ので、 A さんの付箋移動が B さんに見えない・消える、という更新ロストが起きます。 かといって毎操作を共有 DB に書いて解決しようとすると、今度は「読んで→比較して→書く」の間に他人の書き込みが割り込むレースが残り、 結局アプリ側でロックを自作する羽目になります。 DO は「状態の置き場」と「直列化」をインフラ側で同時に解決する部品です。

03 — D1

D1：全体で共有する、ただの SQLite

D1 は難しくありません。Cloudflare が面倒を見てくれる1つの SQLite データベース で、 役割はあなたの知っている MySQL / PostgreSQL とほぼ同じです。Worker からバインディング（env.DB）経由で SQL を投げます。

面白いのはこのリポジトリでの使い方が意図的に薄いことです。D1 に入っているのは users と rooms の2テーブルだけ。ルームの中身（メンバー・付箋）は一切入っていません。

workers/migrations/0001_lobby.sql（抜粋）

-- D1 はルーム横断の「ディレクトリ」だけを持つ。中身の真実は RoomDO。
CREATE TABLE rooms (
  id          TEXT PRIMARY KEY,
  invite_code TEXT NOT NULL UNIQUE,  -- 招待コード → ルーム解決のための索引
  host_id     TEXT NOT NULL REFERENCES users (id),
  created_at  TEXT NOT NULL DEFAULT (datetime('now'))
);

なぜ2つのデータベース（D1 と DO の SQLite）に分けるのか。判断基準は2つです。

  • 横断検索が必要なもの → D1。 DO は「名前が分かっているとき」しか引けません。「招待コード Xy3k はどのルーム？」のような 名前がまだ分からない検索は、SQL の WHERE invite_code = ? ができる D1 の仕事です。
  • 同時編集で競合するもの → DO。 付箋の位置は複数人が同時に書き換えます。02章の通り、これは直列化が必要なので RoomDO の仕事です。
なぜそうするのか / そうしないとどうなる？

もし付箋を D1 に置くと、全ルームの書き込みが1つの DB に集中し、 さらに「変更を他の参加者に push する」手段がないのでポーリングが必要になります。 逆に users を各 DO に置くと、「このユーザーが参加しているルーム一覧」のような横断クエリのたびに 全 DO に問い合わせる羽目になります。 競合するデータは部屋ごとに隔離（DO）、横断するデータは1か所に集約（D1） — この住み分けが設計の背骨です。

04 — リクエストの一生

このリポジトリで1つのリクエストが辿る道

部品が出揃ったので、実際の構成を通して見ます。このリポジトリには Worker が2つあります （wrangler.jsonc が2枚あるのはこのため）。 Next.js アプリ本体を配る idea-flow-app（app-worker）と、 データへの唯一の入口 idea-flow-api（api-worker）です。

「招待コードでルームに参加する」を例にすると：

  • ① ブラウザが /api/rooms/join を叩く。Cookie に HS256 JWT のセッション（lib/session/）。
  • ② app-worker が /api/* を Service Binding（API_WORKER）で api-worker へ転送。
  • ③ api-worker がセッションを検証（Go の認証ミドルウェアに相当。ただし毎ハンドラで明示的に呼ぶ）。
  • ④ D1 に WHERE invite_code = ? でルームを解決 — 横断検索なので D1 の仕事。
  • ⑤ RoomDO を idFromName(roomId) で取得し、RPC でメンバー登録。以降の付箋操作は WebSocket で RoomDO と直接やりとり。

バインディング（env.DB や env.ROOM_DO）は設定ファイルで宣言した「接続の注入口」で、 Go で DB コネクションを DI していたのと同じ発想です。宣言はここにあります：

workers/wrangler.jsonc（抜粋）

"durable_objects": {
  "bindings": [{ "name": "ROOM_DO", "class_name": "RoomDO" }]
},
"d1_databases": [
  { "binding": "DB", "database_name": "idea-flow-lobby", ... }
]
なぜ api-worker を「唯一の入口」にするのか

D1 や DO に触る経路が1本だと、認可チェック（セッション検証・メンバー判定）をその1本に集約できます。 経路が複数あると「片方だけチェックを忘れる」事故が構造的に可能になる。 CLAUDE.md の「Next 側から D1 や DO を直接触らない」というルールは、この事故をルールではなく形で塞ぐためのものです。

05 — まとめ

「真実はどこにあるか」で全部説明できる

Cloudflare のスタックは、突き詰めるとデータごとに「真実の置き場所」を1か所決める設計です。 このアプリの答え合わせ：

データ真実の置き場所理由
付箋・ルームのメンバー RoomDO（DO 専用 SQLite） 同時編集が競合する → 直列化が必要
ユーザー・招待コード D1（idea-flow-lobby） ルーム横断で検索する → SQL が必要
ログイン状態 JWT Cookie（クライアント持ち） 毎リクエスト検証すればサーバー側に状態が不要
境界を流れるデータの形 contracts/（zod スキーマ） クライアントとサーバーが同じ定義を import する

用語ミニ辞書

isolate
V8 エンジン内の軽量な実行サンドボックス。コンテナと違い起動が数ミリ秒以下なので、リクエストごとに作って捨てられる。
binding（バインディング）
Worker から外部リソース（D1・DO・別 Worker 等）への型付きの接続口。wrangler.jsonc で宣言し、env に注入される。
wrangler
Cloudflare の CLI。wrangler dev（ローカル起動）、wrangler deploy、wrangler d1 migrations apply など。Go でいう go run + デプロイスクリプトの合体。
workerd / miniflare
本番と同じ Workers ランタイムのオープンソース実装と、そのローカルシミュレータ。このリポジトリの npm run test:workers（vitest-pool-workers）は本物の workerd 上でテストを走らせている。
Hibernation
DO が WebSocket 接続を維持したままメモリから退避できる仕組み。長時間アイドルなルームでコストがかからない。

  • workers/api-worker.ts — 入口。セッション検証 → D1 / DO への振り分けが1ファイルで追える
  • workers/room-do.ts — DO の実物。RPC・WebSocket・専用 SQLite が全部入り
  • workers/visibility.ts — 「誰に何を見せるか」の一点集約。DO 設計の旨味が出る場所
  • workers/wrangler.jsonc — バインディング宣言。部品同士の配線図として読む
