# ローカルデモの設計メモ

状態: 実装済み。`npm run demo` でローカル専用の入口を起動する。
操作手順・全14ステップの台本・付箋24枚の一覧は[ローカルデモ台本](local-demo-runbook.md)を参照。

## 目的と条件

- 説明者が操作し、初めて見る人が各ステップの目的を具体例で理解できることを優先する。
- 課題整理からHMW（「どうすれば〜できるだろう？」という問い）、アイデア決定まで、1-1〜3-5の全14ステップを見せる。
- デモ時間・説明時間・制限時間は設定しない。共有や投票など共通する操作の再説明は省けるが、各ステップの内容と成果物は見せる。
- 題材は「学生生活の困りごとを解決するアプリを、ハッカソンで考える」。学び合う相手探しという課題から、出会い方の問い、空きコマ勉強マッチへつなぐ。
- ホストとデモ参加者4人の合計5人。各フェーズで全員が1〜2枚、合計8枚を持つ。3フェーズで24枚の具体例を用意する。
- 各フェーズへの進入時に5人分の下書きを準備する。ホストには自分の2枚だけ見える。共有と投票は説明者の操作を待つ。
- 本番と通常開発では無効。明示したローカルデモ起動だけで使える。

## 自動準備と説明者の操作

入口から全14ステップを選べる。途中から開始する場合は、それまでの課題・HMWの決定や現在のステップに必要な共有状態を準備する。
通常の「次へ」で順に進んだ場合も、HMW・アイデアの個人ワークへ入った時点で下書きを準備する。

- 自動: 5人のメンバー、各フェーズ8枚の下書き、途中開始に必要な過去の決定。
- ホストが操作: 自分の付箋の編集・共有、自分の投票、採用案の決定、次のステップへの進行。
- 合図で操作: 「他4人が共有する」「他4人が投票する」。途中開始を除き、ホストの共有や投票を代行しない。
- 1-3の途中開始: 8枚を共有済みにし、「学び合う相手探し」「昼休みの混雑」の2グループを各4枚で用意する。
- 通し進行の1-3: 全8枚を共有した後に「グループ例を配置する」で同じ2グループを作れる。再実行するとサンプルの位置とグループ名を例へ戻す。
- 手動入力の例: グループ名を「空きコマに学び合える仲間がほしい」に変更し、分類から課題の理解へつなげる。全ステップの入力・説明例を画面内と台本に記載する。

画面の折り畳み式「デモ操作」パネルには、各ステップの目的、自動で用意するもの、説明者が操作すること、入力・説明に使う具体例、話す内容の例を分けて表示する。

## 自由操作と固定シナリオ

通常の付箋追加・編集・削除、グループ名の変更、配置変更、投票、採用案の選択は自由に行える。
同じルームへ再接続しても、編集・削除したサンプルは初期状態に戻さない。「見せ場へ移動」「やり直す」は新しいルームを作り、サンプルを初期状態で用意する。

デモ参加者の文章と支持先は固定する。別の課題を採用しても、後続のHMWやアイデアの文章は自動生成しない。
代理投票は共有済みの固定サンプルを対象にし、追加した自由入力へ勝手に投票しない。候補がすべて削除・非公開なら操作を拒否する。
やり直す場合は、新しいデモルームを作る。元ルームでの自由入力は引き継がない。

## 開発環境への置き方

専用ブランチへ恒久的に分離せず、通常の開発ブランチで保守する設計とする。本番で利用できないことはブランチ名に依存させない。
現在はPRのブランチ `codex/local-demo` にあるため、マージ前はその実装がある作業ディレクトリで起動する。

初回セットアップはREADMEに記載する。普段は通常の開発サーバーを停止してから `npm run demo` を実行し、入口で開始ステップを選ぶ。
デモ用ホストとして実セッションを発行するため、Googleログインや5人分のブラウザ操作は不要。

## 実装した構成

- 起動: `npm run demo`。通常開発と同じ 3000 / 8787 ポートを使い、使用中なら終了する。Next と Worker を localhost に起動し、D1 migration と起動確認を終えてから入口 URL を表示する。
- 保存先: `.wrangler/demo/state`。通常開発の `.wrangler/state` とは分離する。起動ごとの構成・一時秘密は `.wrangler/demo/runtime-*` に生成する。既存の `.env.local` / `.dev.vars` は変更しない。
- 本番境界: 通常構成は `workers/api-worker.ts` と `RoomDO`。デモ起動だけが `workers/demo-worker.ts` と `DemoRoomDO` を使い、通常の entry にはデモ RPC を含めない。API は localhost、明示フラグ、起動ごとの秘密、実セッション、固定ホストを検証する。Next のデモページと中継 API も development と明示フラグを要求する。
- データ経路: Next の中継から既存の `apiFetch` → api-worker の認証・ルーティング → RoomDO。ボードは通常の WebSocket を使う。デモの代理共有・投票は既存ハンドラと受信者ごとの可視性判定を通す。
- 初期化: 新しい専用ルームのみに固定メンバー・各場面の付箋・必要な投票と決定を用意する。既存ルームへの再投入は拒否する。テスト専用の `setPhase` RPC は公開しない。
- 合図: 操作種別と期待する現在フェーズ・ステップだけを送る。任意の代理ユーザー ID や移動先フェーズを入力できない。場面が変わった要求は拒否し、共有済み・投票完了済みの合図を再送しても重複しない。ホストの操作は代行しない。
- 台本の自由: デモ参加者の発言と支持の分布は固定。推奨案への支持を多くしつつ、ほかの候補にも票を配る。ホストは付箋を自由に追加し、投票先と各フェーズの採用案を選べる。

## 確認項目

- 全14ステップを選べ、各フェーズで5人全員の1〜2枚を見せられる。
- 通し進行でも、HMWとアイデアの個人ワークに自分の2枚が届く。
- 1-3に2グループと名前の例があり、手動で変更できる。
- 代理共有・投票は明示操作で実行され、重複しない。
- 個人付箋と投票中の他人の票は非公開のまま。
- 編集・削除したデータが再接続で復活しない。
- 通常ルームと本番構成へデモデータが入らない。
- 台本の自動準備・手動操作が実装と一致し、デモ時間の前提がない。
