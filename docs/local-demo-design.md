# ローカルデモの設計メモ

状態: 合意した体験を実装。`npm run demo` でローカル専用の入口を起動する。

## 合意した目的と条件

- 説明者が操作し、初めて見る人にアプリを説明する場面を優先する。
- デザインスプリントの流れに沿って、アイデア出しに慣れていないチームでも全員の意見を出し、課題整理からアイデア決定まで迷わず進められることを伝える。
- 基本は1-1から3-5まで全14ステップを順番に見せる約8分の通しデモ。共通操作の説明を後半で短くする。以前の約5分版は、時間が限られる場合の抜粋として扱う。
- ローカル開発環境で簡単に使えるようにする。本番環境には不要。
- ルームは合計5人。説明者がホスト兼参加者として操作し、残り4人はデモ参加者とする。
- 他4人の共有・投票は、説明者の明示的な合図で実行する。説明中に自動で進めない。
- 題材は「学生生活の困りごとを解決するアプリを、ハッカソンで考える」。まず1つの筋書きを丁寧に作り、課題・問い・アイデアがつながる内容にする。

## 見せ場とやり直し

- 「最初から」「共有直前」「投票直前」「アイデア比較」「完了」の見せ場を選んで開始できるようにする。
- 各見せ場をやり直せるようにする。
- やり直しはデモ専用ルームを作り直す方式とし、通常の開発用ルームには影響させない。
- やり直すと、その見せ場に用意した初期状態へ戻る。

## 自由操作と台本の関係

- 付箋の追加や投票先・採用案の選択など、通常のアプリ操作は自由に行える。
- 通し台本では、おすすめの選択と選ぶ理由を示す。
- デモ参加者4人の発言内容は固定する。台本とは別の課題を選んだ場合、その先の問いやアイデアとの意味的なつながりは保証しない。
- 自由な選択に応じた筋書きの自動生成は初期範囲に含めない。

## 開発環境への置き方

- 専用ブランチに恒久的に分離せず、通常の開発ブランチで保守する。
- ローカルで明示的にデモ起動した場合だけ有効にする。
- 本番で利用できないことはブランチ名に依存せず、実装と検証で担保する。
- アプリ本体の変更へ追従しやすくし、デモ時のブランチ切り替えを不要にする。
- 初期版は通常の開発サーバーを止めてから起動する。同時起動への対応は初期範囲に含めない。
- デモの保存先は通常開発と分離する。
- 起動コマンドの仮称は `npm run demo`。プロセス構成と有効化の判定方法は実装設計で決める。

## 起動から入室まで

初回セットアップ後の体験を次の流れにする。

1. デモ専用コマンドを実行する。
2. 表示されたURLを開く。
3. 「最初から」や「投票直前」などの見せ場を選ぶ。
4. 「デモを開始」を押すと、デモ用ホストとしてログインし、準備済みのルームに入る。

Googleログインや、説明者による5人分のアカウント操作は不要にする。初回の依存導入・環境設定と、普段のデモ起動は区別する。

## 説明者向けの操作

- デモ中の画面内に、折り畳み式の「デモ操作」パネルを置く。
- 今の場面で使える操作だけを表示する。
- 「他4人が共有する」「他4人が投票する」「見せ場へ移動」「やり直す」を提供する。
- 今の場面で伝えることを、一言の台本として表示する。
- 普段は折り畳み、必要なときだけ開けるようにする。
- 他4人の操作が完了したか確認できるようにする。
- 別の管理画面へ移らず、1つの画面で説明を進められるようにする。

## 通常アプリとの関係

- 開発用ログインは3固定ユーザーに対応し、実セッションを発行する。
- ルーム内の状態と操作には、ローカルのAPI・RoomDO・WebSocketを利用できる。
- デモ専用のデータ投入・新規ルームによる復帰・他参加者の操作代行を、通常の API / RoomDO の経路に追加した。
- 個人付箋は本人のみ閲覧できる。投票中は他人の投票内容が隠れる。
- 他参加者の共有・投票が必要なので、ユーザーと付箋の初期投入だけでは一連のデモを完走できない。

- [LEGOの担当者へのインタビュー](https://www.infoq.com/news/2019/08/design-sprints-lego/): LEGOでのデザインスプリント活用を紹介している。

- 現在のPRDの対象はアイデア決定まで。元のデザインスプリント全工程への対応を意味する説明にはしない。

## 現在の基本構成：全14ステップの通しデモ

[通し台本とデータ評価](local-demo-runbook.md)を説明者向けの基本手順とする。1-1から3-5まで同じルームで通常の「次へ」を使い、課題・HMW・アイデアをその場で決定して引き継ぐ。約8分は目安であり、説明時間は未実測。

- 課題整理で個人ワーク・共有・グループ化・投票を説明する。
- 問いの作成ではHMWの意味とテンプレートを見せ、共有・投票の再説明を省く。
- アイデアでは発想支援と2軸評価を見せ、最後に課題から採用案まで振り返る。
- 現行データの初期配置と投票先の安定性など、通し実演に向けた改善案は同資料に記載する。これらは未実装。

## 時間が限られる場合の5分抜粋構成

- 導入（30秒）: 5人のチームと今回のテーマ、画面上の進行ガイドを紹介する。
- 個人ワークと共有（60秒）: 自分の付箋を追加して共有し、合図で他4人の付箋も共有する。
- 課題を選び、問いへ（90秒）: 投票と結果公開を実演し、決定した課題をHMWへつなげる。
- アイデアを比較（90秒）: 用意した問いとアイデアを使い、価値と実現可能性による配置、投票、決定を見せる。
- まとめ（30秒）: 課題から問い、採用アイデアまでのつながりを振り返る。

これは用意した見せ場へ移動する短縮案で、全ステップの実演にはならない。今回の全14ステップを見せる目的には上記の通し台本を使う。

## 実装した構成

- 起動: `npm run demo`。通常開発と同じ 3000 / 8787 ポートを使い、使用中なら終了する。Next と Worker を localhost に起動し、D1 migration と起動確認を終えてから入口 URL を表示する。
- 保存先: `.wrangler/demo/state`。通常開発の `.wrangler/state` とは分離する。起動ごとの構成・一時秘密は `.wrangler/demo/runtime-*` に生成する。既存の `.env.local` / `.dev.vars` は変更しない。
- 本番境界: 通常構成は `workers/api-worker.ts` と `RoomDO`。デモ起動だけが `workers/demo-worker.ts` と `DemoRoomDO` を使い、通常の entry にはデモ RPC を含めない。API は localhost、明示フラグ、起動ごとの秘密、実セッション、固定ホストを検証する。Next のデモページと中継 API も development と明示フラグを要求する。
- データ経路: Next の中継から既存の `apiFetch` → api-worker の認証・ルーティング → RoomDO。ボードは通常の WebSocket を使う。デモの代理共有・投票は既存ハンドラと受信者ごとの可視性判定を通す。
- 初期化: 新しい専用ルームのみに固定メンバー・各場面の付箋・必要な投票と決定を用意する。既存ルームへの再投入は拒否する。テスト専用の `setPhase` RPC は公開しない。
- 合図: 操作種別と期待する現在フェーズ・ステップだけを送る。任意の代理ユーザー ID や移動先フェーズを入力できない。場面が変わった要求は拒否し、共有済み・投票完了済みの合図を再送しても重複しない。ホストの操作は代行しない。
- 台本の自由: デモ参加者の発言と支持の分布は固定。推奨案への支持を多くしつつ、ほかの候補にも票を配る。ホストは付箋を自由に追加し、投票先と各フェーズの採用案を選べる。

### 各見せ場の初期状態

| 見せ場       | 初期位置                      | 用意する状態                                                           |
| ------------ | ----------------------------- | ---------------------------------------------------------------------- |
| 最初から     | 1-1 自分の課題                | 5人が各1枚の非公開付箋を持つ。ホストには自分の1枚だけ見える            |
| 共有直前     | 1-2 課題共有                  | 同じ5枚が非公開。ホストの共有と他4人への合図を実演できる               |
| 投票直前     | 1-4 投票                      | 5枚を共有済み、全員未投票                                              |
| アイデア比較 | 3-3 価値×実現のしやすさで評価 | 課題と HMW を採用済み、アイデア5枚を配置済み、アイデアへの投票は未実施 |
| 完了         | 3-5 アイデアを決定            | 3フェーズの投票と決定を用意し、採用案と課題・HMWを振り返れる           |

「やり直す」は、入室時の見せ場から新しいルームを作る。「見せ場へ移動」も新しいルームを作るため、それまでの自由入力を新ルームへ引き継がない。

### 5分抜粋デモの操作メモ

1. 「最初から」で始め、5人のメンバーと個人付箋を示す（30秒）。
2. ホストの課題を編集または追加し、通常の「次へ」で共有へ。ホストの付箋を共有し、デモ操作パネルから「他4人が共有する」を実行する（60秒）。
3. グループ化から投票へ進み、主観1票・客観3票を自由に投じる。「他4人が投票する」を実行してから結果を公開し、課題を採用する（90秒）。
4. HMW への持ち越しを示す。「アイデア比較」の見せ場へ移動し、用意した課題・HMWとアイデアの対応を説明する。配置を変え、投票と採用を実演する（90秒）。
5. 結果の採用アイデアと持ち越した課題・HMWを振り返る（30秒）。

全ステップを連続して操作する場合は、HMW・アイデアの個人ワークでホスト自身の付箋を作成する。他4人の固定下書きは、各フェーズの共有の合図で用意して共有する。自由に採用した課題にも通常の持ち越しは働くが、デモ参加者の固定文言の意味的なつながりは変化しない。

## 合意した体験から導く確認項目

- 初回セットアップ後、専用コマンドと入口画面から、5人のルームにホストとして入れる。
- 自分の付箋の追加・共有・投票と、ホストによる進行を実際に操作できる。
- 他4人の共有・投票は合図で動き、説明中には勝手に進まない。
- 各見せ場から開始でき、やり直すと用意された状態に戻る。
- デモの開始・やり直しが、通常開発のルームや保存データを変更しない。
- 個人付箋の非公開、共有、投票結果の公開、課題から問い・アイデアへのつながりを説明できる。
- 自由に入力・選択でき、台本のおすすめを強制しない。
- デモ操作パネルを折り畳め、他参加者の操作完了を確認できる。
- 本番環境および明示的にデモ起動していない通常開発では、デモ機能が利用できない。
- 通し台本を使い、全14ステップを見せながら重複する操作説明を省けることを実演で確認する。約8分の配分を目安に、説明時間を測る。
