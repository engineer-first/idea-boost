# ローカル検証環境

`npm run dev:verify` で、開始待ちと1-1〜3-5の全14ステップへ直接入れる環境を起動する。
操作ページでステップを押すと、必要な付箋・過去の決定・投票を準備した新しいルームを作る。

標準は起動から2時間で停止する。長時間の確認は `npm run dev:verify:persistent` を使う。
期限変更・停止範囲・並行worktreeのポート指定は[開発サーバーの起動と停止](dev-server-lifecycle.md)を参照する。

## 起動と使い方

1. 初回は `npm ci`。通常の3000 / 8787サーバーを停止し、`npm run dev:verify` を実行する。起動完了時に検証ページと共有成果の閲覧URLがターミナルへ表示される。
2. `http://localhost:3000/dev/verify` をOwnerで開く。環境ファイルの作成・編集は不要。
3. 検証するステップを押し、「検証ボードを開く」を押す。ボードは別タブで開く。
4. 別ブラウザ／シークレットでMember等としてログインし、同じ `http://localhost:3000/dev/verify/board` を開く。
5. 次の状態は操作ページで選ぶだけ。例えば2-3の後に3-1を押すと、開いている追従タブは全アカウントとも新しいルームへ移る。前面タブでは通常約1秒＋通信・描画時間。バックグラウンドではブラウザのタイマー抑制により遅れる場合がある。
6. 終了は `Ctrl+C`。起動時に新しいセッション秘密を発行するため、再起動後はログインし直す。

| アカウント            | パスワード | 検証ルーム内の役割                          |
| --------------------- | ---------- | ------------------------------------------- |
| <owner@example.test>  | password   | ホスト。状態作成・他2人の代理投票も操作可能 |
| <member@example.test> | password   | 通常の参加者                                |
| <viewer@example.test> | password   | 通常の参加者（閲覧専用ロールではない）      |

既存の開発ログインと同じユーザーIDに付箋を紐付ける。新しいユーザーは追加しない。
Ownerを2タブで開く場合も、同じユーザーの付箋と操作が同期する。
各フェーズ12枚、各アカウント4枚。個人作業では本人の4枚だけが見える。

## 初期状態を選んだ理由

細かな個数やUI操作の組み合わせを列挙せず、操作・表示・権限が変わるステップを入口とする。
PR #272のローカル専用Worker・RoomDO・実WebSocket方式を基に、説明用パネルと台本を外した。

| 開始位置        | 準備する状態                                            |
| --------------- | ------------------------------------------------------- |
| 開始待ち        | 3人参加済み。開始時に各自の下書きを準備                 |
| 1-1 / 2-1 / 3-1 | 各自4枚の下書き。過去フェーズの採用内容も準備           |
| 1-2 / 2-2 / 3-2 | 各自3枚は共有済み、1枚は未共有。3-2はマップに配置       |
| 1-3             | 名前付き2グループと未分類の付箋                         |
| 3-3             | 12枚のアイデアを2軸マップに配置済み                     |
| 1-4 / 2-3 / 3-4 | Memberの主観1票・客観3票が完了。OwnerとViewerは未投票   |
| 1-5 / 2-4 / 3-5 | 全員投票済み。得票あり／0票の候補が混在し、採用は未確定 |

- [投票完了表示（#309）](https://github.com/engineer-first/idea-boost/pull/309)を確認できるよう、投票中は完了・未完了が混在する。「他2人の投票を完了する」は残りの票だけを追加し、Ownerの票は変更しない。
- [0票候補の一括除外（#320）](https://github.com/engineer-first/idea-boost/pull/320)と[採用候補の共有（#322）](https://github.com/engineer-first/idea-boost/pull/322)を確認できるよう、結果画面に0票候補を残し、採用前から始める。
- [ドラッグ排他（#319）](https://github.com/engineer-first/idea-boost/pull/319)や候補共有は、別アカウントの実接続で確認する。
- グループ数、採用後、除外後、タイマー状態は通常操作で作る。長文・多数件・画面幅・テーマは既存のStorybookも併用する。

## ボードへの影響とデータ保持

検証操作は `/dev/verify` に集約する。ボードに操作パネル・ボタン・余白・ショートカットは追加しない。
追従タブは `?verify=follow` を持ち、現在の検証先の参照だけを定期取得する。
検証環境が有効かつ追従を明示した場合だけ実行し、通常のルームURLには載せない。
ロビーから通常の開始操作でボードへ進んでも追従は継続する。

「このルームを固定して開く（追従なし）」で開いたタブは、次の状態へ切り替えず元のルームを表示し続ける。
切替は既存ルームの上書きではなく新規作成。編集・削除は元のルームに残り、再接続でサンプルを復活させない。
同じステップを押せば、いつでも初期状態からやり直せる。後続フェーズの文章は固定サンプルで、採用内容に応じた自動生成はしない。

通常の「次へ」でフェーズを進めた場合も、新しいフェーズの個人作業に初めて入ったときだけ下書きを準備する。
通常操作の検証では、共有・投票・採用・進行の既存の制約が適用される。

## 実装と検証

- データは `.wrangler/verification/state` に保存し、通常開発のDBと分離する。
- ローカル専用構成は `verification-worker.ts`、`VerificationRoomDO`、検証先の参照だけを持つ `VerificationWorkspace` を使う。本番構成には追加しない。
- APIは起動フラグ・起動ごとの秘密・localhost・実セッションを検証。変更操作はOwnerのみで、Next側でも同一originを検証する。検証操作用の秘密をブラウザへ渡さない。成果閲覧専用の値はOwnerが取得できる。
- 個人付箋と投票中の票の秘匿、グループ、重なり順は通常のRoomDOの仕組みを使う。
- `npm test`、`npm run test:workers`、`npm run test:verification`、`npm run typecheck`、`npm run lint` で確認する。検証専用Workerテストは専用構成で実行する。
- Storybookは `Verification/VerificationView` と `Verification/VerificationConsole`。通常ボードの表示確認は `Room/RoomBoardLayout` を併用する。

## 共有成果の検証

Ownerで `/dev/verify` の「共有成果の保存と閲覧」を使う。Owner の閲覧・管理権限は開発用ログイン時に自動登録される。検証用 D1 は通常開発・本番と分離する。

1. 任意のルーム名を入力し「途中を準備」を押す。名前を空欄にした場合と同じ名前を複数回使った場合も確認する。
2. 「成果一覧を開く」から一覧を開き、詳細を開いて一覧へ戻る。表示用IDで同名のルームを区別できる。
3. シークレットウィンドウでは未ログインの成果 API が401になることを確認する。
4. 「完了を準備」では3つの決定と共有盤面を確認する。非共有のアイデア1枚は含まれず、候補外と名前付きグループを区別できる。ボードで以前の工程へ戻って編集しても、確定記録が変わらないことを確認する。
5. 「成果なしを準備」では共有付箋のないルームを作る。「保存失敗を準備」では途中の成功分を残したまま完了記録の投影を失敗させる。ボードでは完了済みの成果をコピー・保存でき、一覧・詳細では失敗と前回成功分が分かることを確認する。
6. 「現在のルームの保存障害を解除」を押す。通常のアラーム再試行で保全済みの完了記録が反映される。一般ユーザーのボードに再試行操作は追加しない。
7. 「期限切れを準備」は検証専用DOで最終利用時刻を過去へ進め、実際の期限判定・削除処理を通す。作った成果は一覧に出ず、詳細も取得できない。OSの時計を変更する必要はない。

ケースを選び直すたびに新しいルームを作り、以前のルーム・成果は上書きしない。再起動でデータを消さず、各成果には通常と同じ30日の期限を適用する。全検証を最初からやり直す場合のみ、停止後に `.wrangler/verification` を削除して再起動する。通常開発の保存先は削除しない。

通常開発との分離は、通常環境で作った成果が検証一覧に出ないこと、検証成果が通常一覧に出ないことで確認する。通常環境の起動には `npm run dev` と `npm run dev:api` を併用する。既存ルームへの導入は [共有成果の保存と閲覧権限](../operations/shared-outcomes.md) を参照する。

## 節目の進行記録を確認する

同じ検証ルームで通常の進行操作を続け、別タブの `/shared-outcomes` から表示用IDが同じルームを開く。検証のステップ選択は新規ルームの初期投入なので、選択位置より前の履歴は作らない。途中ステップから準備したルームは最初の記録の開始が不明となる。

1. 「開始待ち」から通常の開始操作で進める。「進行の記録」に開始したステップが現れ、まだ離れていなければ「終了未記録」と時間差「—」になる。
2. 課題を共有・グループ化した後、書き足しへ戻る。再び共有して本文・位置を変えても、戻る直前の記録の「盤面を見る」では以前の本文・配置・グループを確認できる。
3. 課題の投票を終え、採用する前に再投票する。再投票前の記録には公開済みの主観票・客観票が別々に残る。投票ステップを離れた記録には、そのフェーズの票数を表示しない。
4. アイデア評価で2軸マップを広げて付箋を移動し、次へ進む。評価の記録を開くとアイデアタブが選ばれ、当時の広さ・座標と全文を確認できる。
5. 採用後に初めて成果を公開する。最後の区間が終了し、完了成果を参照できる。ボードと成果を往復しても終端記録は増えない。
6. 保存状態を「最新の状態を取得」で更新する。共有0枚の正常保存と、反映待ち・反映失敗・盤面なしを区別する。履歴の続きを取得しても、訪問順が保たれることを確認する。
7. 狭い画面でも記録選択・課題/問い/アイデアの切り替え・付箋全文・再取得操作へ到達できることを確認する。

運営閲覧の権限剥奪後と30日期限後の拒否、途中の盤面保全失敗、時刻保存失敗による移行取り消し、別記録の独立再試行、投影中の期限超過はWorkerテストで障害を注入して検証する。Storybookの空・反映待ち・反映失敗・欠落・取得エラー表示は、この永続化の検証の代わりにはしない。
