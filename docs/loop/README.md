## 1. なぜループで進めるか

- **完成の定義が Issue に散らばっている。** PRD と進行仕様は詳しいが、「いま何ができていて何が足りないか」を1か所で読めない。エージェントは目の前の Issue を閉じられても、完成への距離を測れない。
- **エージェントの作業が人の起動待ちになる。** いまは人が Issue を選び、エージェントを起こし、PR を見てマージする。小さな改善も人の手が空くまで止まる。
- **評価が作った本人に寄る。** 作ったセッションが自分の成果を確かめるので、甘くなりやすい。

変えるのは「すべての変更に人の起動と人のマージを挟む」こと。戻せる変更はエージェントが PR を出して取り込み、戻せない変更だけ人が見る。

## 2. 原則

1. **完成の定義を先に置く。** [completion.json](completion.json) の差分を埋めるのがループの仕事。定義の無い「改善」は終わらない。
2. **1周1仕事、状態は GitHub とリポジトリに。** 会話の記憶に頼らない。各周回は台帳・Issue・PR・`git log` を読み直し、1つ終えて context を捨てる。
3. **作る人と評価する人を分ける。** 巡回と取り込み前の確認は、作ったセッションとは別の context で行う。
4. **検証とマージの重さはリスク段階で決める（下表）。** 戻せる変更は速く取り込み、巡回で拾う。
5. **チームの仕事を奪わない。** 担当者のいる Issue・人の PR・人が作業中の場所には触らない。ループが拾うのは `loop:*` ラベルの付いた担当者なしの Issue だけ。
6. **本番に出すのは人。** develop への取り込みまでがループ。本番公開は従来どおり人が `$release` で行う。
7. **詰まったら止まらずに迂回する。** 同じ仕事で3周失敗したら `loop:blocked` にして次へ。人の判断が要るものは `needs-human` に積んで待たない。
8. **記録は最小、学びは残す。** 証拠は PR 本文とコメントへ。次の周回が同じ失敗をしないための1行だけ、該当する指示書か規約に足す。条件が毎回違う理由で落ちるなら、実装を足さず条件を疑う。

### リスク段階（検証とマージの重さ）

| 段階            | 例                                                                                              | PR を出す前                                                    | develop へ取り込むのは                                                 |
| --------------- | ----------------------------------------------------------------------------------------------- | -------------------------------------------------------------- | ---------------------------------------------------------------------- |
| **R0 戻せる**   | 文言・見た目・余白、文書、テスト追加、依存のpatch/minor                                         | 変更範囲の lint・型・関係するテスト                            | land ループ。必須チェックと CodeRabbit のレビューが済めば              |
| **R1 振る舞い** | ステップの導線、操作の結果、表示条件、Renovate の major                                         | 上記＋`verify` で PC・iPad 幅を実際に操作、画面資料を PR へ    | land ループ。上記＋別 context の確認（`ui-review` など）が合格なら     |
| **R2 境界**     | 認可・可視性・セッション、RoomDO の共有状態、`contracts/` の形、migration、個人情報、本番の運用 | 上記＋`authz-security-reviewer` の確認、`npm run test:workers` | **人**。PR に `R2` と `needs-human` を付け、人のレビューとマージを待つ |
| **R3 人の判断** | PRD 方針・チームの運用・課金や契約・外部への連絡                                                | 実装しない                                                     | 人が決めた後に R0〜R2 として扱う                                       |

段階は高い方へ倒す。迷ったら1つ上にする。

## 3. 全体図

```text
            ┌──────────── チーム（レビュー・判断・本番公開・利用者の声） ────────────┐
            │  R2 のマージ / R3 の判断 / 台帳の修正 / $release / ユーザーテスト       │
            └──────▲──────────────────────────────────────────┬────────────────────┘
                   │ 現在地 Issue・needs-human                 │ 決定・ラベル
 ┌─────────────────┴──────────────────────────────────────────▼──────────────────┐
 │ 再計画 (replan)  台帳と現実の差分 → loop:finish の Issue を作る・並べ直す          │
 └──────▲───────────────────────────┬────────────────────────────────────────────┘
        │ 所見 (loop:ux)             │ 拾える Issue
 ┌──────┴───────┐          ┌────────▼────────┐  Ready PR  ┌──────────────────────┐
 │ 巡回 (patrol) │          │ 完成 (finish)    │──────────▶│ 取り込み (land)       │
 │ 別 context で │◀─develop─│ 1周1Issue→1PR    │◀──修正────│ レビュー対応→マージ    │
 │ 旅を歩き採点  │          └─────────────────┘           │ R0/R1 と Renovate     │
 └──────────────┘          ┌─────────────────┐           └──────────┬───────────┘
                           │ 庭仕事 (garden)  │                      │ develop
                           │ 文書・死にコード │                      ▼
                           └─────────────────┘         人が $release で本番へ
     develop の CI が赤くなったら、他より先に修理 (mend) が直す
```

## 4. 完成とは何か

完成＝[completion.json](completion.json) の全 item が `pass`、かつ巡回で S1/S2 の所見が2回続けて0件、かつ本番に載っていること。
これは「開発として完成」の定義で、学生チームが迷わずアイデアを決められるかは、実際のユーザーテストで確かめる（[LOOPS.md の価値検証](LOOPS.md#価値検証人が主役)）。

台帳の item と acceptance を足す・分ける・書き直すのは再計画ループか人。finish は `status`・`evidence`・`production` だけを更新する。作業者が条件を緩めて「完了」にする抜け道を塞ぐため。

## 5. チームとの関係

- **ループは junhat6 のアカウントで動く。** PR・コメント・マージは GitHub 上で junhat6 の操作に見える。PR に `loop:*` ラベルを付け、本文末尾に `Loop:` 行を置いて人の作業と区別する。
- **チームが Issue をループに任せたいときは** `loop:finish` を付け、担当者を空けておく。外したいときはラベルを外すか担当者を付ける。
- **マージは Discord に通知される**（既存の merge 通知）。R0/R1 の取り込みに違和感があれば、PR へのコメントか `git revert` の PR で戻す。戻された変更を land は再び取り込まない。
- **Milestone・Project 状態は既存の自動化に任せる。** 番号付きブランチと Draft→Ready で状態が動くので、ループが状態を手で動かすことはしない。

## 6. 元の設計から変えたこと

| 項目            | kobe-student-hub                       | IdeaBoost                                      | 理由                                                                   |
| --------------- | -------------------------------------- | ---------------------------------------------- | ---------------------------------------------------------------------- |
| 取り込み        | main へ直接 push                       | develop への PR。ループの land が取り込む      | ruleset が PR と必須チェックを求め、チームが差分を PR で読む           |
| 本番公開        | 1日2便の定時列車（agent）              | 人が `$release`                                | release skill は明示呼び出し専用で、イベント前の公開判断はチームが持つ |
| 待ち行列        | `loop:*` ラベルの Issue                | 同じ。ただし担当者付きの Issue は拾わない      | チームの仕事を奪わない                                                 |
| 記録            | commit trailer と WORK.md              | PR のラベルと本文の `Loop:` 行、現在地は Issue | develop へ直接書けず、記録のための PR を増やさない                     |
| R2 の扱い       | 別 context の独立検証で agent がマージ | 人がレビューしてマージ                         | 認可・共有状態の破れはチームのデモと利用者に直接届く                   |
| 並行数          | builder 最大3                          | loop の開いた PR 最大2                         | CodeRabbit の枠と、人の PR との衝突を抑える                            |
| 執筆・polish 等 | editor・polish・video-review           | 持ち込まない                                   | IdeaBoost に対応する仕事が無いか、まず6本で回してから決める            |

## 7. 変えないもの

- [AGENTS.md](../../AGENTS.md) の常に守ること（境界、red 先行のテスト、設定を緩めない、秘密をブラウザに出さない）。
- PR 本文は [write-pr](../../.agents/skills/write-pr/SKILL.md) とテンプレートが正本。ループ用の別テンプレートは作らない。
- 「AI の動作確認はユーザーテストではない」という区別。報告でも混ぜない。
