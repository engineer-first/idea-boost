# 巡回の旅と重大度

patrol が歩く利用者の旅と、所見の重大度。人物と要求の正本は [PRD](../prd.md)・[進行仕様](../product/sprint-flow.md)、呼び方は [用語集](../glossary.md)、見た目は [DESIGN.md](../../DESIGN.md)。
ここには「どこを歩き、何を所見と提案にするか」だけを置く。何をループが直してよく、何を提案に留めるかの正本は [README のループが決めてよいこと](README.md#ループが決めてよいこと)。

## 歩く人と画面

- 人物：アイデア出しに慣れていない学生チーム（PRD のメインペルソナ）。進行役がいなくても、画面だけで次にやることが分かるかを見る。
- 人数：3人（開発用ユーザー1人＋別のブラウザ context のゲスト2人）。1人では共有・発表者交代・投票の旅を歩けない。
- 画面：旅を歩き通すのは PC（1280×800）。崩れだけを見るために、変わった画面は iPad 横（1180×820）でも開き、スマホ縦（360×740）は入口（J0 と J1 の参加）だけ開く。
- 1回に歩くのは、変わった場所に関係する旅と、持ち回りの旅1本（J0→J6 の順に、前回の次から）。

## 人の目が落としがちなところ

人が触って確かめるときは、自分の画面・ふつうの量・正しい順の操作で済ませやすい。巡回と polish は、旅の中で次を意識して当てに行く。

- **相手の画面。** 自分の操作が、別の参加者の画面に同じ形で出るか。付箋の位置・投票・発表者・ステップがずれないか
- **端の量。** 長い表示名、長い付箋、付箋が多い（30枚）、参加者が多い（上限）、0件・1件のとき
- **端の時間。** タイマーの時間切れ直後、共有した直後、ステップが切り替わる瞬間、相手が動かした直後に触る
- **戻り道。** 再読み込み、ブラウザの戻る、切断と再接続、タブの切り替えのあと
- **キーボードだけ。** Tab・Enter・Esc で旅を進められるか、ダイアログを閉じたあとフォーカスがどこへ行くか
- **英語表示。** ブラウザの言語を英語にした画面で、未翻訳・はみ出し・日英の混在が無いか（変わった画面だけ）
- **表記。** 画面の言葉が[用語集](../glossary.md)と合っているか、同じものを違う言葉で呼んでいないか（`messages/` を `rg` で照らす）
- **裏側。** ブラウザの console のエラー・警告、失敗した通信、axe の違反

## 重大度

| 重大度 | 意味                                                                                                                                                                                        | Issue                                                        |
| ------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------ |
| S1     | 旅が最後まで進めない。未共有の付箋・投票中の個別票が他の人に見える。データが消える                                                                                                          | `loop:ux` `loop:ready` `P0`                                  |
| S2     | 操作できない・反応しない、PC で崩れて操作できない、相手と表示が違う、axe の critical/serious、付箋を掴めない・動かした位置に保存されない（[移動の台帳](note-move-reliability.md#失敗とは)） | `loop:ux` `loop:ready`                                       |
| S3     | 進められるが欠陥がある：誤字・表記の揺れ、小さな重なり・はみ出し、iPad 横・スマホ縦の入口の崩れ、axe の moderate/minor、console のエラー                                                    | Issue にしない。patrol log に一覧だけ（polish が拾って直す） |
| 提案   | 欠陥ではないが、迷って止まる・誤操作から戻れない・分かりにくい・文言や見た目を変えたい                                                                                                      | `loop:proposal`（[提案の出し方](README.md#提案の出し方)）    |

合否は「旅が最後まで行けたか」と「S1/S2 があるか」で決め、点数で丸めない。提案は合否に数えない。

## 所見の書き方

- S1/S2 は 1所見＝1 Issue（1回3件まで）。Type は `Bug`。直し方に方向の選択が要る所見は、最小の直し（崩れを収める、元の形に戻す）を受け入れ条件にし、その先は提案に分ける。本文は [Issue記述ルール](../team/issue-writing.md) の Why と現状。Project の状態は `未整理` のまま（人がトリアージする）。
- 現状に、旅・画面幅・再現手順・スクリーンショット（ローカルの架空データだけ）を置く。「なんとなく良くない」は所見にしない。
- 進行仕様と食い違うときは、どちらが正しいかを決めず、食い違いとして書く（仕様の判断は人）。
- 重複は `gh issue list --label loop:ux --state all --search "<語>"` で探し、既存へ「<SHA> で再現」とコメントする。

## 分かりやすさの原則

2026-11-24 の定例と野崎さんとの MTG の方針（「プロダクトが伸びるには分かりやすさが大事」「デザインスプリントをもっとシンプルに」「小学生でも迷わないくらいに」）を、提案を書くときと、人が選んだ提案の細部を build が決めるときの基準にしたもの。上ほど優先する。ループはこの原則を理由に、提案を経ずに体験の方向を変えない（2026-11-27 のオーナーの方針）。

1. **今やることが1つに見える。** 画面を開いて3秒で「自分は今なにをすればいいか」が分かる。同時に目立つ操作は1つ。
2. **できない操作は、やる前に分かる。** 押せない・置けないものは押す前に見た目で分かる。やってから失敗のトーストで知らせない。
3. **次へ進む条件が見える。** 「できた！」・タイマー・全員の状態など、次へ進むために何が要るかが画面に出ている。
4. **説明を読ませる前に、形で伝える。** 長い説明文より、配置・アイコン・例で伝える（[DESIGN.md](../../DESIGN.md)）。説明が要るなら1文。
5. **出したり消したりしない。** その場で使わない道具は隠すか弱め、使う場面では同じ位置に出す。位置が飛ぶ UI を作らない。
6. **用語をそろえる。** 同じものを違う言葉で呼ばない（[用語集](../glossary.md)）。

## 較正の記録

人が採点し直してずれた観点を、日付と1行で足す。

- 2026-11-25: 短い通信待ちで「処理中…」などの中間表示へ切り替わるチラつきは許容しない（元の表示を保ち完了後に切り替える）。決定スタンプの押下演出や投票パレットの視認性など、気持ちよさ・見やすさを削る縮小変更は避ける。
- 2026-11-27: オーナーが「満足度を上げるには人間の目がかなり必要」として、体験の方向を変える改善をループが決めず提案に留めることにした。人の目が落としがちな欠陥は、ループがむしろ強く探す。
