# 付箋の移動を失敗させない

付箋を掴んで動かす操作は IdeaBoost の中核で、「動かしたはずが戻る・掴めない」は体験を大きく損なう。2026-11-27、オーナーは見た目ではなくこの失敗そのものを直すことと、一度直して終わりにせずループで直し続けることを求めた。
これまでも移動の失敗は何度も直してきた（References）が、原因は毎回別の場所にあり、直した後に別の失敗が残っていても数える手段がなかった。
判断は [ADR 0033](../adr/0033-note-move-never-fails.md) に記録する。ここには、失敗の定義・測り方・原因の台帳・ループでの回し方を置く。

## 失敗とは

本人が共有付箋を掴んで離したとき、次のどれかが起きること。

- 掴めない（押して動かしても付箋が付いてこない）
- 離した位置に保存されない（元の位置や別の位置へ戻る）
- 本人の画面では動いたのに、ほかの参加者の画面と位置が違う

移動できない工程（投票ステップなど）で動かないことは、ここでは失敗に数えない。それは「できない操作は、やる前に分かる」（[分かりやすさの原則](ux-rubric.md#分かりやすさの原則)）の問題として巡回が見る。

## ほかのツールから引いた原則

共同編集のホワイトボードで枯れている結論。IdeaBoost の移動を直すときは、この順で照らす。

1. **本人の操作は、応答を待たずに本人の画面へ反映する。** Figma は「クライアントのプロパティ変更は、サーバーの応答を待たずに常にすぐ適用する」。tldraw も本人の編集をすぐ適用してからサーバーへ送る。
2. **届いた通知で、本人が今している操作を巻き戻さない。** Figma は、まだ応答が返っていない本人の変更と食い違うサーバーからの変更を捨てる（古い値で一瞬上書きされるちらつきを防ぐため）。tldraw は、本人の未確定の変更をいったん外してサーバーの変更を当て、その上に本人の変更を当て直す。
3. **同じ付箋を同時に動かしたら、後から届いたほうを採る。やり直しを求めない。** Figma は同じオブジェクトの同じプロパティの競合を「サーバーへ最後に届いた値」に決める。Excalidraw は要素ごとの版が新しいほうを採り、同じ版なら乱数の小さいほうに決めて全員の画面をそろえる。どちらも、負けた人に「もう一度操作してください」と出さない。
4. **サーバーが断るのは、権限と整合性が壊れるときだけ。** Figma のサーバーが変更を断る例として記事が挙げるのは、親子関係が輪になる更新だけ。位置の競合は断らない。
5. **途中の位置は流すだけ、保存は離したとき。** 掴んでいる間の位置は他の人へ見せるための一時の情報で、保存する状態とは分ける。

IdeaBoost は 1 と 5 を満たしている（[ADR 0006](../adr/0006-move-transactions.md)・[ADR 0019](../adr/0019-queue-local-note-moves.md)）。2〜4 は満たしていない。移動を始めるときに付箋の版がサーバーと一致することを求め、一致しなければ断る。通知を受けた本人側が、掴んでいる移動や離し終えた未送信の移動を自分から取り消す経路も多い。下の台帳の原因は、ほぼこの差から出ている。

## 測り方

### 手元で数える（計測スクリプト）

実ブラウザ2人と実 RoomDO で、場面ごとに付箋を動かし、「動かしたとおりに保存され、相手の画面とも一致した回数」を数える。往復に本番相当の遅延（既定は片道 80ms）を入れる。遅延が無いと競合の窓が開かず、失敗が出ない。

```sh
IDEA_BOOST_VERIFY_APP_PORT=3147 IDEA_BOOST_VERIFY_API_PORT=8947 npm run dev:verify   # 別の端末で
AUTH_APP_TEST_URL=http://localhost:3147 NOTE_MOVE_PROBE_OUT=/tmp/note-move.json npm run probe:note-move
```

- 場面ごとの `成功/試行` と失敗の理由が標準エラーに、全体の JSON が標準出力（と `NOTE_MOVE_PROBE_OUT`）に出る。10場面で6〜8分かかる。`NOTE_MOVE_PROBE_SCENARIOS=solo,share-then-move` で絞れる。
- [note-move-baseline.json](note-move-baseline.json) の下限を下回った場面があれば exit 1、数えられなかった場面がある・計測そのものが動かなかったときは exit 3、場面名などの指定の誤りは exit 2。exit 3 と 2 は悪化ではないので、直して測り直す。
- 下限は片道 80ms で測った値。`NOTE_MOVE_PROBE_LATENCY_MS` を変えた結果は下限と比べない（exit 3）。
- 計測は「基準を上回りました」も出す。`after-peer-moved-same-note` と `same-note-contention` は掴むタイミングで回ごとにぶれるので、上回っただけでは下限を引き上げない。引き上げるのは、原因を直した PR だけ。
- 1回下回ったら、その場面だけもう1回測る。2回続けて下回ったら悪化として扱う（タイミングに依存する場面があるため）。
- 失敗の理由は、本人の接続を流れたメッセージから1つに決めている。

| 理由                     | 意味                                                         |
| ------------------------ | ------------------------------------------------------------ |
| `never-started`          | 掴んだのに、移動の開始を送っていない（画面側で無視している） |
| `client-cancelled`       | 通知を受けた本人側が、自分から移動を取り消した               |
| `server-rejected`        | RoomDO が移動を断った（理由の文面つき）                      |
| `server-expired` など    | 移動の期限切れ・結果不明・エラー応答                         |
| `overwritten-by-peer`    | 同じ付箋を同時に動かし、相手の位置に決まった                 |
| `diverged`               | 本人の画面と相手の画面で位置が違う                           |
| `accepted-but-displaced` | 保存は成功したが、離した位置と違う                           |

### 本番で数える

まだ無い。本番の失敗の頻度は分かっていない（#1401）。上の計測は「この場面で失敗するか」は数えられるが、「利用者が実際にどの場面にどれだけ当たるか」は数えられない。

## 原因の台帳

2026-11-27 の計測（develop `d2b6d41a`、片道 80ms）。状態が `open` の行が、次に直す候補。`→` の右は直した後の計測。

| ID | 場面（計測の場面名）                                                               | 起きること                                                           | 原因                                                                                                                                                    | 計測        | 状態           |
| -- | ---------------------------------------------------------------------------------- | -------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------- | -------------- |
| M1 | 共有ステップでマイ付箋をボードへ置き、直後に動かす（`share-then-move`）            | 掴めない。知らせも出ない                                             | 共有の応答を待つ間、ボードのすべての共有付箋の移動開始を止めている。置いた付箋自身も、応答が返るまで移動を受け付けない                                  | 0/3 → 13/13 | fixed（#1399） |
| M2 | 掴んでいる最中に時間切れになる（`timer-ends-while-dragging`）                      | 付箋が元の位置へ戻る。離し終えて未送信の移動も捨てる。知らせも出ない | 時間切れの通知を受けた本人側が移動を取り消す。RoomDO は時間切れの後も移動を受け付けるのに、画面側だけが止めている                                       | 0/4 → 4/4   | fixed（#1399） |
| M3 | 相手が動かし終えた直後の同じ付箋を動かす（`after-peer-moved-same-note`）           | 「もう一度操作してください」と出て、相手の位置へ戻る                 | 相手の確定が届く前に掴むと、本人が持つ付箋の版が古く、RoomDO が移動の開始を断る。届いた後でも、掴んでいる途中に届けば本人側が取り消す                   | 0〜5/10     | open（#1400）  |
| M4 | 2人が同時に同じ付箋を掴む（`same-note-contention`）                                | 片方の移動が捨てられる                                               | 先に始めた人が付箋を占有し、後の人の開始を断る。同時に動かせば片方が負けるのは避けられないので、下限は 50% 前後。負けた側への見せ方は M3 と一緒に見直す | 7/14        | 設計どおり     |
| M5 | 続けて動かしている間に、再接続・ステップの移動・別の付箋の競合が起きる（場面なし） | 離し終えていた移動まで、まとめて元へ戻る                             | 未送信の移動を1件ずつではなく列ごと捨てる。コードを読んで見つけた経路で、計測の場面はまだ無い                                                           | 未計測      | open（#1400）  |
| M6 | （本番）                                                                           | 失敗が起きても、誰にも分からない                                     | 移動の拒否・取り消しをどこにも記録していない                                                                                                            | —           | open（#1401）  |

1人で動かす場面（`solo`・`select-then-drag`・`double-click-then-drag`）、2人が別々の付箋を同時に動かす場面（`parallel-different-notes`・`queued-while-peer-moves`・`map-parallel`）は、計測した範囲では全部成功した。

## ループでの回し方

決まりは [README](README.md) と各指示書が正本。ここは移動に関わる部分の要約。

- **patrol（数える）**：移動に関わるコードが前回の巡回から変わっていたら、旅を歩く前に計測スクリプトを回す。下限を2回続けて下回った場面は S2 の所見（`loop:ux`）にする。計測に無い場面で移動の失敗を見つけたら、再現手順を所見に書く。
- **build（直す）**：移動に関わるコードを変える PR は、マージ前に計測スクリプトを回し、場面ごとの数字を PR に書く。下限を下回る変更はマージしない。台帳の原因を直したら、同じ PR で下限を引き上げ、台帳の行を `fixed（PR番号）` にする。新しい失敗の場面を直すときは、先に計測の場面を足して失敗を数字で確かめる。
- **replan（並べる）**：台帳の `open` の行に対応する Issue が待ち行列に無ければ、`loop:ready` に戻す。移動の失敗は「現状の使いにくさ」の中で先に並べる。
- **下限は下げない**：下げないと通らない変更は、移動を悪くしている。計測の誤りで下げるときは、理由を PR に書く。

### 場面を足すとき

`scripts/loop/note-move-probe.mts` の `scenarios` に1件足し、同じ PR で `note-move-baseline.json` に下限（直す前の実測）を足す。場面は「利用者が実際にやる操作」を1つだけ表す。掴む対象が別の付箋の下に隠れた回は自動で数から外れる。
