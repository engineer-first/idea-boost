# Issue 操作と自動化の改善案

PR #339 のレビューに伴う提案。以下は未実装で、[現行運用](issue-management.md)を変更するものではない。
人が「開始」「依頼」「確認済み」を一度示せば、その意図に付随する担当者・状態・リンクの更新をまとめる。

## 優先して試す案

| 優先 | 人の操作・契機                                                 | まとめて行う処理                                               | 状態変更の条件                                                                                        |
| ---- | -------------------------------------------------------------- | -------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| 1    | 「#340 を始める」または開始用 CLI                              | 自分を担当者に設定、Issue 番号付きブランチを作成、Issue を開く | `着手可能` → `作業中`。未整理なら先に内容・完了条件を表示する。他の担当者は上書きしない               |
| 1    | PR のレビュー依頼                                              | 直接対応する Issue を `レビュー中` にする                      | 今回の PR の条件を維持。対象 Issue と変更しなかった理由を Actions Summary に表示する                  |
| 1    | Project の「自分の作業」「レビュー待ち」「今スプリント」を開く | 保存ビューで担当・状態・Milestone を絞り、必要な項目をすぐ表示 | 状態の変更は不要。壁打ち用ビューは PBI・相談・Spike を中心にする                                      |
| 2    | PR を Draft に戻す                                             | 自動でレビュー中にした Issue を `作業中` に戻す                | 単一 PR、実行者の権限、自動更新の記録が一致する場合だけ。手動で移した状態は戻さない                   |
| 2    | 単一 Task / Bug の PR がマージされる                           | 明示的に自動完了を選んだ Issue を `完了` にする                | 子 Issue なし、追加 PR なし、完了条件がマージで満たされるものだけ。PBI・DemoGoal は人が成果を確認する |
| 3    | PBI の子 Task がすべて完了                                     | PBI を「成果確認待ち」ビューに出し、確認項目とデモ手順を提示   | PBI は自動完了にしない。子 Task の完了は受け入れ条件の成立とは限らない                                |

開始操作は最初は既存のスキルまたは CLI にまとめる。専用画面を作る前に、一操作で担当・ブランチ・状態が揃う効果を確かめる。
Issue 作成時は担当者にまだ作業開始の意思がないこともあるため、担当者が付いたことだけで `作業中` にはしない。

GitHub Projects の標準機能で、新規追加時の初期状態、状態変更に伴う Issue クローズ、自動追加・アーカイブを扱える。
これらは [組み込み自動化](https://docs.github.com/en/issues/planning-and-tracking-with-projects/automating-your-project/using-the-built-in-automations)を使い、独自処理を増やさない。
保存ビューの操作は [ビューの管理](https://docs.github.com/en/issues/planning-and-tracking-with-projects/customizing-views-in-your-project/managing-your-views)を参照する。

## 手入力と迷いを減らす案

- **親から作る**: PBI から Task / DemoGoal を作る操作で、親子関係・関連リンクを設定し、Milestone は親の値を初期候補にする。親が未割当なら勝手に現在のスプリントへ入れない。
- **状態名を操作に寄せる**: エージェントへ「#340 を始める」「レビューを依頼」「確認できたので完了」「今回は見送る」と依頼できるようにする。Issue と変更内容を短く示し、同じ情報を二度入力させない。
- **停滞は一覧で見せる**: 長く更新されていない作業、担当なし、PR がマージ済みでも成果確認が残る Issue を一覧にする。経過日数だけで状態を変えず、通知は新しい停滞や対応が必要な変化に絞る。
- **ホワイトボードから直接開く**: 付箋に Issue 番号と URL の QR コードを付ける。写真から読み取った配置は更新候補として提示し、曖昧な文字から GitHub の状態を確定しない。
- **作成の途中から再開**: PBI / DemoGoal 作成の各段階で URL を記録し、通信失敗時には既存 Issue への Project 登録・リンク設定から再開する。現状の作成スクリプトは再実行で重複し得るため、次の改善候補とする。

## 自動更新に共通して必要なこと

- 自動化ごとに「対象の Issue Type」「変更前の状態」「契機」「変更先」を限定する。`見送り` と `完了` を同じ close イベントから推測しない。
- 戻す操作を実装する前に、直前の自動更新と元の状態を記録する。手動更新後に遅れて届いたイベントで状態を上書きしない。
- Issue 単位で更新を直列化し、実行直前に状態・PR の対応関係を再取得する。同じイベントを再実行しても追加の変更が起きないようにする。
- PR 本文のマーカーやコメント本文だけを権限として扱わず、実行者の権限を確認する。
- 「更新した対象・理由・前後の状態」「スキップ理由」を実行結果から追えるようにする。手動で戻す手段も残す。

まず優先 1 を整え、状態の手直しが何回減ったか、誤更新やスキップが何件あったかを1スプリント確認する。
その結果から Draft 復帰と Task / Bug の自動完了を追加する順序がよい。
