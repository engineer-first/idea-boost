# 1-1から3-5まで見せるデモ台本とデータ評価

## 結論

**全14ステップを同じルームで順番に進める、約8分の通しデモを基本にする。** 共通操作は課題整理で説明し、問いの作成ではHMWテンプレート、アイデアでは発想支援と2軸評価を中心に見せる。

現在のデータでも全ステップを完走できる。ただし、説明が自然につながり、繰り返し同じ調子で実演できるデータとしては改善が必要。主な不足は、グループ化前の配置、HMW以降の投票先の安定性、アイデアを比較する根拠。枚数は各フェーズ5枚で十分で、まず内容と配置を整える。

この文書は実装済みの操作に基づく台本と、未実装のデータ改善案を分けて記載する。今回の資料追加で、稼働中のルームや投入データは変更していない。8分は配分の目安で、説明しながらの実測値ではない。

## 見せ方の方針

- 全体を「困りごとを集める → 解くべき問いに変える → 作るものを決める」という1本の話にする。
- すべてのステップに入り、必要な操作を実行する。後半で省略するのは重複した説明であり、共有・投票・採用の操作ではない。
- 通しデモ中は「見せ場へ移動」を使わない。これは新しいルームを作るため、直前に決めた内容の引継ぎを見せられなくなる。
- 個人ワーク・共有・ステルス投票は最初の1回で説明する。2回目からは「先ほどと同じ流れで共有します」の一言で進む。
- 課題、HMW、アイデアを決定するときは、毎回「なぜこれを選ぶか」を一言添える。最高得点が自動的に採用されるとは説明しない。
- アプリの「進め方」「考えるヒント」は見せる。説明者用の「デモ操作」パネルは合図を出したら折り畳む。
- 冒頭で「今回は私が1人分を操作し、残り4人は用意したデモ参加者です」と伝える。5人がライブで操作しているようには説明しない。
- 実際のワークでは考える・話す時間を取るが、デモでは準備済みの内容を使って進める。タイマーは役割だけ紹介し、満了を待たない。

## 準備

1. [READMEの起動手順](../README.md#1人で5人チームを実演するローカルデモ)に従い `npm run demo` を実行する。
2. `/demo` で「最初から」を選ぶ。デモ用ホストとして入室する。
3. 下記のHMWとアイデアの文言を、すぐ貼り付けられるよう手元に置く。
4. 1-1のサンプル付箋は編集して使う。2-1と3-1はテンプレート・ヒントから自分の付箋を1枚作る。
5. 発表前に別の新しいデモルームで一度練習する。やり直しは新ルームになるため、本番の説明中は通常の「次へ」で進む。

### 一貫して採用する3つの内容

| 成果物   | 今のデータで使う文言                                       | 選ぶ理由                                                                 |
| -------- | ---------------------------------------------------------- | ------------------------------------------------------------------------ |
| 課題     | 空きコマに一緒に勉強する仲間が見つからない                 | 学生チーム自身に身近で、小さなサービスとして試せる                       |
| HMW      | どうすれば、空きコマに気軽に学び合う仲間と出会えるだろう？ | 特定の機能に決めつけず、仲間探し・声かけ・短時間の交流へ発想を広げられる |
| アイデア | 空きコマ勉強マッチ：今いる場所と学びたい科目で仲間を探す   | 空き時間に学び合うという課題・問いとのつながりが説明しやすい             |

HMWは「How Might We」の略で、ここでは「どうすれば私たちは〜できるだろう？」という、解決策を考えるための問いを指す。

## 約8分の通し台本

### 導入：20秒

> 「ハッカソンで集まった5人が、何を作るか決める場面です。Idea Boostは、デザインスプリントの考え方に沿って、課題を整理し、問いに変え、作るアイデアを決めるところまで案内します。今回は私が1人分を操作し、他4人はデモ用のデータで再現します。」

### フェーズ1：課題整理（2分30秒）

| ステップ           | 目安 | 見せる操作                                                                             | 話す内容                                                                                                                                       |
| ------------------ | ---- | -------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| **1-1 自分の課題** | 30秒 | 5人のメンバー、進め方とタイマーを示す。自分のサンプル付箋を一度編集する                | 「まず全員が個人で考えます。この付箋は自分にだけ見えます。何を書くか、どのくらい考えるかも画面が案内します。今回は準備済みなので次へ進みます」 |
| **1-2 課題共有**   | 25秒 | 自分の付箋を共有へドラッグ。「他4人が共有する」を押し、共有4/4を確認してパネルを閉じる | 「共有すると初めて他の人に見えます。仲間探し、質問相手、学食など、5人の異なる困りごとが集まりました」                                          |
| **1-3 グループ化** | 35秒 | 学習関連の3枚を近づけ、枠の名前を「学び合う相手探し」にする                            | 「似た困りごとをまとめると、複数の人に共通するテーマが見えてきます。この3枚は、学び合う相手との接点が足りない課題です」                        |
| **1-4 投票**       | 35秒 | 自分の主観1票・客観3票を投じる。他4人の投票を合図し、投票4/4を確認する                 | 「赤は自分が取り組みたいもの、青は課題の大きさなどを考えて選びます。投票中は他の人の票が見えないので、先に投じた人に引っ張られず選べます」     |
| **1-5 課題決定**   | 25秒 | 結果を表示。上記の課題を採用して次へ                                                   | 「全員の票をここで確認します。票を参考に、今回は自分たちにも身近な『空きコマの勉強仲間』を課題にします。最後に選ぶのはチームです」             |

用意された固定座標のまま5枚を共有すると、同じグループ枠に入る。1-3でその状態になった場合は先に学食と締切の2枚を離し、学習関連の3枚を残して名前を付ける。枠が分かれない場合は、付箋同士をもう少し離す。この余分な操作を減らす改善は後述する。

投票対象はグループ名ではなく個々の付箋。主観票の5ポイント・客観票の1ポイントという集計方法は、質問があれば補足する。最初から配点計算を細かく説明する必要はない。

### フェーズ2：問いの作成（1分30秒）

| ステップ                | 目安 | 見せる操作                                                                                    | 話す内容                                                                                                                                       |
| ----------------------- | ---- | --------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| **2-1 課題に対するHMW** | 40秒 | 引き継がれた課題を示す。「考えるヒント」の「もっと簡単に」から付箋を作り、上記のHMWに編集する | 「すぐに機能を決めず、課題を『どうすれば〜できるだろう？』という問いに変えます。書き出しのテンプレートがあるので、初めてでも考え始められます」 |
| **2-2 HMW共有**         | 15秒 | 自分のHMWを共有。他4人も共有させ、5枚を短く指す                                               | 「共有は先ほどと同じです。仲間を見つける、初対面でも質問しやすくする、誘う負担を減らす、といった切り口が出ました」                             |
| **2-3 投票**            | 15秒 | 自分の4票と他4人の投票を完了させ、次へ                                                        | 「今回の課題に合い、いろいろな解決策を考えられる問いを選びます」                                                                               |
| **2-4 HMW決定**         | 20秒 | 上記のHMWを採用。課題との対応を示し、次へ                                                     | 「『気軽に学び合う仲間と出会うには？』を選びます。ここまでで、何を解決するかと、何を考えるかが揃いました」                                     |

ここでは付箋の非公開・ドラッグ方法・赤青の票の説明を繰り返さない。入力はテンプレートから1枚だけ作り、完成文を貼り付ければよい。

### フェーズ3：アイデア（3分15秒）

| ステップ                          | 目安 | 見せる操作                                                                                                                                                               | 話す内容                                                                                                                                                                                   |
| --------------------------------- | ---- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **3-1 アイデアを書き出す**        | 55秒 | 課題とHMWの引継ぎを示す。「考えるヒント」→「発想を広げる」のSCAMPERで「組み合わせる」を一例だけ紹介。「書き出し」の「もっと簡単に」から1枚作り、上記のアイデアに編集する | 「アイデアが出ないときにも、考える切り口があります。例えば『空き時間』と『学びたい科目』を組み合わせると、今一緒に勉強できる人を探す案になります」                                         |
| **3-2 共有・分類**                | 15秒 | 自分の案と他4人の案を共有し、2軸マップに並べる                                                                                                                           | 「共有は同じ操作です。ここからは、出た案を比較して、作るものを絞っていきます」                                                                                                             |
| **3-3 価値×実現のしやすさで評価** | 60秒 | 縦が今回の課題への価値、横が実現のしやすさと説明。マップ表示後、2枚を理由とともに動かす                                                                                  | 「案の良し悪しを同じ軸で話せます。例えば現在地を自動で追い続ける案は便利でも作るのが大変です。一方、場所を自分で選び、科目別に募集する形なら小さく試せそうです。今回はこの範囲で考えます」 |
| **3-4 ドット投票**                | 20秒 | 自分の4票と他4人の投票を完了させ、次へ                                                                                                                                   | 「価値と実現のしやすさを見たうえで投票します。デモでは、短い制作期間で試せることも判断材料にします」                                                                                       |
| **3-5 アイデアを決定**            | 45秒 | 結果を見て上記のアイデアを採用。課題・HMW・採用案を順に示す                                                                                                              | 「今回は『空きコマ勉強マッチ』を選びます。困っていることから問いを作り、その問いに答えるアイデアまで、一つの流れで決められました。最初は、場所と科目を選んで募集する小さな形で試します」   |

3-2の「分類」は、アイデアを2軸マップに配置する操作として見せる。フェーズ1の名前付きグループを再び作る機能としては説明しない。

発想法はSCAMPERの1例だけ見せる。オズボーン・逆転発想・他業界事例も選べることは、質問があれば補足する。ヒントがアイデアを自動生成したとは説明しない。

現在の2軸上の位置は固定のデモ配置であり、チームの評価結果を意味しない。上記の実現性に関する説明は、このデモで置く制作条件と実装範囲の仮定として話す。

### まとめ：25秒

> 「課題を出す、問いを作る、アイデアを選ぶ。この順番と、各場面の考え方が用意されています。アイデア出しに慣れていないチームでも、全員の意見を出しながら、何を作るか決めるところまで進められるアプリです。」

説明の対象はアプリ内の課題整理からアイデア決定まで。元のデザインスプリントに含まれるプロトタイプ作成・ユーザーテストを、このアプリで完了したとは説明しない。

## デモ用データは十分か

### 現状の判定

| 観点                              | 判定               | 理由・台本への影響                                                                                                               |
| --------------------------------- | ------------------ | -------------------------------------------------------------------------------------------------------------------------------- |
| 5人と各フェーズ5枚                | 十分               | 全員の意見が出ることと候補の比較を、画面を埋めすぎず示せる                                                                       |
| 課題→HMW→アイデアの意味のつながり | 推奨ルートなら十分 | ホストが上記の3つを選べばつながる。別の課題を採用しても他4人の文章は変わらない                                                   |
| 1-3のグループ化前の配置           | 改善必要           | 現在の配置では5枚が近接判定でつながり、全件で1グループになる。内容の似たものをまとめる前後の違いが見えにくい                     |
| 1-3の課題の種類                   | 最低限             | 学習関連3枚と、学食・締切の各1枚。1グループを作る説明はできるが、2テーマを比較するには後者のつながりが弱い                       |
| 2-1・3-1のホストの入力            | 台本で補える       | 連続進行では自分の付箋を作る必要がある。HMWテンプレートと発想ヒントを見せる機会として使い、完成文を用意する                      |
| 2・3フェーズの投票先              | 改善必要           | ホストが新規作成した付箋は固定デモIDを持たない。固定候補がない場合の代替選択がID順に依存し、同じ内容でも票の集まり方が変わり得る |
| 3-3の比較の根拠                   | 改善必要           | 5案はあるが、固定位置の理由や制作条件が用意されていない。説明者のその場の補足に依存する                                          |
| 発想支援の実演                    | 台本で補える       | 機能と候補は存在する。「組み合わせる」から具体案に至る説明を1つ決めれば見せられる                                                |
| 全ステップを案内する台本          | 旧版は不足         | 旧5分版はHMWの途中から3-3へ移動する。本文の通し台本で全14ステップを扱う                                                          |

### 実装を確認して分かったこと

- ステップ定義は `contracts/phase.ts` の **5 + 4 + 5 = 14ステップ**。
- `workers/demo-worker.demo.spec.ts` には、同じルームで3フェーズを自由入力・採用して完了する実WebSocketのテストがある。一方、グループの意味や台本に沿った候補への得票までは保証していない。
- `contracts/grouping.ts` の実関数 `calculateClusters` に `DEMO_NOTE_POSITIONS` を渡すと、5枚全体で1クラスターになることを確認した。横の隙間40px・縦の隙間30pxが、近接判定の60px以内に入るため。
- 投票先の代替処理は `workers/room/demo-room-do.ts` の `ORDER BY id` を使う。フェーズ2でホストが新しい1枚だけを作成・共有した場合を、現行の投票先配列で計算した。ホストが自分に4票すべてを投じても、IDが固定候補より前なら自分23点、後なら自分8点・別候補22点となる例がある。これは選択処理の計算確認であり、この調査で実ブラウザから新たに再現したものではない。
- ホストは最高得点以外も採用できるため、上記の挙動で進行が止まるわけではない。ただし「同じ筋書きで何度も説明する」ためのデータとしては、投票先の対応を安定させた方がよい。

## おすすめのデータ改善案（未実装）

### 1. 課題は5枚を維持し、3枚と2枚の2テーマにする

| 人     | 課題                                                   | まとめるテーマ   |
| ------ | ------------------------------------------------------ | ---------------- |
| ホスト | 空きコマに一緒に勉強する仲間が見つからない             | 学び合う相手探し |
| あおい | 友達の空き時間がわからず、声をかけるのをためらう       | 学び合う相手探し |
| けんた | 授業の質問を気軽にできる相手がほしい                   | 学び合う相手探し |
| みさき | 学食が混んでいて昼休みが足りない                       | 昼休みの混雑     |
| りく   | 空いている学食がわからず、店を探すうちに昼休みが終わる | 昼休みの混雑     |

共有直後は意図せず全件がつながらないよう配置し、1-3で少ないドラッグで2テーマに分けられるようにする。画面内に収まることと、グループ化する前後の違いを両方確認する。

### 2. HMWは現行の5枚を基本にし、ホストが1枚作る体験を残す

「出会い」「今参加できる人」「質問のしやすさ」「短時間の活用」「誘う負担」という切り口を短く比較できる。全候補を読み上げず、2つだけ紹介する。

説明者パネルには、ホストが作る完成文をコピーできる形で置くと進めやすい。自動でホストの付箋を作る方式より、テンプレートから考え始める機能を実演しやすい。

### 3. アイデアに、価値と実現のしやすさを説明する理由を用意する

デモの前提を「学生5人・週末のハッカソンで、まず試せるWebアプリを作る」と置く。以下はデモ用の仮説であり、実際の開発見積もりやユーザー調査の結果ではない。

| 案                             | 文言・範囲の案                           | 比較するときの理由                                                                       |
| ------------------------------ | ---------------------------------------- | ---------------------------------------------------------------------------------------- |
| 空きコマ勉強マッチ（採用候補） | 科目・空き時間の募集にワンタップで参加   | 学び合う相手探しに直接つながり、まず募集と参加だけで試せる。位置情報の自動追跡は含めない |
| キャンパスの勉強マップ         | 今いる場所と参加歓迎の状態をマップで共有 | 近くの人が見つかる一方、位置情報や更新の扱いが増える                                     |
| 15分質問カフェ                 | 短い質問から学び合える募集ボード         | 参加のハードルは低いが、継続して勉強する仲間探しには一歩足りない                         |
| 科目別の匿名質問箱             | 匿名で質問を投稿し、回答を集める         | 質問には役立つが、空きコマに人と出会う価値は相対的に低い                                 |
| 空き時間カレンダー共有         | 既存の友達と空き時間を合わせる           | 既存の友達とは会いやすくなるが、新しい仲間との出会いは生まれにくい                       |

初期位置もこの理由に合わせる。3-3では2枚を動かして「議論して位置を変える」場面を残し、最初から評価が完成しているようには見せない。

### 4. 投票は内容・候補との対応を安定させる

- 新しく作ったホストの推奨文にも、意図したデモ候補の票が対応するようにする。
- 全票を採用候補に集めず、次点にも支持を残す。
- 新規ルームのランダムIDが変わっても、同じ推奨ルートでは同じ傾向になるようにする。
- 自由入力・推奨文の編集・推奨候補の未共有では、別候補へ黙って票を集めるのではなく、デモの扱いを明示する設計が必要。
- 投票はチームの判断材料として見せ、採用結果を強制する仕組みにはしない。

### 改善の優先順位

1. **投票先の対応と初期グループ配置**：繰り返し実演するときの不自然さをなくす。
2. **1-3の2テーマ化と3-3の比較理由**：整理・評価する意味を伝える。
3. **画面内の台本を全14ステップ向けに更新**：HMWテンプレート、発想支援、重複操作の短い案内を追加する。完成文を手元に置く負担も減らす。

## 通しリハーサルで確認すること

- 同じルームで1-1→1-5→2-1→2-4→3-1→3-5と進み、全14ステップを見せた。
- 1-3で意味の近い付箋をまとめる前後の違いが見えた。
- 2-1で課題の引継ぎとHMWテンプレート、3-1でHMWの引継ぎと発想支援を見せた。
- 2-2・2-3・3-2・3-4は共通操作を再解説せずに進めた。
- 全フェーズで自分の1枚と他4人の付箋を共有し、自分の4票と他4人の投票を完了した。
- 3-3で2案を理由付きで比較し、3-5で課題・問い・採用案のつながりを話せた。
- 画面内で台本やヒントが邪魔なときは折り畳み、説明対象が見えた。
- 実際に話しながら所要時間を測った。8分を超える場合もステップを飛ばさず、候補の読み上げと同じ操作の説明から削る。
