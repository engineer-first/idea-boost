# 設計判断の記録（ADR）

ADR（Architecture Decision Record）は、重要な設計を「どの前提・候補から、なぜ選んだか」と代償を残す記録。現在の構成は[構成概要](../architecture/overview.md)、実装時のルールは[開発規約](../development/conventions.md)、機能要求は[PRD](../prd.md)を参照する。

## 作る基準

構成、データの権威、境界、認可、永続化、主要依存など、後の変更を長く制約する選択を行うときに作る。採用を見直すときも記録する。

通常の機能追加や文言修正、既存方式に従った権限付与、進捗報告には増やさない。要求はPRD・詳細仕様、実行方法は運用文書、作業はIssueへ置く。

## 書き方と更新

1. [テンプレート](template.md)をコピーし、連番と短いkebab-case名で1件1判断、おおむね1ページにまとめる。
2. 提案は通常のPRでレビューし、採用時に状態を「採用」へ更新する。決定日と記録日を区別する。
3. 判断が変わったら新しいADRを作り、旧ADRに後継へのリンクと「後継あり」を示す。旧判断の背景を現在の説明で上書きしない。
4. 比較・調査の全文はarchiveまたはIssue / PRへ置き、ADRには要点と根拠を残す。現行の仕様・規約をコピーしない。

既存の判断を移す場合はその旨を明記し、確認できない決定日・理由は「不明」とする。記録した日を過去の決定日として扱わない。
