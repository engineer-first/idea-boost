# 0018: 同じ接続のWS操作を受信順に処理する

- 状態：提案
- 決定日：未確定
- 記録日：2026-10-16

## 背景

[0016](0016-account-participation-index.md)の参加確認は各WS操作でAccountDOへ問い合わせる。移動開始の問い合わせが遅れると、同じ接続で後から受信したpreview・commitが先に処理され、未登録の操作に対するunknownが返る。クライアントには「移動を確認できませんでした」と表示され、後から開始だけが成立してlockが残る。

参加確認の目的である、参加先の切り替え中や参加先が曖昧な状態での変更拒否は維持する。自分の付箋の表示は通信応答を待たずにポインターへ追従し、他の参加者の操作も継続できる必要がある。

## 候補と決定

RoomDOのWS入口で、同じ接続から届いた要求を受信順に処理する。参加確認を含む前の要求の完了後に次を処理し、実行時点で期限・在籍・参加先・対象の版を検査する。例外は要求元へ返し、後続要求は継続する。別接続の要求、退出、タイマー等は並行して進む。

処理中のPromiseだけを接続ごとのWeakMapに保持し、最後の要求が終わったら除去する。共有状態・lock・結果はSQLに残し、接続の復帰や結果照会は既存の仕組みを使う。

ルーム全体を`blockConcurrencyWhile`で止めると他の参加者まで外部通信を待つため採らない。許可結果のキャッシュも参加先切り替えを見落とすため採らない。クライアントで開始ACKを待つだけでは、キャンセル・確定・結果照会など他の要求の追い越しを防げないため、順序は受信側で保証する。

## 影響と見直す条件

現在のクライアントとWS形式を保ったまま、高速ドラッグの開始・途中表示・確定・キャンセル・結果照会の順序を守れる。同じ接続では遅い要求が後続を待たせるため、継続的に通信が遅い場合の待ち時間には限界がある。参加確認や成果保存の遅延が継続する場合は、それぞれのI/Oを計測し、一時的なカーソル・previewの集約を別途検討する。
