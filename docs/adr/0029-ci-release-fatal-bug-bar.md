# ADR 0029: CIはリリース時の致命的な不具合を止めることを基準にし、PRでは変更範囲に応じて検査を絞る

## Context

開発の大半はAIエージェントが行い、PRを短い間隔で出す。PRごとのCIは5つのジョブ（lint・test・browser・build・smoke）を毎回すべて回し、約11〜14分かかっていた。最も遅いbrowser（主にStorybookを配信して実ブラウザで検査する）だけで約11分かかり、そのうち3〜7分はChromiumのOS依存をaptから取得する時間だった。PR Previewは `name: CI` のworkflowの成功を待って公開するため、browserの完了を待ち、browserが落ちると公開されなかった。

2026-11-01〜11-19の300回のCIで失敗は42回あり、同じコミットの再実行で通った失敗はbrowser 6回・test 2回・smoke 1回だった。browserには、色・影・アニメーションの秒数・固定のpx寸法・別画面との位置の完全一致を確かめる検査が多く、意図した見た目の変更のたびに直す必要があった。マージ済みの直近40件のPRのうち24件は画面のコードに触れていなかった。対応端末はPC・iPad・スマホ縦（幅360以上）で、スマホ専用の画面はまだない。それでもbrowserは毎回、幅320〜390の検査も回していた。

本番への公開は `/release` スキルからだけ行い、公開前の品質ゲートにbrowserはなかった。`/api/health` はWorkerの起動だけを確かめる設計で、公開後の確認もこれだけだった。人が報告した深刻な不具合は、工程の進行・戻し・投票後の除外・付箋の確定が工程をまたいで壊れるものが中心だった。一方、RoomDOのテストは工程ごとに途中の工程へ直接移ってから検査しており、工程をつないで進めたときの不具合を検知できなかった。

## Decision

CIの基準を「リリース時に致命的な不具合がないこと」にする。致命的な不具合は、ルームに入れない、工程を進められない、付箋・投票・成果が消える、他人の非公開の内容が見える、公開後に画面やAPIが動かない、の5つとする。PRのCIは、細部を縛らず速く結果を返すことを優先する。致命的な不具合は、developへのマージ後とリリース前のゲートで止める。ただし、developに入った時点で取り返しがつかないもの（マージ済みmigrationの書き換えとmigration番号、認可・可視性、型と依存方向）は、従来どおりPRごとに止める。

検査は回すタイミングで3段に分ける。

- PRごと：lint・型・unit・build（Preview用bundleを実際に起動する確認を含む）を毎回回す。Worker系のテストとbrowserは、関係する変更があるときだけ回す。判定できない場所の変更は回す側に倒す。
- developへのマージ後：browser・Worker系のテスト・本番構成のsmokeを毎回回し、PRで省いた変更の影響を拾う。
- リリース前と公開後：ゲートでunit・Workerのテスト・本番構成のsmokeを回し、公開後は読み取りだけで画面とAPIを確かめる。browserはゲートに入れない。同じコードをdevelopへのマージ後に検査済みで、不安定な失敗でリリースを止めないためである。

工程の進行が壊れる不具合と非公開の内容の漏れは、RoomDOの層で2人が全14工程をUIと同じWebSocketのメッセージだけで進める統合テストで止める。実ブラウザの検査より速く安定しており、PR・develop・リリース前のすべてで回せるためである。browserの検査は、重なり・画面外・スクロール・フォーカス・キーボード到達など、実ブラウザでしか分からない不具合に限る。色・アニメーション・固定寸法の一致はCIで縛らず、storiesと表示レビューで確かめる。スマホ幅の検査は、スマホ縦の画面を変えるPRに `mobile` ラベルを付けたとき（または手動実行で指定したとき）だけ回す。

検査を省くときも、workflowは起動したままにする。変更範囲で決める検査はジョブの中でステップを飛ばし、イベントの種類だけで決まるsmokeはジョブごとskippedにする（どちらも成功扱い）。workflowを起動しないと必須チェックがpendingのまま残り、`name: CI` の成功を待つPR Previewも止まるためである。browserは `name: CI` とは別のworkflowに置き、PR Previewが待たないようにする。必須チェックの名前とリポジトリのRulesetsは変えない。

CIで縛らない分は、エージェントへの指示で担保する。push前に変更範囲に必要な検査を手元で通すこと、スマホ縦の画面を変えるPRには `mobile` ラベルを付けること、browserテストに見た目だけの検査を書かないことを、エージェントの指示とスキルに書く。

### 本ADRで決定しないこと

検査を回すかを決めるパスの一覧は [scripts/ci-scope.mts](../../scripts/ci-scope.mts) へ、検査ごとの回すタイミングの表とテストの書き方は [テスト方針](../development/testing.md) へ委譲する。スマホ幅の境界（600px未満）と幅360未満を検査しない扱いは [tests/browser/viewports.ts](../../tests/browser/viewports.ts) とテスト方針へ委譲する。エージェントへの指示の文面は [AGENTS.md](../../AGENTS.md) と各スキルへ委譲する。リリースの手順は `/release` スキルと [リリース運用](../operations/release.md) へ委譲し、このADRでは変えない。

## Consequences

- 良い影響：PRのCIは約6分で終わり、PR Previewはbrowserを待たずに公開される。browserは、Chromiumの準備をaptに頼らないことと見た目だけの検査を外したことで、約14分から約6分半になった。画面に触れないPRではbrowserを回さない。工程の進行と非公開の漏れは、1秒未満の統合テストで、PR・develop・リリース前のすべてで止められる。
- 悪い影響（受け入れるリスク）：画面のコードに触れないPRがbrowserで検知できる不具合を入れた場合、developへのマージ後に初めて検知する。その場合はそのPRの作業者が直す。リリース前のゲートはdevelopのbrowserの結果を見ないため、developでbrowserが落ちたままでも公開できる。スマホ幅の不具合は、`mobile` ラベルの付け忘れでCIを通る。色・影・アニメーション・固定寸法の変化はCIで検知しない。ライト表示の固定や付箋の見た目など、過去に人が報告した見た目の不具合の再発は、storiesと表示レビューに頼る。
- 悪い影響：全14工程の統合テストは1本で1400行を超え、工程の仕様を変えるたびに直す必要がある。パスの判定一覧は、新しいディレクトリを足すときに見直す必要がある（一覧にない場所は両方回すので、取りこぼしではなく待ち時間の増加として表れる）。画面に関わるPRでは、`mobile` 以外のラベルを付けてもbrowserが再実行される。
- 中立：browserは、色・固定のpx寸法・別の工程との位置の完全一致だけを確かめる検査をテスト単位で外し、CIでの検査の実行が約445秒から約327秒（手元では約230秒から約150秒）になった。間引いた主な目的は、意図した見た目の変更で落ちる検査をなくすことである。全14工程を巡回する重なりの検査は、工程ごとに画面の部品が違うため代表の工程に絞らなかった。unitテストとlintの各ステップは減らしていない。unitは全体で約3分、lintはPRの待ち時間の律速ではなく、失敗もほぼコード変更による正当なものだったためである。
- 保証しない範囲：実アプリ（Next.js・api-worker・RoomDO・WebSocket）を実ブラウザで操作する流れは、ホーム・完了一覧の移動を除きCIで検査していない。ルーム画面が200を返してもクライアント側の例外で操作できない不具合や、UIとWebSocketの配線の誤りは、リリース前に検知できない。既存の実アプリE2E（`scripts/preview-smoke-browser.mts`）は今のUIに合わず、どのCIからも呼ばれていない。
- 見直す条件：
  - 画面に触れないPRが原因のbrowserの失敗が、developへのマージ後に繰り返し起きるとき。
  - 見た目の不具合、またはクライアント側の例外が、本番で利用者の作業を止めたとき。実アプリE2Eを短いシナリオで作り直し、リリース前のゲートに入れるかを判断する。
  - スマホ縦専用の画面を作るとき。スマホ幅の検査を常に回すかを見直す。
  - PR Previewが `name: CI` の成功を待たなくなったとき、または必須チェックの名前を変えるとき。

## Alternatives Considered

- workflowの `paths` で起動自体を省く案：必須チェックがpendingのまま残り、PR Previewも止まるため採用しなかった。
- smokeジョブを消し、Rulesetsの必須チェックから外す案：リポジトリ設定の変更が要るため、PRではジョブを飛ばしてskipped（成功扱い）にする形にした。
- browserをリリース前のゲートだけで回す案：不具合を入れたPRの特定が遅れ、不安定な失敗がリリースを止めるため、developへのマージ後と画面に関わるPRで回す形にした。
- `mobile` 以外のラベルではbrowserのジョブをskippedにする案：同じコミットのbrowserの結果を成功扱いのskippedで上書きし、先に落ちていた結果を隠すため採用しなかった。
- 実アプリE2Eを修復して、この判断と同時にリリース前のゲートへ入れる案：今のUIに合わない箇所が多く、固定の文言や演出に依存しているため、修復してもUIの変更のたびに壊れてリリースを止める。工程の進行は統合テストで止められるため、見直す条件に回した。
- AIが提案し、採用しなかった案：Storybookのbuildでスキーマ図・依存図の生成を省く（build全体で約11秒で、図の出力先がないとbuildが失敗する）、lintの各ステップを変更範囲で絞る（どれも1秒前後で律速ではない）、Chromaticの起動を絞る（マージを止めない）、browserの並列数を2に下げる（不安定さの原因と確認できていない）、browserの30ファイルをファイルごと消す（進行・到達性の検査が混在していたため、テスト単位で間引いた）、`/api/health` にSESSION_SECRETとD1の確認を足す（起動確認とPR Previewの起動待ちに使う設計のため、画面の描画確認を別に足した）、unitの見た目だけのテストやscriptsのテストを分ける・消す、Markdownの整形検査をCIから外す。
- 画像比較（ChromaticのUI Tests）を戻して見た目を検査する案：意図した変更のたびに差分の承認が必要になり、承認作業が律速になるため採用しなかった。
