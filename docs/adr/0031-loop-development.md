# ADR 0031: 完成台帳を置き、エージェントの短いループで開発を進める

## Context

開発の大半はAIエージェントが行うが、エージェントは人が起動したときだけ動く。人がIssueを選び、エージェントを起こし、PRを読んでマージするまで、文言の修正のような小さな改善も止まる。

PRDと進行仕様は詳しい一方、「いま何が確かに動き、何が足りないか」を1か所で読めない。完成の判断はIssueとPBIに散らばり、エージェントは目の前のIssueを閉じられても、完成への距離を測れない。作ったセッション自身が動作を確かめるため、確認も甘くなりやすい。

リポジトリは公開で、5人前後のチームが開発する。優先順はProjectの共通の手動順で決め（ADR 0024）、Issueの種類・状態・Milestoneは既存の自動化が動かす。オーナーが個人で開発する別のリポジトリでは、2026-11-21から、完成台帳と役割ごとのループでエージェントが自律的に開発を進めている。

## Decision

PRDのうち「壊れていたら困る」振る舞いと、その確かめ方を、機械可読の完成台帳に置く。エージェントは「1周1仕事」の短いループで、台帳の未確認・未達を確かめて埋め、人が任せた仕事を進める。会話の記憶に頼らず、状態はGitHubとリポジトリに置き、周回ごとにcontextを捨てる。ループは修理・完成・取り込み・巡回・庭仕事・再計画に分け、やることが無い周回では起動しない。

台帳は前へ進む仕事の一覧にしない。新しく作る仕事は、人がループに任せると決めたIssueだけにする。台帳を北極星にすると、既存の機能を写した項目が埋まった後に、ループが好みの改善を回し続けるためである。台帳の受け入れ条件を変えるのは人とし、ループは変更の提案までにする。作業者が条件を緩めて完了にする抜け道を塞ぐためである。

作る周回と確かめる周回を分ける。巡回は作った周回とは別のcontextで利用者の旅を歩き、取り込みはコードを書かずに判定だけを行う。作った本人の甘い採点を避けるためである。

ループはチームのIssue運用・PR運用・リリース運用の上で回し、置き換えない。人が作ったIssueと人のPRには、ループが自分から触らない。

### 本ADRで決定しないこと

エージェントがdevelopへマージする範囲と段階導入はADR 0032へ委譲する。ループごとの起動間隔・判定条件・上限・ラベルはループの仕様と判定スクリプトへ、各周回の手順はループの指示書へ、台帳の項目と受け入れ条件は台帳へ、巡回の旅と重大度は巡回の基準へ委譲する。委譲先へのリンクはReferencesに置く。

## Consequences

- 良い影響：人が起動しなくても、台帳の未確認、巡回の所見、developのCI失敗、Renovateのmajorが処理される。完成までの距離が台帳のpass数で読める。巡回が作った人とは別のcontextで画面を歩く。
- 悪い影響：ループが作るIssue・PR・コメントがGitHubに増え、チームが読む量が増える。巡回の新規Issueを1回3件、S3をIssueにしない上限で抑える。
- 悪い影響：エージェントの利用料、Actionsの実行時間、CodeRabbitの枠が周回に比例して増える。Orcaは周回ごとにworktreeを作って消さず、依存の導入で1回あたり約1.7GBを使うため、庭仕事が片付ける。
- 中立：ループを止めても、GitHubに残るのはラベルとIssueだけで、人の運用はそのまま続く。
- 保証しない範囲：巡回はローカルの開発環境で歩き、本番の画面は歩かない。巡回の合格は、初学者チームが迷わず決められることの証拠ではない。
- 根拠未確認：台帳の項目の選び方と6つのループの構成はAIの提案で、オーナーとチームの採用を確認していない。
- 見直す条件：
  - 2週間の試行で、ループのPRのうち人が手を入れずに残った割合が半分を下回ったとき。
  - 台帳の全項目がpassになったとき。前へ進む仕事の入れ方を見直す。
  - ループの記録や所見を、チームが読まなくなったとき。

## Alternatives Considered

- 台帳をPRDの完成の北極星にし、ループが差分を埋め続ける案（元にした個人リポジトリの方式）：IdeaBoostではPRDの多くが実装済みで、台帳が「確かめ直し」で早く埋まり、その後はループが好みの改善を回し続けるため採用しなかった。
- 待ち行列をリポジトリ内の1ファイルにする案：複数の周回が同時に書いて衝突し、更新のたびにPRが要るため、Issueとラベルにした。
