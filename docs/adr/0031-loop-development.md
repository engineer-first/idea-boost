# ADR 0031: 完成台帳を置き、エージェントのループがリスク段階に応じてdevelopへ取り込む

## Context

開発の大半はAIエージェントが行うが、エージェントは人が起動したときだけ動く。人がIssueを選び、エージェントを起こし、PRを読み、マージする。人の手が空かない間は、文言の修正のような小さな改善も止まる。

PRDと進行仕様は詳しい一方、「いま何ができていて、完成まで何が足りないか」を1か所で読めない。完成の判断はIssueとPBIに散らばり、エージェントは目の前のIssueを閉じられても完成への距離を測れない。また、作ったセッション自身が動作を確かめるため、確認が甘くなりやすい。

リポジトリは5人のチームで開発し、developへの取り込みにはPRと5つの必須チェック（lint・test・browser・build・smoke）が要る。承認の人数は0で、作者がマージできる。本番公開は明示呼び出し専用の `$release` スキルからだけ行う。オーナーが個人で開発する別のリポジトリでは、2026-11-21から、完成台帳と役割ごとのループでエージェントが自律的に開発を進めている。

## Decision

PRDの完成を機械可読の台帳（`docs/loop/completion.json`）に置き、エージェントが「1周1仕事」のループで台帳との差分を埋める。ループは修理・完成・取り込み・巡回・庭仕事・再計画の6つとし、Orca automationが起動する。起こすかどうかはGitHubの状態だけで判定し、やることが無い周回では起動しない。

取り込みの重さは、変更の取り返しのつかなさで分ける。戻せる変更（R0：文言・見た目・文書・テスト）と振る舞いの変更（R1）は、必須チェックとCodeRabbitのレビューが済み、R1では作った周回とは別のcontextの確認が合格したら、エージェントがdevelopへマージする。境界に触る変更（R2：認可・可視性・セッション・RoomDOの共有状態・`contracts/` の形・migration）は人がレビューしてマージする。PRD方針・チームの運用・課金と外部への連絡（R3）はエージェントが実装しない。

ループはチームのPR運用・Issue運用の上で回す。PRは通常のwrite-prスキルとテンプレートで作り、ループ専用のテンプレートや記録ファイルは作らない。ループが拾うのは `loop:*` ラベルが付き担当者のいないIssueだけとし、人の担当・人のPRには触らない。本番公開は従来どおり人が `$release` で行う。

チームの開発の流れを保ったまま、人が起動とマージを待たせる時間を減らせるためである。developへのマージ後の検査（ADR 0030）とDiscordへのマージ通知があるので、R0/R1の取り込みはチームが後から気づいて戻せる。

### 本ADRで決定しないこと

ループごとの起動間隔・判定条件・上限は `docs/loop/LOOPS.md` と `scripts/loop/precheck.mts` へ、各周回の手順は `docs/loop/prompts/` へ、台帳の item と受け入れ条件は `docs/loop/completion.json` へ、巡回の旅と重大度は `docs/loop/ux-rubric.md` へ委譲する。Issueの種類・Project状態・MilestoneはIssue運用、PR本文はwrite-prスキル、本番公開はリリース運用のまま変えない。

## Consequences

- 良い影響：人が起動しなくても、台帳の未達・巡回の所見・developのCI失敗・Renovateのmajorが処理される。完成までの距離が台帳のpass数で読める。巡回が作った人とは別のcontextで画面を歩くため、作った本人の確認に頼らない。
- 悪い影響（受け入れるリスク）：R0/R1の変更は人が読む前にdevelopへ入る。リスク段階の判定を誤ると、R2相当の変更がエージェントのマージで入る。取り込み側でも差分から段階を判定し直し、迷ったら上へ倒すが、判定の誤りを完全には防げない。ループのPR・コメント・マージはオーナーのGitHubアカウントの操作として表示される。
- 悪い影響：CodeRabbitの枠、Actionsの実行時間、エージェントの利用料がループの周回に比例して増える。開いたループのPRを2本までに絞り、1回の起動で扱う量に上限を置いて抑える。Orcaは周回ごとにworktreeを作り、消さないため、庭仕事が片付ける。
- 中立：ループを止めても、GitHubに残るのはラベルとIssueだけで、人の運用はそのまま続く。
- 保証しない範囲：巡回はローカルの開発環境で歩き、本番の画面は歩かない。巡回の合格は初学者チームが迷わず決められることの証拠ではなく、ユーザーテストで別に確かめる。
- 見直す条件：
  - エージェントがマージしたR0/R1の変更をrevertした件数が、2週間で3件を超えたとき。
  - チームの誰かの作業とループのPRが衝突し、どちらかを作り直した件数が繰り返されるとき。
  - CodeRabbitの枠不足で人のPRのレビューが待たされたとき。
  - 承認の必須化など、developのRulesetsを変えるとき。

## Alternatives Considered

- 別のリポジトリと同じく、developへ直接pushし定時に本番へ公開する案：developのRulesetsがPRと必須チェックを求め、チームがPRで差分を読む運用と衝突する。本番公開はイベントの前にチームが判断しているため、採用しなかった。
- すべてのループのPRを人がマージする案：人のマージ待ちが今と同じく律速になり、ループを置く目的が残らないため採用しなかった。
- 待ち行列をリポジトリ内の1ファイルにする案：複数の周回が同時に書いて衝突し、更新のたびにPRが要るため、Issueとラベルにした。
