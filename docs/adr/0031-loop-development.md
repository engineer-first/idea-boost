# ADR 0031: エージェントのループで改善から本番公開までを回し続ける

## Context

開発の大半はAIエージェントが行うが、エージェントは人が起動したときだけ動く。2026-11-24 は定例と野崎さんとのMTGの方針「新機能より先に現状の使いにくさを直す」に沿って、改善PRが一度に10本近くマージされたが、次の改善と本番公開は誰かが思い立つまで始まらない。作ったセッション自身が動作を確かめるため確認が甘くなりやすく、守るべき約束も Issue に散らばっている。

オーナーが個人で開発する kobe-student-hub では、2026-11-21 から、完成台帳と役割ごとのループでエージェントが自律的に開発し、本番へ1日2便で公開している。IdeaBoost は5人前後のチームが開発する公開リポジトリで、develop は PR と5つの必須チェックを求め、承認は0人、ループが動くオーナーのアカウントは admin である。本番は release ブランチへの昇格（Promote Release → Deploy）で、`release:operator` がその入口になっている。

2026-11-24 の初版（同じ番号の Proposed）は、ループを巡回（所見の Issue 化）だけに絞り、コードを書くループとマージは後の ADR に回していた。2026-11-25、オーナーは「どんどん改善して、どんどんリリースする」こと、チームの判断を理由に止めず、止まるのは権限が無くて進めないときだけにすることを求めた。

## Decision

エージェントのループで、改善 → develop へのマージ → 本番公開までを、人の起動なしに回し続ける。ループは Orca automation が起動し、run ごとに新しい worktree で1周1仕事を行い、状態は GitHub とリポジトリに置く。

- **改善**は、待ち行列の Issue を1件ずつ直す build と、画面を歩いて小さな改善を直す polish の2つで行う。待ち行列は replan が、MTG の方針・PRD・利用者の声・人の Issue・巡回の所見から整える。方針が未定の Issue は、ループが案を比べて選び、理由を PR に書いて進める。
- **develop へのマージ**は、人と同じく PR と必須チェックを通し、作った context とは別のサブエージェントのレビューで直すべき指摘が0のときに、ループが squash マージする。境界（contracts・workers・認可・migration）に触る変更は、認可の独立レビューを加える。develop の CI が赤のときは、何より先に mend が直す。
- **本番公開**は、毎日 12:40 と 20:40 の列車が `release:operator` で行う。オーナーはループからの公開を常時の公開意思として認め、release skill の公開前の確認はループの指示書で満たしたものとする。説明の書き方・品質ゲート・health・記録はこれまでの公開と同じ経路を通る。
- **確かめる目**として、巡回（patrol）が作った周回とは別の context でローカルの画面を歩き、所見を Issue にする。守る約束は完成台帳に置く。

ループは、担当者がオーナー以外の Issue、人の PR・ブランチに触らない。チームの誰でも、`loop:stop` ラベル1つで全ループを止められ、`loop:skip` で個別の Issue を外せる。課金・契約、ruleset・secret・environment・認証方式の変更、学外への連絡は行わず、`needs-human` に止まった場所を書く。

### 本ADRで決定しないこと

ループの一覧・起動条件・上限・ラベル・マージと列車の細則はループ開発の文書と判定スクリプトへ、各周回の手順は指示書へ、守る約束は完成台帳へ、旅・重大度・分かりやすさの原則は巡回の基準へ委譲する。委譲先へのリンクは References に置く。

## Consequences

- 良い影響：人が起動しなくても、改善が PR になってマージされ、1日2回本番に出る。作った人と別の目（レビューのサブエージェント、巡回）が入る。
- 良い影響：ループの成果はすべて PR・Issue・GitHub Release に残り、チームは通常のマージ通知と Release で追える。
- 悪い影響：チームの Issue の一部がループに拾われ、方針が未定のものもループが選んで実装する。選んだ理由を PR に書き、`loop:skip` と `loop:stop` で外せるようにする。結果が合わなければ人が次の Issue で直す。
- 悪い影響：admin のアカウントで動くため、ループの誤りや Issue に書かれた指示の注入を ruleset では止められない。書いた人が OWNER / MEMBER / COLLABORATOR でない指示に従わないこと、必須チェックと別 context のレビュー、境界の独立レビュー、列車の品質ゲートと health で抑える。
- 悪い影響：エージェントの利用料と worktree のディスク（1個約1.7GB）。precheck で仕事が無い周回を起こさず、`ib tidy` が終わった worktree を毎時片付ける。
- 中立：ループを止めても、GitHub に残るのはラベル・Issue・PR だけで、人の運用はそのまま続く。
- 保証しない範囲：巡回はローカルの PC 幅だけを歩き、本番・iPad・スマホは歩かない。ループの合格は、初学者チームが迷わず決められることの証拠ではない。
- 見直す条件：
  - ループがマージした変更が本番で P0 を起こしたとき。マージの決まりかリスク段階を厳しくする。
  - チームがループの PR を revert する、または `loop:stop` を付けることが続いたとき。拾う範囲と選び方を直す。
  - 巡回の所見のうち、見送りで閉じた割合が半分を超えたとき。巡回の基準を直す。

## Alternatives Considered

- 巡回だけから始め、コードを書くループとマージは後で決める案（2026-11-24 の初版）：admin のアカウントでの迂回マージや注入への懸念から一度は採ったが、改善とリリースが人の起動待ちのまま残り、オーナーの方針（どんどん改善し、どんどん公開する）に合わないため改めた。懸念は、必須チェック・別 context のレビュー・境界の独立レビュー・書いた人による指示の扱いで抑える。
- kobe-student-hub と同じく develop へ直接 push する案：develop の ruleset は PR を求め、チームも PR とマージ通知で変更を追っているため採らない。必須チェックは10分前後で終わり、PR を通しても1周の時間はほぼ変わらない。
- 変更があれば毎時公開する案：本番を学生が授業中に使うと、公開のたびにルームの接続が切り替わる。これまで人の公開が昼に集まっていたことに合わせ、昼と夜の2便にした。
- ループの PR に人の承認を求める案：承認待ちで止まり、オーナーの方針（チームの判断を理由に止めない）に反する。人はマージ通知と Release で事後に見て、合わなければ revert か Issue で直す。
