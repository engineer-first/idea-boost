# 0007: ルーム作成要求を削除後も保持する

- 状態：提案（[0008の後継提案](0008-room-creation-expiry.md)あり）
- 決定日：未決
- 記録日：2026-10-06

## 背景

ルーム作成はD1への予約とRoomDOの初期化にまたがる。応答喪失後の再送を新規作成として扱うと、同じ作成意図から複数のルームが生まれる。終了・解散・期限切れの後に要求対応を失うと、古い要求がルームを復活させる。

## 候補と決定

利用者とUUIDの要求IDをキーとして、正規化したルーム名、roomId、招待コード、pending/readyをD1に期限なしで保持する案を提案する。ルーム行とは削除連鎖を持たず、ルーム削除後は同IDへ410を返す。pendingの初期化済みDOが終了・解散・成果保持期限切れになった場合も、既知の終了として410を返し、結果不明の再試行を永久に続けない。名前の省略・空欄・空白だけは同じ入力として扱う。

有限期間だけの対応保持は、その後の再送を新規要求と区別できない。短期の対応表と長期の墓標に分ける方式も、墓標の最終削除後には同じ問題があるため、今回採らない。将来の期限契約が定まるまで対応行を自動削除しない。これは対応・墓標の保持期限であり、ルームを利用できる期限や成果の保存期間を延ばすものではない。回復で成立できるのは、対象DOが終了・解散・保存期限切れになる前までである。

RoomDOは初期状態・作成マーカー・成果投影outboxを同じローカルtransactionに保存する。再試行では外部投影だけ再開し、工程・参加者・ホストを初期化しない。ready後はDOの初期化を呼ばない。作成中のディレクトリ行は参加・閲覧に使えない。ブラウザは利用者ごとのsessionStorageに要求を保存してから送信し、結果不明時や再読み込み後も同じ要求で確認する。別作成の明示操作だけ新IDを発行する。

## 影響と見直す条件

途中失敗・応答喪失・同時送信が同じルームへ収束し、ルーム削除後も復活を防げる。要求IDは認可を代替せず、毎回認証した利用者のキーだけを参照する。

代償は要求数に比例するD1の永続増加と、ルーム名を含む対応記録の保持である。pendingは自動的に成功扱い・削除せず、同要求の再試行で回復する。sessionStorageが利用不能な場合は送信を止める。タブやブラウザ保存領域を失った場合、同じIDによるクライアント側の回復はできない。

保持期間・データ削除要求・孤立要求件数の運用が定まった時点で見直す。対応を削除する方式へ変える場合は、過去IDを新規作成せず拒否する仕組みと墓標の保持契約を同時に決める。
