# ADR 0029: ステップガイドの既読は本人×ステップ×案内の版で端末に残し、ルームをまたいで再表示しない

## Context

ステップガイドは、1-1・1-2・1-3・1-4・1-5・2-1・3-1・3-3に初めて入ったときに自動で開く。既読の記録は、タブを閉じると消える保存先に、ルーム×本人×ステップの単位で残していた。そのため、同じ本人でも、タブを開き直したときや、別のルームで2回目のワークショップに参加したときに、8ステップ分の案内がすべて再び開いていた。操作に慣れた人の作業の流れを遮ると報告されている。

既読の記録は、一度利用者の端末に書くと、後から形を変えた時点で全員が「未読」に戻る。そのため、記録の単位は後の変更を長く制約する。

一方、案内の原稿は今も頻繁に変わっている。2026-10-01〜11-16に原稿のファイルは6回変更された。その中には、投票シールの名前の変更（ADR 0028）のように見た人に伝え直したい変更と、動画の差し替えのように伝え直さなくてよい変更が混ざっている。原稿の変更の多くはAIエージェントが行っている。どの変更で案内を開き直すかを決める基準が原稿の近くにないと、変更のたびに作業者ごとに判断が揺れる。

## Decision

既読の記録はルームを含めず、本人×ステップ×案内の版の単位で、端末のブラウザ（localStorage）に残す。同じ本人が同じ版の案内を一度開いたら、別のルーム・別のタブでも自動では開かない。案内を開いた時点で既読とし、閉じる操作は待たない。開き直したい人は、従来どおり「進め方」から何度でも開ける。

保存先はサーバー（アカウント）ではなく端末にする。サーバーに置けば端末をまたいでも既読を保てるが、境界の型・保存先・APIの追加が必要になる。さらに、ゲストの本人は端末のCookieに結び付くため、端末をまたいで効くのは実質Googleでログインした人だけになる。端末に置いた場合に失うのは「別の端末で一度だけまた開く」ことで、案内が余分に一度開くだけで済む。

案内の版はステップごとに持ち、版を上げたステップだけを、既読の人にも一度だけ自動で開く。版を上げる基準は次のとおりとする。

- 上げる：前の版の案内のとおりに操作すると迷う、または誤る変更。操作の手順、決まり、判断基準、案内に出てくるボタンや機能の名前が変わる場合。
- 上げない：言い回しの調整、誤字の修正、図・動画の見た目だけの変更、スライドの並べ替え。
- 迷ったら上げない。Issueの目的は流れを遮らないことにあり、「進め方」から開き直せるため。
- 新しいステップに案内を足すときは版1から始める。新しいステップは既読の記録がないため、自動で開く。

版は案内の原稿と同じ場所に置き、そこに基準の要約と本ADRへの参照を書く。原稿を直す人やAIエージェントが、原稿を開いた場所で版を上げるかどうかを判断できるようにするためである。自動で開く案内を足したのに版を書き忘れた場合は、型検査で止める。

### 本ADRで決定しないこと

案内の原稿、どのステップで自動表示するか、「進め方」の振る舞いは[進行仕様](../product/sprint-flow.md)へ委譲する。記録のキーの具体的な形と、版を置く場所は実装（References）に置く。端末をまたいで既読を共有するかどうかは、見直す条件を満たしたときに別のIssueで扱う。

## Consequences

- 良い影響：2回目以降のワークショップでは、案内が自動で開かずに作業へ入れる。サーバー・境界の型・保存先は変えない。
- 良い影響：原稿を直すときに、版を上げるかを基準に沿って決められる。上げたステップだけが、既読の人に一度だけ伝え直される。
- 悪い影響（受け入れるリスク）：別の端末・別のブラウザ・シークレットウィンドウでは、案内が一度また開く。閲覧データを消した場合や、Safariを使った7日間にこのサイトで一度も操作しなかった場合も同じである。
- 悪い影響：数か月ぶりに参加して手順を忘れた人にも、案内は自動では開かない。その人は「進め方」から自分で開く必要がある。
- 悪い影響：版を上げるかどうかは人またはAIエージェントの判断に頼る。機械では、伝え直すべき変更を見落としたことを検出できない。
- 中立：導入前の既読の記録はタブを閉じると消える保存先にあったため、引き継がない。導入後に各ステップへ入ると、一度だけ案内が開く。
- 見直す条件：
  - 別の端末で案内が再び開くことへの不満が出たとき、または利用者が端末を頻繁に替えることが分かったとき。サーバー保存を検討する。
  - 久しぶりの参加者が手順に迷う様子が多く見られたとき。期間を置いた再表示や、「進め方」を目立たせる合図を検討する。
  - 版を上げ忘れた、または上げすぎたことがレビューで続けて見つかったとき。基準の書き方か、検出の仕組みを見直す。

## Alternatives Considered

PRの見直しで、次の案を利用場面ごとに比べた。

- 端末にルーム×本人×ステップで残す（見直し前の実装）：変更が最小だが、別のルームでは8ステップ分の案内がまた開く。Issueの目的の「また使ってもらったとき」を解決しないため採用しなかった。
- アカウントに保存する：端末をまたいで既読を保てるが、境界の型・保存先・APIが増える。ゲストには効きにくい。端末に残す案で困りごとが出てからでよいと判断した。
- 案内に「次から表示しない」を置き、本人に選ばせる：意図ははっきりするが、案内のたびに判断が1つ増える。押さない人には何も変わらないため採用しなかった。
