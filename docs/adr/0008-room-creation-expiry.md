# 0008: 作成受付と回復情報の寿命を分ける

- 状態：提案（0007の後継）
- 決定日：未決
- 記録日：2026-10-06

## 背景

同じ作成の再送を同じルームへ収束させるため、0007は要求と名前を期限なしで保持する案だった。名前の二重保持を短期化し、タブ閉鎖後も回復できるようにする。作成成功が不明なまま削除すること、対応不存在を公開証拠にすることは避ける。

## 候補と決定

正規UIは副作用のないサーバーUUIDv7発行、IndexedDB保存commit、別POSTの順に進む。ID内UTC msから24時間を固定し、再試行で延長しない。署名は採らず、自作の正しいv7も受理し得る。サーバー発行の真正性ではなく、ブラウザ時計に依存しない正規UIと古い同IDの拒否が目的である。期待principalは実セッションとの比較に限り使い、作成者・照会所有者は常に実セッションから決める。

RoomDOはcreator/request/room/deadlineを持ち、同期transaction内で一度だけ初期化、または期限後の未初期化閉鎖を決着させる。照合は初期化しない。初期化済みの事実は期限後もD1公開へ投影でき、公開は既存hidden行とpending対応へのCASとする。roomsと成果投影に独立した公開証拠を保持し、詳細削除・正常解散後も公開判定を失わない。

有限保持と時計後退を両立するため、D1の小さな単調retired watermarkを予約SQLとGCで共有する。要求単位の永久墓標を増やす方式は採らない。D1実行時計は秒精度を切上げて保守的に予約を拒否し、DOはUTC msで初回初期化を検査する。通常の時計差・遅延へのGC猶予は5分、future許容は60秒で、別の用途の値である。大きな時計異常・DB巻戻しは停止と照合を要する。

ブラウザはprincipal/requestごとに控えを持つ。現在の選択をtransactionで比較し、別意図を自動合流しない。送信前submittedをcommitし、成功receiptを保存してから通常認可の再訪へ進む。結果照会はread-onlyで、受付24時間と通常ルーム寿命を分ける。保存喪失・別端末からの意図発見は保証しない。

## 影響と見直す条件

要求詳細は期限＋猶予後の毎時bounded GCで削除する。通常ルーム名・成果の寿命は従来どおり。ready/closedの最小対応は通常ルーム・成果の寿命終了後に整理する。DO不通のunknownは名前を消して最小照合情報を保全・監視するため、全コピーの24時間消去は保証しない。DO markerは旧caller排除の安全を優先して今回積極的に削除せず、保持例外とする。オフラインのブラウザ控え、ログ・backupの寿命もD1詳細と同一ではない。

追加migrationで旧要求を固定24時間の互換猶予へ移し、新規v4は拒否する。D1のINSERT guardも旧Workerの追跡外新規予約を拒否する。大小衝突は保全して409、無条件統合しない。旧RPCは新規初期化を拒否する。GCは切替確認後の明示有効化が必要で、旧版への単純rollbackは行わずforward fixする。

比較の背景は[Issue533](https://github.com/engineer-first/idea-boost/issues/533)と[PR551](https://github.com/engineer-first/idea-boost/pull/551)。運用・移行の正本は[ルーム作成の受付と回復](../operations/room-creation.md)。24時間の適切さ、unknown滞留、marker廃棄は利用状況を見て見直す。
