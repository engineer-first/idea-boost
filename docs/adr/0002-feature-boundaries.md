# 0002: 機能単位で分割し公開境界を持つ

- 状態：採用（既存判断の整理）
- 決定日：不明。PR #128で採用を確認
- 記録日：2026-09-30

## 背景

従来のリポジトリ全体をAtomicの粒度で分ける構成では、1機能の変更が複数の階層とapp内ロジックに散在した。粒度名だけではappへの逆流依存や非UIの置き場を制約できなかった。

## 候補と決定

全体のAtomicツリーではなく、ユーザーに見える機能単位で`features/`へまとめ、`index.ts`を外部向け公開境界とする。変更理由が同じものを近くに置き、依存方向は静的検査する。ドメインを知らない汎用UIは`components/ui/`、インフラは`lib/`、通信の形は`contracts/`へ置く。

feature内部のui/logic二層は当初の方式であり、現在は[ADR 0003](0003-feature-bands.md)が扱う。全体の分割軸と内部の配置は別の判断とする。

## 影響と見直す条件

機能の変更範囲と公開APIを把握しやすくなる。一方、共有部品への昇格やfeature切り出しには判断が必要で、許可する依存を増やすときは循環を確認する。依存の可視化はディレクトリだけに任せずStorybookの実測依存図を使う。

複数機能にまたがる変更が恒常化した場合は、まずドメイン境界や共通資産の責務を見直す。粒度の見栄えだけを理由に全体Atomicへ戻さない。
