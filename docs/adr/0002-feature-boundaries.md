# ADR 0002: 機能単位で分割し公開境界を持つ

## Context

リポジトリ全体をAtomicの粒度で分けた構成では、1機能の変更が複数階層と画面内のロジックに散在していた。粒度名だけでは画面側への逆流依存や非UIの置き場を制約できなかった。

## Decision

ユーザーに見える機能ごとに実装をまとめ、機能の外へ公開する境界を明示する。変更理由が同じものを近くに置き、機能間の依存方向を静的に検査する。ドメインを知らない汎用UI、インフラ、通信契約を機能から分ける。変更範囲と依存関係をレビュー可能にするためである。

### 本ADRで決定しないこと

関数・通信形式・保存の具体手順と移行方法は、開発規約へ委譲する。参照先はReferencesに示す。

## Consequences

良い影響は、機能の変更範囲と公開する責務を把握しやすくなること。悪い影響は、共通化と機能の切り出しの判断が引き続き必要なこと。中立の影響として、見た目の粒度と機能境界は一致しなくなる。複数機能にまたがる変更が恒常化した場合は、分割したドメインの責務を見直す。

2026-11-03に実コード・一次資料を照合。根拠未確認：実装または提案記録は確認できるが、オーナーがこの技術方針・比較理由まで採用した元発言は確認できない。実装済みであることだけではAcceptedにしない。決定日は不明のためdateは旧ADRの記録日。

## Alternatives Considered

全体をAtomicの階層に分け続ける案に対し、機能単位の分割を実装した。当時の比較資料には、ディレクトリだけでは実際の利用関係を示せないという制約も残されている。
