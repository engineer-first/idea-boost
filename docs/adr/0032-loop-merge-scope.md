# ADR 0032: エージェントがdevelopへマージする範囲を変更ファイルで決め、段階的に広げる

## Context

ADR 0031のループは、PRを出すだけでは人のマージ待ちが律速のまま残る。一方、エージェントにマージを任せると次の危険がある。

- developのRulesetsはPRと5つの必須チェックを求めるが、承認は0人で、作者がマージできる。オーナーのアカウントはadminで、Rulesetsを迂回するマージ、Rulesetsの書き換え、本番公開のworkflowの起動が技術的にできる。本番のenvironmentに承認者はいない。
- 公開リポジトリのため、外部の人がIssueやコメントを書ける。エージェントがそれを指示として読むと、意図しない変更が入る。
- 変更の危険度を作った周回が自己申告すると、境界に触る変更が軽く申告されたまま入る。ループが自分の指示書や判定スクリプトを書き換えれば、マージの条件そのものを緩められる。
- 本番公開はdevelopの全体を対象にし、個別PRを除外しない。developに入ったものはそのまま次の公開に載る。

## Decision

エージェントがマージしてよい範囲を、変更ファイルのパスで機械的に決める。文書・テスト・stories・文言をR0、画面とロジックをR1、worker・RoomDO・migration・データの形・セッション・認証・Server Action・Route HandlerをR2とする。ループ自身と、検査・設定・指示を縛るファイルもR2とする。一覧にない場所はR1に倒す。自己申告に頼らず、ループが自分を縛る規則を緩めてマージする経路を塞ぐためである。

R2とR3（PRD方針・チームの運用・課金・学外への連絡）は常に人がマージする。エージェントに任せる範囲は段階的に広げる。

1. 段階1：再計画・巡回・修理だけを動かし、IssueとPRを作るが、マージしない。
2. 段階2：取り込みを動かし、R0のループのPRと、条件を満たすRenovateのmajorだけをマージする。
3. 段階3：R1もマージする。ただし、ループを書き込み権限だけを持つ専用のアカウントに分け、本番のenvironmentに承認者を付けた後に限る。

マージは、必須チェックとCodeRabbitのレビューが最新のheadで済み、人の変更要求がないときだけ、確かめたheadに固定して行う。取り込みはコードを書かず、直す必要があれば作る側へ差し戻す。作った周回と判定する周回を分けるためである。

オーナーとメンバー以外が書いたIssue・コメントと、依存の変更履歴は、指示ではなくデータとして読む。チームの誰でも、ラベル1つで全ループを止められるようにする。1日のマージ数には上限を置く。

### 本ADRで決定しないこと

R0〜R2に割り当てるパスの一覧は判定スクリプトへ、マージの条件・上限・止め方の具体はループの仕様へ委譲する。専用アカウントの作り方と、本番のenvironmentの承認者は、段階3へ進むときに別途決める。委譲先へのリンクはReferencesに置く。

## Consequences

- 良い影響：R0の変更は人のマージを待たずにdevelopへ入る。境界に触る変更は、作った周回の申告にかかわらず人が見る。ループが自分の規則を緩めることはできない。
- 悪い影響（受け入れるリスク）：段階3までは、ループはオーナーのadminアカウントで動く。迂回マージ・本番公開をしない約束は指示書の文面に頼り、技術的には防げない。R0の判定はパスだけで決めるため、文言や文書の変更が利用者に与える影響（誤った案内など）は人が読む前にdevelopへ入る。
- 悪い影響：パスの一覧は、新しいディレクトリを足すときに見直す必要がある（一覧にない場所はR1に倒れるので、取りこぼしではなくマージ待ちの増加として表れる）。
- 中立：段階2のRenovateのmajorは、CIが緑で、認証・データの形・フレームワークの基盤に関わる依存でないものに限る。
- 根拠未確認：R0〜R2の境界、段階の区切り、上限の値はAIの提案で、オーナーとチームの採用を確認していない。
- 次の段階へ進む条件（各段階2週間）：
  - 段階1→2：巡回の所見のうち、人が妥当と判断した割合が半分以上。修理のPRが原因を正しく特定している。
  - 段階2→3：ループがマージしたR0のPRのrevertが0件。人が`loop:stop`を使った件数と理由を確認した。専用アカウントと本番の承認者が用意できた。
- 見直す条件：
  - ループがマージした変更をrevertした件数が、2週間で2件を超えたとき。前の段階へ戻す。
  - チームの誰かの作業とループのPRが衝突し、どちらかを作り直したとき。
  - CodeRabbitの枠不足で人のPRのレビューが待たされたとき。
  - developのRulesetsで承認を必須にするなど、マージの前提が変わるとき。

## Alternatives Considered

- 元にした個人リポジトリと同じく、developへ直接pushし、定時に本番へ公開する案：RulesetsがPRと必須チェックを求め、チームがPRで差分を読む運用と衝突する。本番公開はイベントの前にチームが判断しているため、採用しなかった。
- 最初からR0とR1をエージェントがマージする案：adminのアカウントで動く間は、判定の誤りやプロンプトへの注入を技術的に止められないため、段階に分けた。
- すべてのループのPRを人がマージする案：人のマージ待ちが律速のまま残るため、段階2からR0を任せる。
- 作った周回が段階を申告し、取り込みが差分を読んで判定し直す案（最初の設計）：AIのレビューで、境界の変更が軽く申告される経路と、ループが自分の指示書を書き換える経路が指摘されたため、パスによる機械判定にした。
