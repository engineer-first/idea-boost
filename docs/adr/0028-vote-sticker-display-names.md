# ADR 0028: 投票シールの画面の名前を「イチオシ！」「需要ありそう」にし、内部の種別名は変えない

## Context

ドット投票には、1人1票で5ポイントのシールと、1人3票で1ポイントのシールの2種類がある。画面ではこれを「主観」「客観」と呼び、それぞれの基準（「激しく共感する、取り組みたい」「自分以外の人にも価値がありそう」）を投票パレットの各ボタンに添えていた。

「主観」「客観」は、基準の一文を読まないと何を選べばよいかが分からない名前だった。調べた範囲では「主観票・客観票」という決まった言い方は外部に見つからず、IdeaBoost独自の名前だった。

一方、コードと保存データでは種別を `subjective` / `objective` と呼んでいる。この名前はWebSocketのプロトコル、RoomDOの保存行、運営向けの記録、持ち越しデータ、色トークン（`vote-subjective` / `vote-objective`）に入っている。画面の名前に合わせて変えると、保存済みデータの移行と、接続中のクライアントとの互換を同時に扱う必要がある。

## Decision

画面と文書で使うシールの名前を「イチオシ！」（1票・5ポイント）と「需要ありそう」（3票・1ポイント）にする。表記はどこでもこの形にそろえ、数え方は「票」のままにする。名前自体が意味を伝えるようにすることで、パレットに基準の一文を常に出さなくても選べるようにする。

基準の一文は消さずに、名前と並べてステップガイドで示す。投票パレットには、シールの名前と残票だけを出す。

コードと保存データの種別名 `subjective` / `objective` は変えない。画面の名前は種別名と対応だけを持ち、名前の変更が保存形式やプロトコルに波及しないようにする。どの種別名がどの画面の名前に当たるかは、用語集を正本にする。

### 本ADRで決定しないこと

シールのアイコン・色・形と、パレットの並べ方は、この判断では扱わない。現在の値は[DESIGN.md](../../DESIGN.md)にある。各名前の意味と、使わない言い方は[用語集](../glossary.md)へ委譲する。ステップガイドをどのステップで開くかは[進行仕様](../product/sprint-flow.md)へ委譲する。内部の種別名を変えるかは、別のIssueで扱う。

## Consequences

- 良い影響：シールの名前だけで、自分が推したいものと、誰かに価値がありそうなものの違いが分かる。名前の変更は画面の文言と文書だけで済み、保存データの移行は要らない。
- 悪い影響（受け入れるリスク）：画面の名前（イチオシ！・需要ありそう）とコードの名前（`subjective` / `objective`）が一致しない。新しく読む人は用語集で対応を確かめる必要がある。
- 悪い影響：投票パレットから基準の一文を外したため、ステップガイドを閉じた後は、名前だけを頼りに投票する。基準を見直したいときは「進め方」から開き直す。
- 中立：デザインスプリントの元の手法は主観・客観の投票として知られているため、LPでは元の手法を参考にしていることを一言だけ添える。
- 見直す条件：
  - 名前だけでは迷う、または基準を見直すために「進め方」を開く様子が多く見られたとき。
  - 内部の種別名を変える作業を行うとき。その時点でこのADRの「内部の種別名は変えない」部分を見直す。

## Alternatives Considered

Issueでは、次の名前の組み合わせを比べた。

- 「すごくいいね」「いいね」：「いいね」が弱い好みとして使われ、自分以外の誰かのためという意味が消える。
- 「ほしい！」「ありそう」：アイデアには自然だが、課題（困りごと）に貼ると不自然になる。
- 「自分に刺さる」「誰かに刺さる」：対比は一目で分かるが、オーナーは最終的に採用しなかった。
- 「イチオシ！」「アリ」、「熱盛！」「需要ありそう！」：オーナーがコメントで挙げた候補で、最終的に「イチオシ！」「需要ありそう」に決めた。

内部の種別名は、画面の言葉だけを変える案、色トークン名も変える案、保存データまで変える案を比べた。オーナーは、今は画面の言葉だけを変え、今後の開発に響く箇所の改名は別のIssueに分けると決めた。
