# 0022: ゲストは入室前に同じ本人のCookieを更新する

- 状態：提案
- 決定日：2026-10-29
- 記録日：2026-10-29

## 背景

[0010](0010-room-entry-authentication.md) は、入室時に認証の残りが5時間を下回るとGoogleで再認証させる。
ゲスト（[0021](0021-guest-session-identity.md)）にはGoogleの本人がなく、ログイン操作なしで使い続けることが目的なので（[PBI #749](https://github.com/engineer-first/idea-boost/issues/749)）、この前提がそのままでは成り立たない。
一方で、Cookieの消失・実期限切れの後に、名前やルームURLから以前のホスト・付箋・投票を復元してはならない。

## 候補と決定

有効なゲストが作成・参加・再入室・参加切替をするとき、または在籍するルームを直接開いたとき、残りが5時間を下回っていれば、同じ `sub` のCookieを発行から7日で再署名する。5時間以上あれば何もしない。accountの不足は0010どおりGoogleで再認証する。

- Nextは認証付きの `POST /api/auth/guest/refresh` を呼ぶ。Workerは検証済みセッションの `sub` だけを使い、`kind` がguestで、D1に行があり、メールとGoogleの紐付けがない場合だけ同じ `userId` を返す。ブラウザが送るIDや期限は受け取らない。
- NextはWorkerの応答が要求時の `sub` と一致した場合だけ再署名し、以降の入室判定とチケットに更新後の `exp` を使う。
- ページの描画中はCookieを書けない。直接の再訪で残りが不足するゲストには、画面が更新用のServer Actionを自動で呼んで同じページを再読込する。このActionはルームの在籍をWorkerで確認してから更新し、ルームに入らない延長には使えない。ゲストに認証方法の選択を見せないため、ボタン操作を挟まない。
- 既存WebSocketの期限は延ばさない。0009の実期限での拒否を維持し、停止した画面は再読込で現在のCookieから判定し直す。新しい接続でsnapshotを受信してから操作を再開する。
- Cookieの消失・署名不正・実期限切れ・D1の行がない場合は更新しない。新しく始めると別の本人になり、以前の権限は戻らないことを画面で伝える。

ページを開くたびの無条件延長は、使っていない端末の本人を延ばし続けるため採用しない。作業中の自動更新は、既存WebSocketの期限を変えられず、再接続を伴う点が入室時の更新と変わらないため見送る。更新用トークンや短命JWTは、失効を個別に管理する仕組みが要るため導入しない。

## 影響と見直す条件

- 1週間に1回以上入室するゲストは同じ本人を使い続けられる。7日間入室しなければ本人を失う。ルームと成果の保存期限（成果の30日など）はこの判断で変えない。
- 一度漏れたゲストCookieは、入室を続ける限り更新され続ける。0021と同じく個別失効の仕組みはない。「本人情報を消す」もこのブラウザのCookieを消すだけで、消す前に複製されたCookieは無効にならない。
- Server Action内で読めるCookieは要求が届いた時点の値なので、更新の応答と別タブの操作（本人情報の削除やGoogleログイン）はブラウザ上で後に届いた方が残る。削除の直後に別タブの自動更新が届くとゲストのCookieが戻り得る。この競合はまれで、戻るのは同じ本人なので受け入れる。
- Google連携（[#850](https://github.com/engineer-first/idea-boost/issues/850)）では、連携の確定と更新APIの判定の間にゲストのCookieが発行され得る。連携後の本人は0010の再認証に従うべきなので、#850 で連携と更新の順序をWorker側で保証する。
- 5時間を超えて1つのルームに入り続けると、0010と同じく実期限で接続が止まる。再読込で残りがあれば更新して続けられるが、実期限を過ぎていれば同じ本人には戻れない。

本人の個別失効（削除した本人の無効化を含む）が必要になったとき、または作業中の継続を5時間より長く保証する必要が出たときに見直す。
