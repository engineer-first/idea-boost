# ADR 0033: 共有付箋の移動は本人の操作を優先し、失敗を数えて減らし続ける

## Context

共有付箋を掴んで動かす操作は、共有・グループ化・2軸マップの中心にある。ADR 0006 は、移動を RoomDO の一括確定とし、移動の開始時に対象の付箋の版が一致することを求め、掴んでいる間は付箋を占有する形にした。ADR 0019 は、保存待ち中の次の移動を本人の画面で受け付けるが、競合・切断・再同期では未送信の移動を捨てると決めた。

「付箋を動かしたはずが動いていない」という報告は、2026-10 から繰り返し出ている。そのたびに原因を直したが、原因は毎回別の場所にあり、直した後に何が残っているかを数える手段がなかった。2026-11-27、オーナーは、付箋の移動の失敗を体験の中核の問題として直すことと、一度直して終わりにせずループで直し続ける仕組みを求めた。

同日、2人のブラウザと実 RoomDO に片道 80ms の遅延を入れて場面ごとに数えた。1人で動かす場面と、2人が別々の付箋を同時に動かす場面は全部成功した。次の場面は失敗した。

- 共有ステップでマイ付箋をボードへ置いた直後に掴み直す：0/3。共有の応答を待つ間、画面がすべての共有付箋の移動開始を止めていた。
- 掴んでいる最中に時間切れの通知が届く：0/4。RoomDO は時間切れの後も移動を受け付けるが、通知を受けた本人側が移動を取り消していた。
- 相手が動かし終えた直後の同じ付箋を動かす：0/10。本人が持つ版が古く、RoomDO が開始を断っていた。

失敗はどれも、RoomDO が共有状態を壊さないために断った結果ではなく、版の一致を前提にした仕組みと、本人側の安全側の取り消しから出ていた。Figma・tldraw・Excalidraw は、本人の操作をすぐ反映し、届いた通知で進行中の操作を巻き戻さず、同じ対象の競合は後から届いたほうに決めて、やり直しを求めない。

## Decision

共有付箋の移動は、本人の操作を優先して成立させる。移動を直す・足すときは、次の順で判断する。

- RoomDO が受け付ける移動を、画面側が先に止めたり取り消したりしない。画面が移動を止めるのは、RoomDO も断る場合（工程が移動を許さない、接続が切れている、ルームを出た）だけにする。
- 届いた通知で、本人が掴んでいる移動や、離し終えて未送信の移動を、関係のない分まで巻き戻さない。巻き戻すのは、その通知で成立しなくなった移動だけにする。
- 版が古いことだけを理由に本人へやり直しを求めない方向へ寄せる。本人が離した位置を保ったまま、最新の状態に対して送り直す。
- 共有状態の権威と一括確定（ADR 0006）、可視性と認可の検査は RoomDO に残す。本人の画面の表示を共有状態の真実にしない。

移動の失敗は、場面ごとに数え、数字で直す。計測の場面と下限を台帳に置き、下限は直すたびに引き上げて下げない。ループは、移動に関わる変更のたびに数え、下限を下回る変更をマージせず、台帳に残る原因を待ち行列の先頭寄りに置いて直し続ける。

理由は2つある。付箋が言うことを聞かない体験は、初学者チームが画面を信頼しなくなる直接の原因になる。もう1つは、これまでの個別の修正が再発を止められなかったのは、失敗を数える手段と、守るべき優先順が書かれていなかったためである。

### 本ADRで決定しないこと

計測の場面・下限・失敗の定義・原因の一覧・各ループの手順は移動の台帳と指示書へ、移動の通信形式と操作の詳細はキャンバス操作仕様へ委譲する。版が古い移動の送り直しを1枚の移動に限るか複数枚にも広げるか、同時に同じ付箋を掴んだときの占有をやめるか、本番での失敗の数え方は、それぞれの Issue で決める。委譲先は References に置く。

## Consequences

- 良い影響：共有の直後・時間切れ・相手の移動の直後のように、利用者がよくやる動きで付箋が掴めない・戻る場面が減る。直した効果と悪化が、場面ごとの数字で分かる。
- 良い影響：移動に関わる変更のたびに同じ場面を数えるので、別の修正で前の修正が壊れても気づける。
- 悪い影響：同じ付箋を2人が続けて動かすと、後から動かした人の位置が黙って勝つ場面が増える。先に動かした人は、自分の位置が変わった理由を画面からは知りにくい。ほかの人の途中の位置と名前を出している表示で補う。
- 悪い影響：計測は実ブラウザ2人を起動して6〜8分かかり、タイミングに依存する場面は1回の結果がぶれる。2回続けて下回ったときだけ悪化として扱う。
- 中立：ADR 0006 の一括確定と ADR 0019 の本人の画面での受け付けは残る。ADR 0019 の「競合・切断・再同期では未送信の移動を捨てる」は、この ADR に沿って、成立しなくなった移動だけを捨てる形へ狭めていく。複数枚の移動を競合で中断する現在の操作仕様は、Issue で決めるまで変えない。
- 保証しない範囲：計測は手元の遅延つき環境で場面を数えるもので、本番で利用者がどの失敗にどれだけ当たっているかは分からない。本番での数え方は未実装である。iPad とスマホの指での操作は数えていない。
- 根拠未確認：失敗を直すこととループで直し続ける仕組みは、オーナーが 2026-11-27 に求めた。上の判断の順（画面側が先に止めない、巻き戻しを狭める、送り直す）と計測の方式は AI の提案で、オーナーが個別に採用した記録はないため Proposed とする。
- 見直す条件：
  - 送り直しや巻き戻しの縮小で、位置や分類が利用者の意図と違う形で保存される不具合が出たとき。
  - 本番の計測ができ、手元の場面と本番で多い失敗が食い違ったとき。場面と優先順を直す。
  - 計測のぶれで、ループが誤った所見や差し戻しを繰り返すとき。

## Alternatives Considered

- これまでどおり、報告が来た失敗をその都度直す案：2026-10 から同じ種類の報告が続き、直した後に残る失敗を誰も数えていなかった。同じことを繰り返すため採らない。
- 版の一致と占有をやめ、位置を「最後に届いた値」で決める方式へ作り替える案：ほかのツールに最も近いが、一括確定・分類の再編・元に戻す操作の前提を同時に変えることになる。まず画面側の取り消しと送り直しで失敗を減らし、数字を見てから決める。
- 計測を PR の必須チェックにする案：実ブラウザ2人の起動に時間がかかり、ぶれる場面がある。CI の基準（ADR 0030）に合わないため、ループが移動に関わる変更のときに回す形にした。

## Related ADRs

- ADR 0006：移動を RoomDO の一括確定とする判断。権威と一括確定は残し、版の不一致で本人にやり直しを求める点をこの ADR で狭めていく。
- ADR 0019：保存待ち中の移動を本人の画面で受け付ける判断。未送信の移動を捨てる範囲をこの ADR で狭めていく。
- ADR 0031：ループで改善から公開までを回す判断。この ADR は、そのループに移動の計測と台帳を足す。
