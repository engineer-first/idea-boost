# 0006: 共有付箋の移動をRoomDOのtransactionとして確定する

## この文書で使う用語

「原子的確定」の「原子的」は、変更を分割して確定できないという意味。たとえば3枚を移動して分類も変える操作では、3枚の位置・分類・成功記録をすべて保存するか、すべて保存しないかのどちらかにする。1枚だけ動いたり、位置だけ保存されて分類が変わらなかったりする状態を残さない。

| 用語                              | この文書での意味                                                                                                                                                                                                     |
| --------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 原子的確定 / transaction          | 関連する変更をひとまとまりとして保存すること。途中で失敗したら、そのまとまりの変更をすべて取り消す。                                                                                                                 |
| RoomDO / SQLite / transactionSync | RoomDOはルームごとの共有状態を管理するサーバー側の仕組み（Cloudflare Durable Object）。SQLiteはその保存先。`transactionSync`は関連する保存を一括で成功または取消にするための機能。                                   |
| client / member / peer            | clientはブラウザ側のアプリ、memberはルームの参加者、peerは他の参加者の接続。                                                                                                                                         |
| drag / pointerup                  | dragは付箋を掴んで動かす操作。pointerupはマウスボタンなどを離した時の入力イベントで、移動の確定要求を送るきっかけ。                                                                                                  |
| preview / ローカルdelta           | previewは保存前に見せる仮の移動。本人はローカルで即応し、他の可視な参加者はRoomDOが認可した途中位置を表示する。deltaは開始位置からの移動量で、同じ量を選択した全付箋へ適用する。                                     |
| 固定集合                          | 掴み始めた時点で決めた移動対象の付箋一覧。移動途中に対象を追加しない。                                                                                                                                               |
| ACK                               | サーバーからの応答。開始の許可や確定結果を知らせる。応答が届かなくても、保存自体は成功している場合がある。                                                                                                           |
| lock / lease                      | lockは同じ付箋への競合する移動を防ぐ予約。leaseはその予約の有効期間で、接続が応答しなくなっても予約を永久に残さないための期限。                                                                                      |
| half-open接続 / ハイバネーション  | half-openは通信が途絶えているのに切断として検知されていない接続。ハイバネーションは接続を維持しながらRoomDOを休止する仕組み。どちらでも操作・予約・確定結果を取り違えない必要がある。                                |
| 版 / 専用期待版 / ABA             | 版は更新のたびに増える番号。期待版は操作開始時に確認した番号で、確定時に他の更新がないか検査する。位置・可視性などの番号を本文・票の更新から分ける。ABAは値がA→B→Aと戻る変更で、見た目が同じでも版の違いで検知する。 |
| receipt                           | 成功した移動の記録。変更前後の位置・分類と検査に必要な版を持ち、将来のUndoが他者の変更を壊さないか判断する材料にする。                                                                                               |
| ID墓標                            | 詳細な結果を削除した後も、操作IDが使用済みであることだけを残す記録。古い要求で同じ操作を再び確定させないために使う。                                                                                                 |
| pending / 結果照会 / unknown      | pendingは確定要求を送ったが結果が分からない状態。結果照会は操作IDでサーバーへ保存済みの結果を尋ねること。unknownは照会で結果を取得できない応答で、取消成功を意味しない。                                             |
| streaming保存                     | drag中の座標を継続して保存する旧方式。新方式では途中座標はpreviewにとどめ、離した時に確定する。                                                                                                                      |
| group / 分類副作用                | groupは1-3工程の付箋の分類。分類の「メンバー」は所属する付箋を指す。分類副作用は移動に伴う分類の名前・所属などの変更で、移動していない付箋にも影響しうる。                                                           |
| 可視性 / private                  | 可視性はその参加者がデータを見られるかどうか。privateは他の参加者へ共有していない付箋。位置だけでなく分類やreceiptの返信にも可視性の検査が必要。                                                                     |
| snapshot / batch / 投影           | snapshotは参加者へ送る現在状態、batchは確定した複数の変更をまとめた通知。投影は共有状態から、現在工程と受信者の権限で見せられる内容を取り出すこと。                                                                  |
| map / 表示px / 評価値             | mapは価値と実現のしやすさを評価する平面。表示pxは画面上の距離、評価値は保存する0..100の値。zoomが変わっても評価値の意味は変えない。                                                                                  |
| clamp / 共通の線形変換 / 再投影   | clampは移動を範囲内に制限すること。共通の線形変換は、全付箋で同じ尺度を使って評価値と画面座標を対応させる計算。再投影は保存値を変えず、平面寸法などに合わせて表示位置を計算し直すこと。                              |
| drop-only共有 / Undo / Redo       | drop-only共有は有効な場所へ付箋を離した時だけ共有・非共有を確定する方式。Undoは確定した移動を戻す操作、Redoはその移動をやり直す操作。それぞれ#524・#525で扱う。                                                      |

## 背景

単一dragの途中座標をその都度保存すると取消で戻せず、複数移動や分類副作用も部分確定する。ACK待ちで本人previewを始めると通信遅延が入力の応答性を決めてしまう。RoomDOのハイバネーションとhalf-open接続でも、確定結果とlockの所有を取り違えない必要がある。

## 候補と決定

旧single-dragのstreaming保存を複数枚へ拡張する方式は、全件取消とgroupの原子的確定を保証できないため採らない。クライアントpreviewを共有状態の真実にする方式も、工程・可視性・競合の認可をクライアントへ移してしまうため採らない。

本人previewは固定集合のローカルdeltaとして描画し、確定座標から分ける。RoomDOはSQLiteに操作ID、接続所有者、全対象lock、専用期待版、leaseと成功receiptを保存し、pointerupで位置・分類・receiptをtransactionSyncに含める。送信後は結果照会だけで復帰し、エラーへの即時再照会で応答ループを作らない。閉鎖後もmember本人には保存済み結果を返し、非memberまたは操作削除後には内容を含まないunknownを返してpendingを終端にする。新旧lockは相互に競合し、対応snapshotで新UIのtransaction経路を選ぶ。

## 影響と見直す条件

遅延したACKを待たず本人が操作でき、全対象と分類が成功か拒否のどちらかになる。位置と可視性の版は本文や投票から独立し、ABAも検知する。receiptは将来の安全な逆操作へ全影響対象の版とgroup前後を渡す。

peer previewは、保存済み操作の全件lock・所有接続・現在member・工程・可視性・専用版を検査した後、現在memberかつ全対象が可視な受信者へ座標だけ非永続配信する。UIは確定notesと別のoverlayを持ち、操作ID・単調な通知番号・工程版・全対象版で古い通知を拒否する。取消・失効・切断・除外・工程変更・採用・拒否で解除し、確定batchを終了通知より先に送る。lease表示は受信からの相対期間を単調時計で測り、端末時計のずれに依存させない。新preview未対応の旧clientは確定位置のみ受け取り、途中保存を互換目的で追加しない。旧clientの途中保存とprivate共有は互換経路に残るため、この保証を全操作へ拡張したとは扱わない。成功receiptは24時間で削り、ID墓標はルーム削除まで保持するため操作数に比例する小さい永続コストを持つ。長期ルームの操作数や保存量が問題になった場合は、操作IDの世代境界と保持期間を合わせて見直す。

## 可視性とmap表示の補足

receiptには実際に変わった分類の完全な前後と、その全メンバーの検査版を記録する。無関係な分類を丸ごと保存・配信すると、工程を戻して非共有化した旧メンバーの存在や分類名を再公開しうる。不可視な副作用を単に切り捨てると安全な逆操作の検査対象が欠けるため、その操作は位置・分類ごと拒否する。snapshot、確定batch、新move由来の互換group配信は現在工程と全メンバーの可視性で同じ投影を使う。保存済みreceiptの返信時にも再検査し、不可視な対象があれば成功statusを保ったままreceipt全体を伏せる。UIは失敗と表示せず、前の操作のreceiptを逆操作情報として残さない。

mapの個別CSS clampは0..100の共通deltaを端で異なる画面deltaへ変えるため、中心を共通の線形有効域に配置し同じ式でpointer入力を逆変換する。軸欄・gap・borderを除いた平面寸法と、全付箋の最大表示高を共有して使う。意味上の評価値0..100とサイズ変更時の保存値は保つ。長文の本文は保持し、表示高を平面高75%までに制限して正の移動域を残す。代償として長文表示と他の付箋の中心域が連動するため、高さ・mapサイズ変更時は表示を再投影する。
