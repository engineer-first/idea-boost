# 0004: 付箋ボードを自前で実装する

- 状態：採用（既存判断の整理）
- 決定日：2026-07-04（PR #76の既存記録による）
- 記録日：2026-09-30

## 背景

必要な中心操作は付箋の作成・編集・移動・投票で、自由描画アプリ全体ではない。未共有付箋とステルス投票を、端末で隠すだけではなくサーバー側で保護する必要がある。当時のtldrawとSupabase BroadcastのPoCは、永続化・初期snapshot・競合解決・認可が不足していた。

## 候補と決定

tldrawのドキュメント同期、DIY同期、自前の構造化ボードを比較し、自前ボードを採用した。付箋をアプリの明示的なデータとして扱い、Pointer Eventsで操作する。必要な付箋UXを仕様として取り入れ、描画SDKと同期モデルを全面採用しない。

当時はSupabase RLSと既存の認証・テスト資産を維持する理由もあった。この理由は[Cloudflare移行](0001-cloudflare-room-authority.md)後の現行構成には当てはまらない。現在はRoomDOの認可と受信者別配信が同じ可視性要求を担う。カーソル共有やパン・ズームも実装済みで、当時の「4操作だけ」を現在の全機能とは説明しない。

## 影響と見直す条件

進行・候補整理・可視性をドメインに合わせられる。一方、選択・編集・ドラッグ・中断・キーボード・パン・ズームを自前で保守する責任を持つ。自由描画や汎用シェイプなど要求が大きく変わり、保守費用が既存SDK採用を上回る根拠が得られたら見直す。Cloudflare採用だけをtldraw採用の根拠にはしない。
