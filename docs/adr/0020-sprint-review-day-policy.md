# 0020: Sprintのreview日を含む割当期間をversionで区別する

- 状態：提案
- 決定日：未決定
- 記録日：2026-10-28

## 背景

Milestoneのdue日にreview/demoを行う一方、v2の自動割当はその日のJST 00:00に終了する。そのためreview当日には未完了のopen Issueが次期へ移り得る。未完了を繰り越す仕様は保ち、review日いっぱいを当期として扱う運用を提案する。

ただし既存のv2期間はwhiteboardの過去集計でも使われる。自動割当だけでv2の意味を変えると、同じmetadataが処理・版によって別の境界を示す。過去の所属を再解釈したり、実Issueを前期へ戻したりする変更は含めない。

## 候補と決定

- **v3だけdue翌日のJST 00:00をexclusiveな終了にする案を提案する。** v2はdue日のJST 00:00終了のまま読める。コメントとJSONのversionは一致を必須とし、不明versionを推測しない。
- v2を一律に1日延ばす案は、既存期間・過去の境界を無言で再解釈するため採らない。
- 前期優先の自動補正で重複を解決する案は、`assignment_start_date`と実効開始日を二重化するため採らない。v3の後続開始は前期dueの翌日へ明示登録し、期間が重なる時刻は従来どおり割当を保留する。番号・title・API配列順は日程の根拠にしない。

## 影響と見直す条件

開始日の意味は変えず、review日の全時間を当期へ含められる。代償としてv3を採用する際には次期の明示開始日を調整し、日程を読む利用先の対応も必要になる。前期がv2なら次期はdue日開始、前期がv3ならdue翌日開始とし、移行のために過去の境界を延長しない。

コードのマージと運用採用は分ける。既存metadata・実Issueはこの提案では変更しない。whiteboard現行releaseはv2 strict parserのみなので、v3の実登録前に別途対応を揃える。終了済みのpin境界は保ち、未pinのactive期間は対応後に正式な期間で移行を判断する。[移行時の確認](../team/issues.md#review日を含むv3運用採用は別途判断)を満たすまで適用しない。

reviewが日付でなく特定時刻に終わる運用や、期間の重なりを明示的に認める運用へ変わる場合は、推測を追加せず新しい契約として見直す。
